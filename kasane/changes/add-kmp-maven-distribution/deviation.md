# Deviation: add-kmp-maven-distribution

- design Decision 1 / tasks 2.1「ルートには vanniktech / KGP の型参照も `apply false` も足さない」: design では ルート `kmp/build.gradle.kts` に plugin 宣言を置かない → 実装では `alias(libs.plugins.kotlinMultiplatform) apply false` の 1 行だけをルートに置いた。理由: 発行プラグインを `:ksdialogs-kmp` にだけ適用するとモジュール間の plugin 集合がずれ、Gradle が KGP を 2 つの classloader に別々に読み込み、両モジュールが共有する Kotlin/Native ツールチェーンの build service が型不一致で構成段階から失敗する (`Could not create task ':ksdialogs-kmp:linkDebugTestIosArm64'`)。vanniktech / AGP はルートに足しておらず、design が避けたかった「ルートで発行プラグインの型を参照する」状態にはなっていない (ガードはタスク名のみで判定)。別案 (`:api-surface-check` に発行プラグインの `apply false` を並べる) は発行しないモジュールに発行の宣言が載るため不採用 (2026-09-09、実装ワーカーの発見。オーナー承認済み 2026-09-09: 現状のまま採用、姉妹ビルド android/ のルートと形を揃える)
- [付随修正] tasks 2.1 の字面 `KotlinMultiplatform(JavadocJar.Empty(), sourcesJar = true)`: `sourcesJar = true` は vanniktech 0.37.0 で deprecated (構成のたびに警告) → 同義の `sourcesJar = SourcesJar.Sources()` にした (`android/build.gradle.kts` の `AndroidSingleVariantLibrary` と同じ書き方)。挙動は同一 (2026-09-09)
- design Decision 2「`:ksdialogs-kmp` の group / version をルートで与える」: 実装ではルートが `extra["ksdialogsVersion"]` に導出値を置き、モジュール側が `version = rootProject.extra["ksdialogsVersion"]` で読む形にした (`subprojects {}` で一律に与えると `:api-surface-check` に Maven 座標が付くため)。spec の要求 (`:api-surface-check` は公開対象外) の範囲内 (2026-09-09)
- Scenario「リリース版の配信リポジトリ参照」(specs/kmp-maven-distribution): spec では `-Pversion=0.1.0-beta.1` (URL 上書きなし) で `:ksdialogs-kmp` を `publishToMavenLocal` → 実際は root publication 単独発行 (`publishKotlinMultiplatformPublicationToMavenLocal`) で SwiftPM 連携メタデータを確認した。理由: KGP はビルド全体で 1 つの umbrella SwiftPM パッケージを解決し、cinterop klib を伴う iOS publication の発行には配信リポジトリ `KsDialogs-SPM` に同版 (`0.1.0-beta.1`) の tag が実在する必要がある (未 push のため `no versions of 'ksdialogs-spm' match the requirement` で失敗)。全 publication の検証 (6.1〜6.3) は tag 付きローカル clone の `file://` URL で行い、既定 URL のケースは root publication のみの発行のため、全 publication の POM / `.module` / klib / aar が URL に依存しないことは**実証していない** (実証したのは root の POM の一致・root の `.module` の差が SwiftPM 連携メタデータのファイル項目の size / チェックサムに限られることと、SwiftPM 連携メタデータの URL・`packageName` が URL に応じて変わること。evidence/swiftpm-reference-derivation.txt)。公開座標 (https) での全 publication の発行と解決は phase-8 (smoke) / phase-9 の責務。phase-9 の release workflow は「SPM tag を push してから Maven へ発行する」順序が必須という含意を持つ (2026-09-09、検証ワーカーの発見)
- tasks 1.1 / design Decision 2「SNAPSHOT 中の Central 向けタスクを `doFirst` で失敗させるガード」: spec Requirement の「ネットワークアクセスや認証より前に」を満たすため、`doFirst` (タスク実行時。Gradle の credentials 検証が先に走り、認証情報なしではガードに到達しない) → 設定段階の `gradle.startParameter.taskNames` 照合 + `gradle.taskGraph.whenReady` の `allTasks` 照合の 2 段に変更 (対象判定はタスク名のみ、プラグインの型は不参照のまま)。認証情報プロパティなし・`--offline` で 10 経路が SNAPSHOT 診断のみで設定段階に失敗する。**残り**: 集約タスク `publish` 経由だけは、Gradle の credentials 検査が同じ task graph 確定時のリスナで走るため SNAPSHOT 診断と認証情報未解決が同時に報告される (ガード側だけを先に効かせる手段は無いことを実測)。Scenario「SNAPSHOT の Central 発行拒否」の「認証不足を理由としない」はこの 1 経路で字義どおりには満たない (診断は必ず出て実行前に止まる)。理由: review-001 と並走した second-opinion-code-001 の Major を採用 (2026-09-09)
- [付随修正] `android/build.gradle.kts` の同じ SNAPSHOT ガード (`doFirst` 方式) も同じ 2 段の形へ揃えた (design Decision 2「android/ と同じ式」を保つため。診断文言は android 側の既存文言のまま)。実測: 認証情報なし `--offline publishToMavenCentral` → SNAPSHOT 診断のみ、`publishToMavenLocal` 成功、android 単体テスト 68 件 / 0 failures。archive 済み change (add-native-distribution) の evidence は書き換えていない (2026-09-09)
- [付随修正] `samples/android/settings.gradle.kts` の置換コメント (「AGP のライブラリモジュールは Maven publication を生成せず自動置換が発火しないため」) を、android/ が発行設定を持つ現状で成立する理由 (公開済み成果物への無音フォールバックを避けるため明示置換する) に書き直した。`samples/kmp/settings.gradle.kts` の同文 (review-001 Minor 2) と同じ 1 行 (2026-09-09)
- specs/kmp-api-surface Requirement「Swift 境界の失敗経路の宣言検査」: spec では 4 経路の throws 節に `DialogException` があること → 実装では期待例外型の集合の完全一致 (suspend 3 経路は `DialogException` + `CancellationException`、`KsToast.show` は `DialogException` のみ) に拡張。理由: review-001 Minor 1 — `CancellationException` の宣言だけが落ちても Kotlin 側は緑のまま、Swift からの取り消しで Kotlin/Native が abort する退行型を proposal の Why が塞ぐ対象としているため。spec の要求は包含する (2026-09-09)
