# Proposal: deliver-swiftui-content-safe-area-ios

## Why

iOS の器 (Dialog・Loading・Toast) に SwiftUI で書いた中身を載せると、その中身から見える安全領域は常に 0 になる。ホストが安全領域を一切渡していないためである。基準領域を窓全体にして画面の端に付けた中身は、ステータスバーやホームインジケータの位置を知る手段が無い。SwiftUI 標準の「安全領域を避ける・無視する」の書き方も効かない。UIView で書いた中身には器と安全領域の重なりが届いていて (実測、`evidence/safe-area-sizing-probe.md`)、core/ADR-0011 の「技術によらず同じ挙動」とも食い違う。ColorAnalyzer の KMP 移植では、この差のためにアプリ側で窓の安全領域を直接読む回避策が要った。

方向は ios/ADR-0002 (proposed、オーナー採用済み)。ただし、ホストに安全領域をそのまま渡すと器の大きさが変わる (上端・下端の器が重なりの分だけ大きくなり、中央の重なる中身は窓まで膨らむ)。そのため、器の大きさを今のまま保つ形にした (フェーズの agenda の決定事項「器の大きさの決め方」)。

## What Changes

- 基準領域が窓全体のとき、iOS の器に載せた SwiftUI の中身は、位置が端に固定される軸 (配置 start / end と、比率サイズを伴わない fill) について、器と安全領域の重なりを SwiftUI 標準の安全領域として受け取る。届けるのはシステムの領域 (ステータスバー・ホームインジケータ等) だけで、キーボードの領域は含めない
- 位置が中央に固定される軸 (配置 center と、比率サイズを伴う fill) と、窓全体以外の基準領域 (可視領域・表示中のページ) では、今と同じく安全領域を受け取らない (0)。移動量でシステムの領域に重なっても同じ
- 器へ伝える中身の要求サイズは、受け取った安全領域に左右されない (今と同じ大きさ)。器の大きさと位置はどの配置でも今と同じで、端に付けた中身が器の内側で安全領域を避けるだけになる
- 既定の基準領域 (可視領域) では見た目は変わらない
- UIView で書いた中身の扱いは変えない
- 影響する能力: ios-native (Dialog・Loading・Toast の SwiftUI の中身のホスト。KMP の Swift 面から登録した SwiftUI の中身も同じホストを通る)
- 蒸留時に反映: concepts — `kasane/concepts/ios/api/layout-surface.md` に、器の中の SwiftUI の中身から見える安全領域の意味を書く (窓全体基準の端の軸だけが重なりを受け取る・中央の軸と窓全体以外の基準領域は 0・要求サイズに重なりは入らない・キーボードは含めない・既定の可視領域では 0・安全領域に収まらない固定サイズの中身の注意)
- 蒸留時に反映: decisions — ios/ADR-0002 の範囲と Consequences を、この change の形 (端の軸だけに渡し、要求サイズに重なりを入れない) に書き直し、出典をこの change に直して accepted にする

## Non-Goals

- Android の器の中の中身から見える insets を揃えること: 別の能力 (android) で、ロードマップの非ゴール。差は簡易起票 `align-android-content-insets-meaning` に積んだ
- 共通ケース表 (`core/layout-spec/cases.json`) へのケースの追加: 表の読み手が android/・maui/ にもあり、委任状の禁止事項に当たる。iOS 固有のテストで固定する
- Sample へのデモの追加: ロードマップの非ゴール (4 ルートに広がるため)
- 安全領域を独自の値で中身へ渡す公開 API (ios/ADR-0002 の却下案 B): 公開 API が増え、委任状の任せない判断に当たる
- `ui/` (brief・モック) の作成: 委任状の見た目の基準が「承認済みモックは使わない。ios/ADR-0002 の挙動そのものが基準」と定めている。見た目の変化は下のデルタスペックの挙動として書き、自動テストと Simulator での実測で確かめる

## Impact

- 破壊的変更: 公開 API の変更は無い。挙動の変化は、窓全体を基準領域にして端に付けた SwiftUI の中身が、器の内側で安全領域を避けるようになること (委任状で承認済みの見た目の変化)。安全領域を無視する指定の中身、中央の中身、既定の可視領域の中身は今と同じ
- 端に付けた中身が使える大きさは重なりの分だけ減る (器は大きくならない)。UIView の中身と同じ振る舞い
- 安全領域に収まらない固定サイズの中身は、器の矩形は変わらないが、器の内側での並び方は SwiftUI 標準のホストの規則に従う (実測では、下端で安全領域を無視する固定サイズの中身が 17 上へ動いた)
- 中央の軸と窓全体以外の基準領域では、UIView の中身 (重なりを受け取る) と SwiftUI の中身 (0) の差が今のまま残る。中央の重なる中身を膨らませないための選択で、端の軸の差だけを解消する
- リスク: ホストが求めるサイズから受け取った安全領域を引く計算は、実測ではちょうど足し算になっていた (固定サイズ・理想サイズの中身)。中身の大きさが動的に変わったとき (文言の変化など) に、器が新しい大きさに追従することをテストで確かめる
