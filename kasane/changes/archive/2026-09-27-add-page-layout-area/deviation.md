# Deviation: add-page-layout-area

- 現在ページは登録された provider から得る (dialog-contract) / Compose の modifier (android-native): spec では「窓座標の矩形を返す provider」は内部の共通型として公開しない → 指示により、Android では台帳への出入り口 (`DialogCurrentPageLedger`) と矩形を返す印の型 (`DialogCurrentPageMarker`) を `@KsDialogsInternalApi` (`@RequiresOptIn(level = ERROR)`) つきの public とする。利用者向けの登録口は View を返す関数と modifier の 2 つのままで、オプトインしない限りコンパイルエラーになる。理由: Compose の modifier が別モジュール `:ksdialogs` (android/ADR-0001) にあり Kotlin の internal では届かないため。「公開しない」は利用者向けの登録口として出さない意味で満たすと判断 (2026-09-26)
- 現在ページは登録された provider から得る (dialog-contract) / CURRENT_PAGE と provider の登録 (android-native) / モーダルが優先される (maui-binding): spec では候補を「提示先と同じ window (Android は同じ Activity のウィンドウ)」に限る → 指示により、Android の「同じ Activity のウィンドウ」は提示先 Activity が持つウィンドウ (メインウィンドウに加え、同じ Activity に属するモーダル・ダイアログのウィンドウ) と解釈し、候補に含める。KsDialogs 自身の器のウィンドウは除外し、別 Activity のウィンドウは引き続き除外する。同じ Activity かは各ウィンドウの根の View が持つ `WindowManager.LayoutParams.token` の同一性で判定し、器のウィンドウは器が decor view に付ける印 (`ksdialogs_container_window`) で見分ける。MAUI 層 (`PlatformCurrentPage` / `DialogCurrentPageLocator`) も候補を Native へ渡す前に同じ条件 (token・器の印・空の矩形・提示先ウィンドウと重ならない) で判定し、外れたら次の取得元 (上書き provider → MAUI の既定ページ) へ進む (review-001 / second-opinion-code-001 の修正で追加)。理由: MAUI の Android 版はモーダルページを Activity とは別のダイアログウィンドウに載せるため、メインウィンドウ限定では Scenario「モーダルが優先される」が Android で満たせない (ナビゲーションバー付きのモーダルでバーに重なる)。座標は画面座標で突き合わせるためウィンドウが別でも位置は正しく出せる (2026-09-26)
- modifier の台帳規則 (dialog-contract) / SwiftUI の modifier (ios-native): spec の台帳規則は「attach 中のもの・窓外は除外・入れ子は内側・それ以外は最後に配置されたもの」→ 判断により、iOS では「画面に表示されていない印も候補から外す」を加える。判定は問い合わせの時点で、印自身かウィンドウまでの祖先のどれかが `isHidden`、または `alpha` (演出の行き先の値。見た目の presentation 値は見ない) が 0.01 未満 (UIKit の hitTest と同じ閾値) なら除外する。理由: SwiftUI の `TabView` はタブ切替の演出中 (実測約 0.7 秒) 去るタブと来るタブの View を両方ウィンドウに載せており (去る側は alpha 0 へ演出中)、この間の問い合わせでは attach 中の判定だけでは去るタブの印が残り、入れ子の規則で Panel タブの矩形が選ばれ、samples の Scenario「Info タブでは画面の上端に出る」が iOS 系 2 ルートで満たせなかった。演出が終われば去るタブの View はウィンドウから外れる。Compose は `when` による切替なら非選択タブが composition から外れるため同じ状態は起きないが、`Crossfade` / `AnimatedContent` / Navigation Compose のフェード遷移では演出中に同種の状態が起き得る (本項は iOS のみ) (2026-09-26)
- [付随修正] Sample (Android Native / KMP Android) の移動量欄: API 35 で初期値「0」が表示されなかった (AndroidView に載せた EditText の既定の横スクロールが寸法確定前の文字配置を残していた) → 両ルートの `SampleOffsetField.kt` で `setHorizontallyScrolling(false)` と `maxLines = 1` を指定。tasks 5.3 の撮り直しで発見 (2026-09-26)
- [付随修正] Sample (Android Native / KMP Android) のステータスバー: API 35 でアイコンが白地に白で見えなかった (メニュー画面にも以前からあった) → 両ルートの `MainActivity.kt` で API 35 以上のときだけ `isAppearanceLightStatusBars = true`。証跡の状態間で画素が一致してしまう問題も解消。tasks 5.3 の撮り直しで発見 (2026-09-26)
- レイアウトデモ項目 (属性調整パネル) (samples): spec の Scenario は「dialogMargin 分内側に出る」で既定値 (全辺 24) を前提にしていた → 指示により、4 ルートの Layout Dialog パネルが出すダイアログは dialogMargin を全辺 0 にする。カードが基準領域の端 (タブバーの上端・ナビゲーションバーの下端・ステータスバーの下端) に接し、基準領域どおりに置かれたかを見た目で判定できるようにするため。Scenario の「dialogMargin 分内側」は 0 で満たす。Scenario「既存のパネル操作は変わらない」の「従来と同じ位置に出る」は、余白が 0 になったぶん (Start / End 寄せでカードが基準の端に接する) を除いて従来と同じ、と読み替える (review-004 Minor 1) (2026-09-26)
- CURRENT_PAGE と provider の登録 (android-native): spec では「器はその root の画面上の位置で測り」→ 実際は器の面 (レイアウトの面) 自身の画面上の位置で測る。理由: 本番では面が root の左上にあり両者は一致するが、ケース表のテストホストでは面が root の左上にないため、面自身を原点にしないと同じ基準で測れない (蒸留時の補完、2026-09-27)
- Compose の modifier (android-native) の Scenario「Scaffold の content 枠に付けると下部バーを避ける」: spec では `Scaffold` のテストホスト → 実際は material3 に依存しない同等の画面 (中身の枠 weight 1 + 下部バーの縦並び、modifier の付け先は同じ) で検証。理由: `:ksdialogs` の androidTest に material3 の依存が無く、ライブラリのテスト依存を増やさないため。Sample (Android Native / KMP Android) は material3 の Scaffold で同じ付け方をして撮影証跡で確認済み (蒸留時の補完、2026-09-27)
