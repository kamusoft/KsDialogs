# Exploration: fix-android-container-system-bar-appearance

旧 change-id: `fix-android-api35-overlay-status-bar-icons` (2026-09-26 に簡易起票)。2026-09-27 の探索で起票時の前提が崩れたため、中身を組み直して改名した (「決定事項」)。

## 課題 / 動機

### 発見の経緯

add-page-layout-area の tasks 6.1 (全ルートの全件実行) で、instrumented テスト `DialogTransparentOverlayTests.覆いが透明ならステータスバーの明るさは表示前後で変わらない` が API 35 の専用 AVD で間欠的に失敗した (`表示前 246.7… / 表示中 255.0`)。起票時は「API 35 で透明な覆いのダイアログを出すと、ステータスバーのアイコンが白くなって白地に溶ける」と見ていた。記録は `kasane/changes/archive/2026-09-27-add-page-layout-area/evidence/distill-handoff.md` の失敗 A。

### 実測で分かったこと (2026-09-27、専用 AVD Small_Phone / API 35)

証跡: `evidence/` の画像 8 枚と `evidence/api35-dumpsys-excerpt.txt` (各ウィンドウの外観の値の抜粋)。

**1. テストの失敗はテストの測り方によるもので、ダイアログの器は関係ない**

- テスト APK は targetSdk 36 のため、API 35 では edge-to-edge が強制される。提示先 `DialogLayoutTestActivity` の白いステータスバー色の指定は効かない。明暗の指定も無いので、ダイアログが無くても帯は白地に白アイコン (輝度 255) になる (`evidence/test-overlay-before-settled.png`)
- 失敗する回は、「表示前」を測っている間に起動スプラッシュ (`APPLICATION_STARTING`、`LIGHT_STATUS_BARS` あり) の外観がステータスバーに残っていた (輝度 244〜247、`evidence/test-overlay-before.png`)。その後、提示先自身の外観に切り替わって 255 になる
- 器のウィンドウは提示先の値 (明暗の指定なし) を正しく写していた。表示中にステータスバーが隠れたことも一度もない。起票時の仮説 (H1 読み取りの空振り・H2 あとからの上書き・H3 バーが消えている) はすべて否定された
- テストが通る回も、白地に白アイコン同士 (255 と 255) を比べているだけで、明暗の引き継ぎは実質的に検証されていない
- add-page-layout-area の付随修正 (Sample が API 35 以上で暗いアイコンを指定した件) は提示先自身の設定の話であり、器の不具合とは別の系統

**2. Loading と Toast の器は提示先のアイコンの明暗を変える (利用者に見える不具合)**

- Sample Android (API 35 以上で画面を暗いアイコンにしてある) での見え (`evidence/sample-*.png`):

  | 表示中のもの | アイコン | 器ウィンドウの外観 |
  |---|---|---|
  | 通常メニュー | 濃い | (提示先) `LIGHT_STATUS_BARS` あり |
  | Dialog | 濃いまま (帯は覆いで灰色) | `LIGHT_STATUS_BARS` あり (引き継ぎが効いている) |
  | Loading | 白に変わる | 指定なし |
  | Toast | 白に変わって見えない | 指定なし |

- Loading / Toast の器は `DialogWindowSystemBars.makeSystemBarBackgroundsTransparent` だけを呼び、`inheritSystemBarState` を呼ばない (`android/ksdialogs-core/src/main/kotlin/jp/kamusoft/ksdialogs/LoadingContainer.kt`・`ToastContainer.kt`)
- Toast の器は触れない・フォーカスを取らないウィンドウだが、画面全体の大きさなので、ステータスバーの外観を決めるウィンドウとして選ばれる
- core の Loading / Toast の規則 (`kasane/concepts/core/api/loading-semantics.md`・`toast-semantics.md`) には、システムバーについての約束が無い。Dialog には「覆いに透明を指定しても、システムバーの見えは変わらない」がある (`kasane/concepts/core/api/layout-semantics.md`)

### Web / AOSP ソース調査の要点 (2026-09-27)

- ステータスバーの明暗は、前面にあって画面上端にかかる全画面のアプリウィンドウの外観で決まる (`DisplayPolicy`)。Dialog / Loading / Toast の器はどれもこれに当たる
- `WindowInsetsController.getSystemBarsAppearance()` は、API 30〜34 ではアプリが `setSystemBarsAppearance` で明示した値しか返さない (明示が無ければ 0)。API 35 以降は、明示した値とテーマ由来の値を合わせて返す。旧来の `SYSTEM_UI_FLAG_LIGHT_STATUS_BAR` から来る明暗は、どの版でも返らない
- AndroidX の `WindowInsetsControllerCompat` は、API 30〜34 では旧来のフラグ経由で明暗を設定する。このため、API 30〜34 で提示先が AndroidX 経由で暗いアイコンにしていると、Dialog の器の引き継ぎも 0 を読む恐れがある (ソースからの推論。2 回目の実測で、現行の androidx.core では外れと判明)

### 2 回目の実測 (2026-09-27、論点 3 の確認)

Android の確認は、リポジトリの外に作ったコピーの Sample だけを書き換えて行った (リポジトリ本体は無変更)。証跡: `evidence/sample-hidden-bars-*.png`・`evidence/round2-android-dumpsys-excerpt.txt`・`evidence/ios-statusbar-compare.png`。

**(a) バーを隠した画面から出したとき (Android、専用 AVD Small_Phone / API 35)**

| 表示中のもの | バー | ステータスバーの明暗 | 仕組み |
|---|---|---|---|
| Dialog | 隠れたまま | 提示先どおり (暗いアイコン) | 引き継ぎが効いている (PB-SB-01 どおり) |
| Loading | **ステータスバーとナビゲーションバーの両方が出てくる** | **白に変わる** | フォーカスとバーの制御が Loading の器に移り、器は何も引き継いでいない |
| Toast | 隠れたまま | 器の値 (指定なし) に変わる | フォーカスを取らないので、バーの制御は提示先に残る。明暗だけは器の値が使われる (バーが隠れているので目には見えない) |

**(b) API 31 で、提示先の明暗の指定のしかたを変えたとき (Android、新規の専用 AVD `ksn_api31`)**

| 提示先の指定のしかた | Dialog | Loading | Toast |
|---|---|---|---|
| AndroidX (`WindowCompat` 経由、androidx.core 1.13.1) | 引き継げる | 白 (指定なし) | 器は指定なしだが、画面の明暗は提示先のまま |
| OS の API で直接 (`setSystemBarsAppearance`) | 引き継げる | 白 | 同上 |
| 旧来のフラグだけ (`systemUiVisibility` の `SYSTEM_UI_FLAG_LIGHT_STATUS_BAR`) | **白 (0 を読む)** | 白 | 同上 |

- androidx.core 1.13.1 の API 30〜34 向けの実装は、旧来のフラグと `setSystemBarsAppearance` を両方呼んでいた。そのため AndroidX 経由なら Dialog も引き継げる。推論が当たるのは、提示先が旧来のフラグだけで明暗を指定した場合
- Toast の器の明暗は、API 31 では画面に効かず、API 35 では効く (OS の選び方の版による差と推測。未確認)
- 副次所見: API 31 では、Dialog の器の再表示の作法が 0 (API 31 の定数では「触れたらバーを出す」) になった。提示先は作法を明示しておらず、既定値 (スワイプで出す) で動いていた。明暗と同じく「明示していない値は 0 で返る」ことによる欠落と推測している (原因は未特定)
- Sample の targetSdk は 36

**(c) iOS (Simulator iPhone 17 / iOS 26.5)**

| 表示中のもの | ライト外観 | ダーク外観 |
|---|---|---|
| 通常メニュー | 黒 | 黒 (Sample のメニューはダーク外観でも白地のまま) |
| Dialog (暗幕あり) | 黒 | **白** |
| Loading (暗幕あり) | 黒 | **白** |
| Toast (暗幕なし) | 黒 | 黒 |

- ステータスバーが消えることは、どの状態でも無い
- iOS の器は、ステータスバーの見えを何も指定していない。Dialog は提示元の最前面の VC に `.overFullScreen` で present し、Loading / Toast は key window に View を重ねるだけ (`ios/Sources/KsDialogs/Presentation/` の各 PresentationSurface と ContainerViewController)
- ダーク外観の Dialog / Loading で白くなるのは、ステータスバーの下に暗幕 (灰色) が来て、OS が下の色に合わせて文字色を選んだためと見ている。暗幕を敷かない Toast では変わらない。同じ灰色でもライトとダークで選ばれる色が違う理由は未確認
- Android の Loading / Toast (器の指定そのものが提示先と食い違う) とは性質が違う。iOS は「器が見えの指定を変えている」のではなく、「暗幕に合わせて OS が見えを調整している」

## 検討した選択肢 (却下案と理由を含む)

change の組み立て (2026-09-27):

| 案 | 中身 | 判断 |
|---|---|---|
| A. 1 本に組み直す | テストの測り方の修正と、Loading / Toast の器の修正を同じ change で扱う | **採用** |
| B. 2 本に分ける | この change はテストだけにし、Loading / Toast は別に簡易起票する | 却下。テストの修正 (提示先に暗いアイコンを明示させる) は Loading / Toast の検証の土台でもあり、話題も「器がシステムバーの見えを変えない」で同じ。テストの失敗は手元の API 35 だけで CI を止めていないため、分けて急ぐ理由がない |
| C. テストだけ直す | Loading / Toast は見送る | 却下。利用者に見える不具合が残る |

## 決定事項

- (2026-09-27) change を組み直し、次の 2 つを扱う。change-id を `fix-android-api35-overlay-status-bar-icons` から `fix-android-container-system-bar-appearance` に改名した
  - テストの測り方を直す
  - Loading / Toast の器も、提示先のシステムバーの見えを変えないようにする
- (2026-09-27、論点 1) Loading / Toast の器も、Dialog と同じ引き継ぎ (アイコンの明暗・表示/非表示・隠れたバーの再表示の作法) を、表示した時点で 1 回行う。3 つの器が同じ処理を呼ぶ
  - 却下: Loading は 3 つ・Toast は明暗だけ (見える結果は同じで、器ごとの説明が 1 段増えるだけ)。Toast をステータスバーの明暗を決めるウィンドウにならない作りに変える (ウィンドウの種類・大きさが変わり、Toast の配置の計算と Loading との前後関係に響く)
  - Toast で表示/非表示を写しても、フォーカスを取らない Toast ではバーの制御が提示先に残るので効かない。害もない
- (2026-09-27、論点 2) 「Dialog / Loading / Toast の器は、提示先の画面のシステムバーの指定 (アイコンの明暗・表示/非表示・隠れたバーの再表示の作法) を変えない」を core の共通の約束として足す。暗幕がステータスバーの下を暗くしたときに OS が文字色を合わせるのは約束の外。Dialog の既存の 1 文 (覆いが透明ならシステムバーの見えは変わらない) もこの約束にまとめる。iOS はコードを変えずに満たしている
  - 却下: Android の公開面にだけ書く (MAUI / KMP の利用者に OS 差かどうかが分からない。退行の検出が Android だけになる)。約束を足さず不具合の修正としてだけ扱う (利用者に見えず、テストが何を守るかの根拠が文書に無い)
  - iOS 側にもテストを足すか (「器がステータスバーの見えを指定しない」ことの検査) は提案のときに決める
- (2026-09-27、論点 4) テストは 2 つの検査に分ける
  - 画面の指定が保たれること (明暗・表示/非表示・再表示の作法): 器のウィンドウの指定の値を提示先の値と直接比べる。Dialog / Loading / Toast で同じ形にする。提示先には暗いアイコンを明示させ、「提示先が暗いアイコンになっていること」を前提として確かめてから比べる (白と白の比較で空振りしないため)
  - 透明な覆いで暗くならないこと: 帯の明るさの比較を残す。提示先に暗いアイコンを明示させ、起動スプラッシュが消えてから「表示前」を測るように直す。今の落ち着き判定 (2 回続けた差が 0.5 未満) は、数百 ms 変わらずに残るスプラッシュの外観を落ち着いたと読んでしまう
  - 却下: 明るさの比較だけで直す (画素の平均と待ち方の作りに左右される。Loading は既定の暗幕で明るさが変わるので、アイコンの変化を取り出せない)。値の比較だけにして明るさの比較を捨てる (実際の見えを確かめる検査が無くなり、覆いを敷かせない設定のフラグ検査だけが残る)
  - 値の読み取り方・スプラッシュの待ち方・Scenario ID の振り方は提案のときに決める
- (2026-09-27、論点 5) API 36 (CI) と API 33 実機で再現しなかった理由は調べずに閉じる。新しいテストは提示先の前提を確かめてから比べるので、端末ごとの再現条件に依存しない。理由が分かっても直し方は変わらない
- (2026-09-27、論点 7) 引き継ぎの読み取り元を 2 点補強する (Dialog / Loading / Toast 共通の引き継ぎ処理 `DialogWindowSystemBars` の中で)
  - 明暗: OS の返す値に加えて、提示先の旧来のフラグ (`systemUiVisibility` の明るいステータスバー / ナビゲーションバーのフラグ) も合わせて読む。MAUI Android も同じ器を通る (`maui/android/native/ksdialogs-maui-bridge` は `ksdialogs-core` に依存)
  - 隠れたバーの再表示の作法: 提示先が明示していない (OS が 0 を返す) ときは、OS の既定として扱う。値 0 は「指定なし」と「触れたら出す (非推奨の定数)」の区別がつかないので、後者を明示した提示先は取りこぼす (受け入れる)
  - 却下: 作法だけ直す (旧来のフラグで明暗を指定した画面で約束を満たせない)。どちらも直さず制約として書く (API 31 で作法が提示先とずれたまま残る)。別の change に切り出す (同じ処理を 2 つの change で触ることになる)
  - 旧来のフラグ由来の明暗が API 35 以降も OS から返らないことは、ソースを読んだだけで実測していない。実装時に確かめる
- (2026-09-27、論点 6) KsSettingsView への未配達の知らせは、最後の段落をその場で書き直した (新しい change-id のパスと、「調べた結果 Sample の件とは別の系統で、overlap に当たらないため追いの知らせは無い」という結論)。相手の受信台帳に記録が無い (未処理の) うちに直せば、崩れた前提を読ませずに済み、相手の処理も 1 件のままになる
  - 却下: 結果を別の知らせで追って送る (必要のない知らせが 1 件増える)。段落を消すだけ (「調べている」と書いた件の結末がどこにも残らない)。何もしない (パスが壊れたまま)

## ADR 候補 (作成済み: core/ADR-0039 (proposed) — 器は提示先の画面のシステムバーの指定を変えない / 未起票: なし)

## 未決の論点

1. **Loading / Toast で何を引き継ぐか** — 決定済み (決定事項の論点 1)。Dialog と同じく、明暗・表示/非表示・隠れたバーの再表示の作法の 3 つを引き継ぐか。Toast は、引き継ぐ代わりに「ステータスバーの外観を決めるウィンドウにならない」形もあり得る
2. **契約の置き場** — 決定済み (決定事項の論点 2・core/ADR-0039)。「器はシステムバーの見えを変えない」を、Loading / Toast も含めた core の契約として足すか。足すなら iOS の挙動の確認が要る (論点 3 の 3 つ目)
3. **実測していない疑い** — 2 回目の実測で確認済み (「2 回目の実測」の節)
   - Loading / Toast でバーが出てくるか → Loading は出てくる。Toast は出てこない
   - API 30〜34 で、AndroidX 経由で暗いアイコンにしている提示先の上で Dialog のアイコンが白くなるか → 現行の androidx.core ではならない。旧来のフラグだけで指定した提示先ではなる
   - iOS の Loading / Toast はステータスバーの見えを変えるか → 器は見えを何も指定していない。ダーク外観では、暗幕に合わせて OS が文字色を変える
4. **テストの直し方** — 決定済み (決定事項の論点 4)。提示先に暗いアイコンを明示させる (明るい地で差が出る状態を作る)。起動スプラッシュが消えてから「表示前」を測る。明暗を、帯の明るさではなく器ウィンドウの外観の値で直接検査するか
5. **API 36 (CI) と API 33 実機で再現しなかった理由** — 閉じた (決定事項の論点 5)。推測だけ残す: API 33 は edge-to-edge が強制されないので表示前も表示中も 255、API 36 はスプラッシュのタイミングの違い
6. **KsSettingsView への未配達の知らせ** — 決定済み (決定事項の論点 6)。`kasane/outbox/KsSettingsView/2026-09-27-sample-api35-status-bar-and-edittext.md` の最後の段落に、旧 change-id のパスと崩れた前提 (「同じ系統の原因なら結果を知らせる」) が書かれている。相手の受信台帳にまだ記録が無い (未配達) ので、直すか、結果を別の知らせで送るかを決める
7. **引き継ぎの読み取り元を補強するか** — 決定済み (決定事項の論点 7)。提示先が旧来のフラグだけで明暗を指定していると、Dialog も 0 を読む (2 回目の実測 (b))。API 31 では再表示の作法も 0 で写る (副次所見)。API 30〜34 で旧来のフラグも読むか、作法の 0 を既定値として扱うか

## 変更級の推奨: M (2026-09-27 にオーナーが確定)

- core の約束を Dialog / Loading / Toast の 3 機能にまたがって足すので、それを Scenario として固めるデルタスペックが要る (S の直接実装では残せない)
- コードは Android の本体モジュール (`ksdialogs-core`) の中の小さな変更 (引き継ぎの処理と Loading / Toast の器で 3 ファイルほど)。公開 API は変わらず、元に戻しやすい。iOS はコードを変えない
- 設計判断は core/ADR-0039 と決定事項にそろっているので、design.md とスペックレビュー一式 (L) までは要らない
- 見た目のデザインを作る変更ではないので `ui/` は作らない
