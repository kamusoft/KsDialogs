# Deviation: fix-android-container-system-bar-appearance

- tasks.md 1.4・6.1 (実行端末): tasks では Android の instrumented を既存の専用 AVD `Small_Phone` (API 35) と `ksn_api31` (API 31) で回す → 指示により、この change 専用に作成した AVD `ksn_sbfix_api35` (API 35、`system-images;android-35;google_apis_playstore;arm64-v8a`、small_phone) と `ksn_sbfix_api31` (API 31、`system-images;android-31;google_apis;arm64-v8a`、small_phone) で回し、iOS も専用シミュレータ `ksn-sbfix-ios` (iPhone 16 / iOS 26.5) を使う。いずれも作業後に削除する。理由: エミュレータ・シミュレータは専用のものを使い作業後に削除するオーナー指示 (2026-09-27)
- proposal「テストの実行」(PB-SB-10 の API の絞り方): proposal ではずれが起きる範囲 (API 32〜34 の想定) に `assumeTrue` で絞る → 実装では `assumeTrue(SDK_INT >= 31)`。器の作法は `dumpsys window windows` の `bhv=` で観測する (API 31〜33 はアプリから読める値で「指定なし」と「0 を明示」を区別できないため)。理由: 実測でずれは API 31〜33 で起き (34 は sources 不在で未確認)、API 35 以降でもテストは正しく通って退行の検出に使えるため、範囲に絞るより spec (API 30+、API 30 は 0 が既定でずれない) に沿う (2026-09-27、tasks 1.4 の実装判断)
- Requirement「システムバー表示状態の引き継ぎ」(明暗・旧来のフラグ、PB-SB-09) と ADR-0039「器は提示先の指定を変えない」: spec では提示先の指定のしかたによらず明暗を引き継ぐ → 指示により、明暗の読み取りを API で分ける。API 35 以上では、提示先のテーマ (`windowLightStatusBar` / `windowLightNavigationBar`) が明るい地向けにしていないビットは「OS の返す値」と「旧来のフラグ」のどちらかが立っていれば明るい地向け、テーマが明るい地向けにしているビットは両方が立っているときだけ明るい地向けと読む (テーマが明るい地向けで、WindowInsetsController で暗い地向けを明示した提示先・旧来のフラグの代入で明るいビットを外した提示先のどちらでも、器は暗い地向けになる)。API 30〜34 は OS の返す値と旧来のフラグの OR を採る。受け入れる取りこぼしの仕組み: プラットフォームの WindowInsetsController での明示と旧来の明るいフラグが食い違う提示先では、OS が旧来のフラグを見えに使わなくなる単位 (API 31 / 33 はウィンドウ単位、API 35 はビット単位) と器の読み取り規則がずれ、器の明暗が提示先の見えと食い違い得る (review-003 の Suggestion。例として、API 35 以上でテーマ外のビットに旧来の明るいフラグを立てつつ、そのビットを WindowInsetsController で暗い地向けと明示した提示先も該当する)。代表例: API 30〜34 で、テーマが明るい地向けでプラットフォームの WindowInsetsController から暗い地向けを明示した提示先 (器は明るい地向けになる)、API 35 以上で、プラットフォームの WindowInsetsController から明るい地向けを明示しつつ旧来のフラグも外した提示先 (器は暗い地向けになる)。どちらも androidx の WindowInsetsControllerCompat 経由の指定 (旧来のフラグも一緒に切り替わる) では起きない。コード由来とテーマ由来をビットごとに見分ける公開 API が無いため、見分けの根拠はテーマの属性に置き、取りこぼしは `hostAppearance` の KDoc に残す。理由: review-001 の Major (旧来のフラグの OR 読みの退行) と review-002 の Minor (API 35 以上で旧来のフラグの代入を取りこぼす) に対し、非公開属性の reflection を避けつつ、見分けられる範囲で正しく引き継ぐため (選択肢 B と review-002 の対応 a、2026-09-27)
- バーを隠す提示先を使う Android テスト (tasks 3.4・3.5・3.8。LD_SB_02・TS_SB_02・PB_SB_01〜03・06): spec・tasks はバーを隠した提示先で器を出して見るだけで、端末の状態には触れない → 指示により、テストの間だけ端末の設定 `immersive_mode_confirmations` を `confirmed` に切り替え、終了時 (失敗時を含む) に元の値へ戻す (共通の `support/ImmersiveModeConfirmation.whileSuppressed`)。元が未設定なら削除、値あり (空文字を含む) なら content provider への挿入で書き戻す (uiAutomation のシェルでは `settings put` に空文字を渡せないため)。理由: API 36 では器がフォーカスを取った瞬間に OS の「全画面表示の確認」ウィンドウが出てフォーカスとバーの制御を取り、提示先のバーが一瞬再出現して LD_SB_02 が落ちる (Dialog でも同じ割り込みを実測)。利用者が一度確認すれば出なくなる OS 側の現象で ADR-0039 の約束の外なので、判定を弱めずに OS の割り込みだけを外す。適用範囲は、同じ割り込みを受け得るバーを隠すテスト全部にそろえた (選択肢 a、2026-09-27)
