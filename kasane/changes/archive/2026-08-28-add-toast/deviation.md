# Deviation: add-toast

- Toast の公開面と fire-and-forget (design Decision 1 のシグネチャ例): design の例示は iOS のカスタム factory 閉包を非 throwing (`(ViewModel) -> UIView`) で描いている → 実装では `throws` 化 (`(ViewModel) throws -> UIView`)。理由: spec の受理後失敗モデルが「factory の例外」を失敗源として明示しており、非 throwing のままでは iOS でこの条項が到達不能 (MAUI bridge の例外境界修正 = second-opinion-code-001 Major 2 の成立にも必要)。Kotlin / C# の factory が自然に例外を投げられることとの鏡像で、ソース互換 (samples 無改変ビルドで実証)。design 自身が「各形態のイディオムで写す」と規定するスケッチ差分であり spec とは整合 (2026-08-27)

- [付随修正] 支援技術への通知 (Requirement: 支援技術への通知): Android の既定の通知口 (`SystemToastAccessibilityAnnouncer`) が支援技術オフの端末で `IllegalStateException` を投げ、Toast 表示のたびにアプリが落ちていた。`AccessibilityManager.isEnabled` のガードを追加し、「支援技術が無効でも例外を投げない」テストを1件追加 (`android/ksdialogs/src/androidTest/kotlin/jp/kamusoft/ksdialogs/ToastAccessibilityTests.kt`)。理由: 本務ファイル内の局所修正で、テスト1件で担保できる (同梱条件充足)。UI 通し (6.3) で発見 (2026-08-27)
- 4ルートパリティ / 各デモ項目 (samples): spec は Sample メニューの画面構成を規定していない (縦積み・スクロールなしが現状) → デモ項目が 9→14 に増え、縦の短い端末 (1080x2340 級) で結果表示エリアが画面外へ押し出されるため、オーナー指示によりメニューのスクロール化 (4ルート) を本変更に同梱。理由: TS-SA-05/06 の結果表示確認が小画面端末で成立しなくなるため (2026-08-27 オーナー決定「スクロール同梱」)
- スコープ追加 (オーナー決定): Toast の MAUI iOS 例外境界修正 (second-opinion-code-001 Major 2) で判明した**既存面の同型の穴** — Loading (`maui/KsDialogs.Maui/Platforms/iOS/PlatformLoadingGateway.cs`) と Dialog (`maui/KsDialogs.Maui/Platforms/iOS/PlatformDialogGateway.cs`) の C# provider が例外を捕捉せず、Swift 側 (`MauiLoadingBridge.swift` 等) が非 throwing のため、利用者 factory の例外が managed/native 境界を越えて未処理障害になりうる — を、簡易起票ではなく**本変更に同梱して修正**する。理由: Toast で作った修正の型がそのまま型紙になり、別変更に分けるより効率的 (2026-08-27 オーナー決定「このまま Loading / Dialog の対応を進める」)。Android 側 (Loading / Dialog の Kotlin 受け皿) の確認も同梱範囲
- スコープ追加の実装形 (Loading / Dialog の factory 契約): 上記オーナー決定の修正に伴い、iOS native の **Loading / Dialog の既存 factory 閉包契約も throws 化** (`(VM) -> UIView` → `(VM) throws -> UIView`。LoadingViewFactory / DialogViewFactory・両 Registry の register・KsLoading / KsDialogs のインライン show / start)。理由: Toast と同じく、bridge の失敗を Native の既存失敗経路 (Loading = 開始そのものの失敗 / Dialog = 閉鎖通知の Failed) に合流させるために必要。**呼び出し側**のソース互換は samples/ios・samples/kmp/iosApp の無改変ビルド成功で実証 (throws 共変性により非 throwing 閉包はそのまま渡せる)。ただし公開 protocol (`KsToast` / `KsLoading` / `KsDialogs`) を**外部で準拠実装しているコード**にはシグネチャ変更として breaking (review-003 が swiftc 最小再現で確認)。ライブラリは一般公開前であり既知の外部準拠は無い。正常系の観察可能挙動は不変。KMP / Interop 面は非 throwing のまま無改変 (2026-08-27、表記修正 2026-08-28)
- 失敗系の実機観測 (オーナー決定): factory 例外境界の修正 (スコープ追加分) の実機検証は、自動テストが境界の両端を固定するだけでは足りないとの review-004 指摘に対し、**Sample へ「失敗する factory」を一時追加して実機/シミュレータで失敗系まで観測する**方式を採用 (2026-08-28 オーナー決定「念の為、A で」)。一時編集は撮影後に copy 方式で復元し、復元の完全性を git diff で確認する。観測対象: MAUI iOS の Toast / Loading / Dialog の factory 失敗 (クラッシュせず既存失敗契約に流れること)、MAUI Android の Toast factory 失敗 (1枚破棄・後続継続)
- [付随修正] Compose 登録の Toast の観察テスト (`android/ksdialogs-compose/src/androidTest/kotlin/jp/kamusoft/ksdialogs/compose/ComposeToastCustomViewTests.kt`): 中身が画面に載った直後 (レイアウト前) の矩形を読んでいたため、稀に大きさ 0 の矩形で比較して失敗していた。大きさが決まるまで待つ条件を足した。理由: テスト1本の中で閉じた局所修正 (同梱条件充足)。レビュー指摘の修正サイクルでの全実行中に発現 (2026-08-27)
