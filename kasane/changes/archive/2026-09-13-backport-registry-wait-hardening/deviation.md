# Deviation: backport-registry-wait-hardening

- [付随修正] `scripts/release/check-time-budget.py`: spec は接続上限を規定していないが、接続上限が応答上限を超える退化を検査に含めた。理由: 応答上限だけを読む設計では接続上限の退化が無音で通るため (オーナー承認、2026-09-13)
- [自己テストの構造] `scripts/release/central-portal.sh` の自己テスト (tasks 4.3): 台本切れのモック応答を「戻り値 1」から「応答が得られなかったことを示す HTTP ステータス」へ変え、公開待ちを回す検査には期待の成否によらず短い上限を与え、上限と終端の取りこぼしを分けるために照会回数の表明を対で添えた。理由: 検査は `if` の条件で呼ぶため set -e が働かず、状態照会の失敗だけでは待機が止まらない。上限を与えないと誤った実装が失敗ではなく停止として表れ、上限だけでは「上限が効いた」と「終端を取りこぼして台本を使い切った」を区別できない。待機が止まらない誤りへの備えは、この外側の層と、下記 `cmd_wait_published` 側の内側の層の二層になる (実測で確認、2026-09-13)
- [オーナー指示] `scripts/release/central-portal.sh` の `cmd_wait_published`: spec は公開待ちに状態分類を求めていないが、状態を取り出せなかった ID を待機対象に残さず失敗させる分岐を足した。理由: 終端の状態を終端として扱わない誤った実装を与えたとき、自己テストが失敗ではなく停止として表れる穴が、上限を与えるだけでは塞ぎきれなかった (review-002 が `FAILED` / `NOT_FOUND` の 2 種で実測)。Scenario「待ちの誤実装が停止ではなく失敗として表れる」を構造的に満たすための変更で、本番経路は `deployment_state` が自分で停止するため到達しない (オーナー承認、2026-09-13)
