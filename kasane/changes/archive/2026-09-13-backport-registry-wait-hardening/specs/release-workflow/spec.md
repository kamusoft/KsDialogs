# release-workflow デルタスペック

## ADDED Requirements

### Requirement: 待ちの時間予算

publish の実行時間の上限は、公開待ちの上限と本体処理を収容する SHALL。検証の決着待ちはこの予算に含めず、
上限を超える場合は job の打ち切りで再実行に回す。

| 項 | 内訳 | 分 |
|---|---|---|
| 公開待ちの上限 | 2 枠まとめて 1 本 | 90 |
| 最後の照会 | 照会 1 回あたりの応答上限 5 × 1 待ち | 5 |
| 巡回間隔の端数 | 巡回間隔 0.5 × 1 待ち | 1 |
| 本体処理 | 成果物の取得・署名つき再ビルドと比較・upload・nuget.org への push | 16 |
| 余裕 | | 38 |
| **合計** | | **150** |

検証の決着待ち (枠ごとに上限 30 分、引き継ぎ経路と upload 後で最大 4 回) と待機外の照会を予算に含めないのは、
Maven Central の枠が 2 つあるため全項を収容すると合計が実行環境の job 実行時間の上限に対して余裕を持たないこと、
検証は枠ごとに短時間で決着するのが常態であること、deployment ID が upload の直後に保存されて次の試行が
引き継ぐため打ち切りが不可逆な損失を生まないことによる。

公開レジストリへの反映待ちの実行時間の上限は、待機の上限と、期限を跨げる照会 1 件の応答上限と、
job の前後の処理を収容する SHALL。

| 項 | 内訳 | 分 |
|---|---|---|
| 待機の上限 | | 45 |
| 期限を跨げる照会 | 応答上限 2 × 1 件 | 2 |
| job の前後 | checkout 等 | 5 |
| 余裕 | | 8 |
| **合計** | | **60** |

期限を跨げる照会が 1 件までであることは、照会が残り時間の正のときだけ始まり対象 1 件ごとに再判定する
巡回の構造に依存する。待機側の構造を変えたときはこの項も見直す。

両者の各項の定数 (待機の上限・照会の応答上限・巡回間隔・実行時間の上限) を変えたときに、
合計が実行時間の上限を超えていないことを機械的に検査できる SHALL。定数が検査から読み取れない形へ変わった場合、
および同じ定数の値が複数に割れている場合も検査は失敗する SHALL。

#### Scenario: 公開待ちを延ばすと予算の超過が検出される
- **GIVEN** 公開待ちの上限を publish の実行時間上限に収まらない値へ変えた状態
- **WHEN** 時間予算の検査が実行される
- **THEN** 検査は失敗し、内訳と合計が出力される

#### Scenario: 反映待ちの応答上限を延ばすと予算の超過が検出される
- **GIVEN** 反映待ちの照会の応答上限を、反映待ち job の実行時間上限に収まらない値へ変えた状態
- **WHEN** 時間予算の検査が実行される
- **THEN** 検査は失敗する

#### Scenario: 定数を読み取れない形へ変えると検査が失敗する
- **GIVEN** 待機の上限が検査の読み取れない形 (別の変数への委譲など) へ変わった状態
- **WHEN** 時間予算の検査が実行される
- **THEN** 検査は「定数を読み取れない」として失敗し、読めないまま通過しない

#### Scenario: 時間予算の検査が lint job で走る
- **GIVEN** 定数または実行時間の上限を変更した状態
- **WHEN** 検証 CI の lint job が実行される
- **THEN** 時間予算の検査が実行され、失敗すれば lint job が落ちる

### Requirement: 公開レジストリ照会の状態分類

公開後の反映待ちは、照会できたうえで未反映であることと、照会そのものが行えなかったことを区別する SHALL。

- この区別は、待機の対象それぞれについて独立に保つ SHALL。対象は Maven Central の Android 2 座標
  (`ksdialogs-core` / `ksdialogs`) と KMP 5 publication (`ksdialogs-kmp` の root / android / iOS 3 ターゲット)、
  nuget.org の 3 Package ID (`KsDialogs.Maui` / `KsDialogs.Binding.iOS` / `KsDialogs.Binding.Android`) の計 10 件である。
- 判定不能は、失敗の種別 (通信そのものの失敗 / 応答が成功を示さない / 応答を解釈できない) まで区別する SHALL。
- いずれの場合も待機を継続する SHALL。照会が行えなかったことを理由に即座に失敗しない。
- いったん反映済みと判定した対象は、以後の巡回で再照会せず反映済みのまま扱う SHALL。
  出力に示す分類は、その時点で各対象が保持している分類とする。
- 一度も照会していない対象は、未反映ではなく未照会として区別する SHALL。
- 上限に達して失敗するときは、対象ごとに保持している分類を出力に含める SHALL。
- 照会は残り時間が正のときにだけ開始する SHALL。残り時間による応答上限の切り詰めは行わない。

#### Scenario: 未反映は待機を続ける
- **GIVEN** 当該 version がまだ反映されていない対象
- **WHEN** 反映待ちが照会する
- **THEN** 未反映として扱われ、待機が続く

#### Scenario: 照会できなかった場合も待機を続ける
- **GIVEN** 対象が一時的に応答しない、または応答を解釈できない状態
- **WHEN** 反映待ちが照会する
- **THEN** 判定不能として失敗の種別つきで記録され、未反映と区別できる形で待機が続く

#### Scenario: 判定不能から回復すれば反映済みになる
- **GIVEN** 前の巡回で判定不能だった対象
- **WHEN** 次の巡回で照会が成功し、当該 version が反映されている
- **THEN** その対象は反映済みとして扱われ、以後は再照会されない

#### Scenario: 対象ごとに状態が分かれて残る
- **GIVEN** 一部の対象が反映済み、一部が未反映、一部が判定不能である状態
- **WHEN** 反映待ちが 1 巡する
- **THEN** 10 件の対象それぞれについて、その時点で保持している分類が分かる

#### Scenario: 上限超過時に対象ごとの最後の状態が分かる
- **GIVEN** 上限まで反映が確認できなかった実行
- **WHEN** 反映待ちが失敗する
- **THEN** 失敗の出力に、対象ごとに保持している分類と、判定不能であればその種別が含まれる

#### Scenario: 期限の直前に始まった照会が種別を偽らない
- **GIVEN** 待機の期限が迫っている状態
- **WHEN** 残り時間が尽きる
- **THEN** 期限を過ぎてからの照会は開始されず、未反映だった対象が通信の失敗として記録されることはない

#### Scenario: 不正な形の応答は判定不能として扱う
- **GIVEN** nuget.org の index の version の一覧に、文字列でない要素が混ざった応答
- **WHEN** 反映待ちが照会する
- **THEN** 応答を解釈できない判定不能として記録され、未反映とは区別される

### Requirement: 保留中 deployment の引き継ぎの読み込み順序

同じ version の再実行が前の試行から引き継ぐ deployment ID の読み込みは、publish が必要とする
他の成果物の取得よりも先に行う SHALL。

- 引き継ぎを読み込んだかどうかと、引き継ぎが存在したかどうかは、実行の出力から区別できる SHALL。
- この順序は機械的に検査できる SHALL。

#### Scenario: 引き継ぎの読み込みが他の成果物の取得より先に行われる
- **GIVEN** 保留中の deployment を残した前の試行がある再実行
- **WHEN** publish が成果物の取得に失敗する
- **THEN** その時点で引き継ぎの読み込みは既に完了しており、読み込んだ結果が出力に残っている

#### Scenario: 引き継ぎが無い初回の実行と区別できる
- **GIVEN** 前の試行が存在しない初回の実行
- **WHEN** publish が引き継ぎを読み込む
- **THEN** 引き継ぎが存在しなかったことが出力に残り、読み込みに失敗した場合と区別できる

#### Scenario: 順序が崩れると検査が落ちる
- **GIVEN** 引き継ぎの読み込みを他の成果物の取得より後ろへ移した状態
- **WHEN** step 順序の検査が実行される
- **THEN** 検査は失敗し、検証 CI の lint job が落ちる

### Requirement: リリース用スクリプトの自己テスト

リリースで使うスクリプトは、ネットワークに出ずに判定ロジックを検査する自己テストを持ち、
その自己テストが日常の検証 CI で実行される SHALL。

publish と反映待ちの経路は不可逆な公開の後にしか到達しないため、判定ロジックの誤りを
リリース時に初めて知ることがないようにする。

- 自己テストは、誤った実装を与えたときに待機が終わらない形ではなく、失敗として表す SHALL。

#### Scenario: リリース用スクリプトの自己テストが lint job で走る
- **GIVEN** リリース用スクリプトを変更した状態
- **WHEN** 検証 CI の lint job が実行される
- **THEN** 各スクリプトの自己テストが実行され、失敗すれば lint job が落ちる

#### Scenario: 待ちの誤実装が停止ではなく失敗として表れる
- **GIVEN** 複数の対象を待つ処理が、対象の一部しか見ない誤った実装になっている状態
- **WHEN** 自己テストが実行される
- **THEN** 自己テストは終わらなくなるのではなく、失敗として報告される
