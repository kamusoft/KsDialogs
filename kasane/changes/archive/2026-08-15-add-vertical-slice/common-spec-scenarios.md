# 共通仕様シナリオ表 (core)

全形態 (iOS Native / Android Native / MAUI / KMP) に**同じ操作を与えて同じ観察結果になるか**を検証するための、core 契約のシナリオ表。design.md Decision 9 (シナリオ表 + 同名テスト規約) の初版であり、この変更で実装する各 platform のテストはここのシナリオ ID を冠した同名テストとして書く。

- 契約の意味論の正は concepts ([結果通知のルール](../../concepts/core/api/result-notification-semantics.md) / [多段表示のルール](../../concepts/core/api/multi-display-semantics.md))。本表は「その契約をどの操作でどう観察するか」を定める
- この変更で検証する Requirement / Scenario の正は [specs/dialog-contract](specs/dialog-contract/spec.md) ほかのデルタスペック。本表の受け入れ Scenario はデルタスペックの Scenario に1対1で対応する
- 本表は変更の足場層に置く作業文書。調査ケースの実挙動記録が埋まった後 (tasks 7.4)、長命の知識部分は蒸留で concepts へ引き上げる (「6. 蒸留への申し送り」)
- 検証手段の割り当て (どのセルを自動テスト / 手動確認 / Native 継承で判定するか) は [検証対応表](verification-matrix.md) が正

## 1. シナリオ ID の規約

- 形式は `<系統>-<連番>`。系統は 2 文字の英大文字、連番は英小文字 1 文字 (例: `MD-a`)
- 系統は観察対象のまとまりごとに割り当てる。初版は **MD = multi-display (多段表示)** の 1 系統のみ。新しい観察対象が増えたら系統を追加する (既存 ID の意味は変えない)
- **ID は安定キーとして扱う**: 一度割り当てた ID の意味を変えない・削除して再利用しない・欠番を詰め直さない。シナリオが不要になったら行は残し、種別欄に「廃止」と記す
- 種別は 2 つ
  - **受け入れ Scenario**: 期待される観察可能な結果を持ち、テストの合否 (または手動確認の可否) で判定する
  - **調査ケース**: 期待値を定めない。**各 OS の実挙動の記録が存在すること**が終了条件であり、記録を見てから期待値の確定 (= 受け入れ Scenario への昇格) を判断する

## 2. 同名テスト規約

各 platform は、同じシナリオを**同じ ID を冠した同名のテスト**として実装する。ID を横串の対応キーにすることで、形態をまたいだ実装漏れと挙動差を追跡できる。

- **表示名**: `<ID> <シナリオ名>` を本表の「シナリオ名」列そのままで使う (例: `MD-a 2枚重ねて上から順に閉じる`)
- **識別子**: 表示名を識別子にできない言語では `MD_a_` を先頭に付けた識別子とする (例: `MD_a_CloseFromTop`)
- 言語別の書き方
  | 形態 | 書き方 |
  |---|---|
  | iOS Native (Swift Testing) | `@Test("MD-a 2枚重ねて上から順に閉じる") func MD_a_closeFromTop() async throws` |
  | Android Native / KMP (Kotlin) | ``@Test fun `MD-a 2枚重ねて上から順に閉じる`()`` |
  | MAUI (C#) | `[Fact(DisplayName = "MD-a 2枚重ねて上から順に閉じる")] public async Task MD_a_CloseFromTop()` |
- **テストからこの文書のパスを参照しない**。ソースコメント規約 ([ソースコメント規約](../../concepts/cross/conventions/comment-policy.md)) により `kasane/` 配下の文書パスと変更識別子の裸参照はコメントに書けない。対応付けは**テスト名に含まれるシナリオ ID だけ**で成立させる (ID はテスト名の一部であり、コメント上の外部参照ではない)
- UI 操作が要るために自動テストにできないシナリオは、手動確認 + 証跡で代替してよい。その場合は証跡を `ui/verification/` に保存し、本表の記録欄からファイル名で参照する。**既定は自動テストであり、手動へ落とした場合は理由を記録欄に残す**
- テスト実行時は件数確認まで行う ([テスト実行規約](../../concepts/cross/conventions/test-execution.md))

## 4. 受け入れ Scenario の詳細と記録欄

### MD-a 2枚重ねて上から順に閉じる

- **GIVEN** show を 2 回呼び出し、ダイアログが 2 枚重なって表示されている
- **WHEN** 手前の 1 枚を完了操作で閉じ、続けて残る 1 枚を完了操作で閉じる
- **THEN** 各 show の呼び出しはそれぞれ独立に、自分のダイアログの結果値で completed を受け取る

2 枚は異なる結果値で完了させ、**どちらの show がどちらの値を受け取ったか**まで観察する (結果チャネルの取り違えを検出するため)。

| 記録項目 | 内容 |
|---|---|
| 判定結果 (iOS Native) | 合格 (2026-08-14)。自動テスト `MD-a 2枚重ねて上から順に閉じる` で、上を true・下を false で閉じ、各 show が自分の値で completed を受け取ることを確認 |
| 判定結果 (Android Native) | 合格 (2026-08-15)。自動テスト `MD-a 2枚重ねて上から順に閉じる` で、上を true・下を false で閉じ、各 show が自分の値で completed を受け取ることを確認 |
| OS 差の記録欄 | iOS Native: 自動テストは提示面 (器の出し入れ) を差し替えた状態での判定。UIKit の提示遷移がテストランナー (UI シーンを持たない) で完走しないため、閉鎖アニメーションのラグ・完了通知の順序といった実挙動の差は手動確認 (tasks 7.2) で観察する<br>Android Native: 同じく提示面を差し替えた状態での判定 (ダイアログのウィンドウ表示は画面を持たない JVM のテストで完走しないため)。器そのものは実装のものを組み立てて判定している。1枚が1つのウィンドウなので下の1枚は独立に残る想定で、閉鎖のラグを含む実挙動は手動確認 (tasks 7.2) で観察する<br>**実環境での観察 (2026-08-15、tasks 7.2)**: iOS Native (iPhone 17 Simulator / iOS 26.5) と Android Native (Emulator API 35) の**どちらも、上を完了操作で閉じると上だけが消えて下がそのまま残り、続けて下を閉じると各 show が独立に completed を受け取った**。OS 差は観察されなかった (見た目の差は覆いの重なりが 2 枚ぶん濃く見える点のみ)。証跡 `ui/verification/ios-native-md-a-*.png` / `android-native-md-a-*.png` |
| MAUI / KMP での差 | *(未記入 — 委譲による継承が崩れる挙動は観察していない。MD-a の実環境観察は規約どおり Native 2 セルを基準に行い、MAUI / KMP の 4 セルでは未観測)* |

### MD-c 重ね出し中の外側タップは手前のみ

- **GIVEN** ダイアログが 2 枚重なって表示されている
- **WHEN** 外側をタップする
- **THEN** 手前の show だけが cancelled で完了し、下のダイアログは表示されたまま結果未確定である

外タップキャンセルは既定有効 ([結果通知のルール](../../concepts/core/api/result-notification-semantics.md))。下の show が**未完了のままであること**の観察を必ず含める (完了していないことの確認なので、待ち合わせずに未完了を確認する形にする)。

| 記録項目 | 内容 |
|---|---|
| 判定結果 (iOS Native) | 合格 (2026-08-14)。自動テスト `MD-c 重ね出し中の外側タップは手前のみ` で、手前だけが cancelled で完了し、下は器が残ったまま結果未確定であることを確認 |
| 判定結果 (Android Native) | 合格 (2026-08-15)。自動テスト `MD-c 重ね出し中の外側タップは手前のみ` で、手前だけが cancelled で完了し、下は器が残ったまま結果未確定であることを確認 |
| 検証手段 (自動 / 手動) と理由 | iOS Native: 自動。ただし外側タップは器の外タップ処理を直接呼ぶ形で、タップ認識器から外タップ処理への配線 (中身の上のタップを除外する判定を含む) は合成タッチを作れないため手動確認 (tasks 7.2) に回す<br>Android Native: 同じく自動。覆いへのタップから外タップ処理への配線 (中身を包む層でタップを止める判定を含む) は実タッチを作れないため手動確認 (tasks 7.2) に回す |
| OS 差の記録欄 | **実環境での観察 (2026-08-15、tasks 7.2)**: iOS Native (iPhone 17 Simulator / iOS 26.5) と Android Native (Emulator API 35) の**どちらも、重ね出し中の外側タップで手前の show だけが cancelled になり、下のダイアログは表示されたまま結果未確定だった**。自動テストで手動へ回していた「タップ認識器 / 覆いから外タップ処理への配線」も、この観察で成立を確認した。OS 差は観察されなかった。証跡 `ui/verification/ios-native-md-c-outside-tap.png` / `android-native-md-c-outside-tap.png`<br>単独表示での外側タップは 6 セル全部で cancelled を確認済み (brief.md「最終照合の記録」) |
| MAUI / KMP での差 | *(未記入 — 委譲による継承が崩れる挙動は観察していない。重ね出しでの観察は Native 2 セルのみ、単独表示の外側タップは 6 セルで確認)* |

## 5. 調査ケースの詳細と実挙動記録欄

調査ケースの記録は**実環境の観測に限る**。コード読解からの推測を記録欄に書かない ([実行時挙動の検証規約](../../concepts/cross/conventions/runtime-behavior-verification.md))。記録には次を含める: 実施日 / OS バージョン・機種 (Simulator・エミュレータ可) / 実行した形態 (6 セルのどれか) / 観察結果 / 証跡 (`ui/verification/` のファイル名)。

記録は **Native iOS / Native Android の 2 セルを基準**とする (挙動を決めるのは Native 実装であり、MAUI / KMP は委譲で継承するため)。MAUI / KMP で基準と異なる挙動を観察した場合のみ追記する。

### MD-b 下のダイアログを先に閉じる

- **GIVEN** ダイアログが 2 枚重なって表示されている
- **WHEN** 下 (先に出した) の show が持つ DialogNotifier に対して先に完了報告を行う
- **終了条件** 各 OS で「どちらのダイアログが閉じたか」「上下それぞれの show がどう完了したか (完了した / 未完了のまま / 別の値になった)」の実挙動記録が存在すること

プログラムからダイアログを閉じる公開 API は本変更では提供しないため (design.md Decision 5)、下の 1 枚を先に閉じる操作は**その show の DialogNotifier への報告**で行う。多段表示のルールは「上から順に閉じる以外の閉じ方を保証しない」としており、移植元の調査では iOS で下の 1 枚を閉じたつもりが上の 1 枚が消える可能性がコード上示唆されている (実機未確認)。**この示唆に引きずられず、観察した事実だけを書く**。

| 記録項目 | 内容 |
|---|---|
| 実挙動記録 (iOS Native) | 実施日 2026-08-15 / iPhone 17 Simulator (iOS 26.5) / セル: Native iOS (samples/ios)。**下の1枚の DialogNotifier へ complete(false) を報告した瞬間に、上下 2 枚とも画面から消えた**。下の show は completed(false) で完了。**上の show はその後も完了せず、上のダイアログの器も戻ってこない (宙吊り)** — 15 秒待っても結果表示は「下:completed(false)」のままだった。証跡 `ui/verification/ios-native-md-b-lower-first.png` / `ios-native-md-b-upper-unresolved.png`。<br>**手当て後 (2026-08-15)**: 器が提示の連なりから外れたのに結果が未確定なら cancelled で確定させる手当て (`DialogContainerViewController.viewDidDisappear`。上に別の画面が全画面で重なっただけの場合は確定させない) を入れ、**上の show は cancelled で確定する** (宙吊りは解消)。根拠は自動テスト `MD-b 下のダイアログを先に閉じる` (器の出し入れは差し替えた提示面だが、閉鎖時の出現状態の遷移を実際に器へ伝えて確定を確認) と `器が画面から外れたら未確定の結果は cancelled になる`。<br>**手当て後の実機再観測 (2026-08-15 / iPhone 17 Simulator (iOS 26.5) / セル: Native iOS (samples/ios))**: 2 枚重ねた状態から下の 1 枚の DialogNotifier へ complete(false) を報告すると、**上下 2 枚とも画面から消える点は手当て前と同じ**で、**上の show は cancelled で確定して返った** (画面の結果表示が「下:completed(false)」「上:cancelled」の 2 行になった)。宙吊りが解消していることを実環境で確認。証跡 `ui/verification/ios-native-md-b-recheck-stacked.png` / `ios-native-md-b-recheck-upper-cancelled.png`。観測には samples/ios への一時変更 (2枚重ね表示と、下の show の notifier へ先行報告する経路) を使い、観測後に撤去してチェックサム一致を確認済み |
| 実挙動記録 (Android Native) | 実施日 2026-08-15 / Android Emulator API 35 (1080x2340) / セル: Native Android (samples/android)。**下の1枚だけが閉じ、上のダイアログは表示されたまま残った**。下の show は completed(false) で完了し、**上はそのまま操作でき、後から OK を押すと completed(true) で正常に完了した**。証跡 `ui/verification/android-native-md-b-lower-first.png` / `android-native-md-b-after-upper-closed.png`。<br>**手当て後 (2026-08-15)**: 器が画面から外れた時点で結果が未確定なら cancelled で確定させる手当てを入れた (閉鎖の通知・提示先の画面の破棄の購読・ウィンドウの取り外し検知の3経路から確定させる。画面の破棄では閉鎖の通知が届かないことを実機で確認したため、購読と取り外し検知を足した)。下の1枚を閉じる操作そのものには手を加えていない。**手当て後のエミュレータ再観測は未実施** — 本経路の観測結果が変わるかは次の手動確認の機会に再観測する。自動テストの範囲では `MD-b 下のダイアログを先に閉じる` の観察 (上の show は報告なしでは完了せず、器も1枚残ったまま) に変化はなかった。手当てが効くのは画面の破棄など**結果報告を経ずに器だけが消える経路**で、根拠は自動テスト `外の要因で器が閉じた show は cancelled で完了する` / `器が画面から外れたら未確定の結果は cancelled になる` / `確定済みの結果は器が画面から外れても変わらない`。<br>**器の閉鎖通知の実機観測 (2026-08-15 / Android Emulator API 35 / セル: Native Android)**: MD-b そのものではなく、手当てが効くはずの「画面の破棄」経路を実測したところ、**画面回転で Activity が作り直されると、ダイアログは画面から消えるのに show は完了しなかった** (logcat に `android.view.WindowLeaked`。Activity 破棄ではウィンドウが取り除かれるだけで `Dialog.dismiss()` は呼ばれず、閉鎖通知が発火しない)。この経路では宙吊りが残っていた。<br>**手当ての修正後の再観測 (2026-08-15 / 同環境)**: 画面破棄の購読・自前の閉鎖・ウィンドウ取り外しの検知を足した修正の後、**画面回転で show は cancelled で完了し、作り直された画面に `結果: cancelled` が出た**。`WindowLeaked` の警告も出なくなった (0 件)。**MD-b 自体 (下を先に閉じる) の手当て後の再観測も実施し、結果は手当て前と同じ** — 下だけが閉じて下の show が completed(false) で完了し、**上はそのまま残って後から OK で completed(true) で完了できた**。証跡 `ui/verification/android-native-md-b-recheck-*.png` / `android-native-rotation-recheck-*.png`。詳細は [検証対応表](verification-matrix.md) の実績メモ |
| MAUI / KMP での差 | *(未観測 — 記録は Native 2 セルを基準とする規約に従い、MAUI / KMP の 4 セルでは MD-b を観測していない)* |
| 期待値確定の判断 | **iOS と Android で挙動が割れる**ため、そのままでは受け入れ Scenario へ昇格できない。選択肢は (a) Android の挙動 (下だけ閉じ上は生存) を契約として規定し iOS 実装を寄せる、(b)「上から順に閉じる以外は保証しない」を明文化したうえで **iOS で上の show が宙吊りになる (結果が永久に返らない) こと**を既知の穴として記す、の 2 つ。**iOS の宙吊りは呼び出し側が await から戻れないという実害があるため、(a) 寄りの判断が要る**。確定作業自体は本変更のスコープ外 (蒸留への申し送り)。<br>**手当て後 (2026-08-15)**: 宙吊り (結果が返らない) は解消し、上の show は cancelled で返るようになった。残る差は「iOS は上も一緒に閉じて cancelled / Android は上が残り操作を続けられる」であり、どちらを契約にするかの判断は引き続きオーナー判断 (手当ては挙動の作り込みではなく、結果を必ず1回返すための最低限の手当て) |

### MD-d キーボード表示中の戻るボタン (Android)

- **GIVEN** Android で、入力欄を持つダイアログが表示されソフトキーボードが出ている
- **WHEN** 戻るボタンを押す
- **終了条件** 「キーボードだけが閉じてダイアログは残るか / ダイアログが cancelled になるか」の実挙動記録が存在すること

iOS に戻るボタンはないため **iOS 系のセルは非該当**。キーボード非表示時の戻るボタンは cancelled と規定済み (android-native の Requirement「戻るボタンによるキャンセル (通常時)」) であり、本ケースは**キーボード表示中に限った規定外の範囲**の実測。縦串の最小カスタム View (ラベル + OK / Cancel) は入力欄を持たないため、記録には**入力欄を持つ検証用 View** が別途要る (この検証用 View は Sample のデモ項目には含めない — パリティ対象は Basic Dialog のみ)。

| 記録項目 | 内容 |
|---|---|
| 実挙動記録 (Android Native) | 実施日 2026-08-15 / Android Emulator API 35 (1080x2340) / セル: Native Android (samples/android)。ソフトキーボード表示中に戻るボタンを押すと、**キーボードだけが閉じ、ダイアログは表示されたまま結果も未確定のまま**だった (`dumpsys input_method` の `mInputShown` が true → false)。**続けてもう一度戻るボタンを押すと cancelled** になり、通常時の規定どおりに閉じた。証跡 `ui/verification/android-native-md-d-keyboard-shown.png` / `android-native-md-d-after-back.png` / `android-native-md-d-second-back.png` |
| MAUI Android / KMP Android での差 | *(未観測 — 記録は Native 2 セルを基準とする規約に従い、MAUI / KMP では観測していない)* |
| 検証用 View の用意 | 観測時に **samples/android の MainActivity へ一時的に**、入力欄 (EditText) だけを持つ検証用 ViewModel / View を登録し、音量ボタンで起動する経路を足して観測した。Sample のデモ項目 (Basic Dialog) には含めていない。**観測後に原本へ戻し、samples 全 60 ファイルのチェックサム一致を確認済み**。エミュレータ側は `settings put secure show_ime_with_hard_keyboard 1` でソフトキーボードを出し、観測後に `settings delete` で既定へ戻した |
| 期待値確定の判断 | 観測結果は移植元の「キーボード表示中は無視」と一致する (キーボードを閉じるのが OS 既定の戻る処理で、ダイアログは無関係に残る)。**移植元の挙動をそのまま引き継ぐ方向で確定できる**が、明文化するなら「キーボード表示中の戻るは cancelled にしない」ではなく「戻るの1段目は OS の IME 閉鎖に消費される」という OS 由来の説明にするのが実態に近い。確定は本変更のスコープ外 |

## 6. 蒸留への申し送り

- MD-b / MD-d の実挙動記録は、[多段表示のルール](../../concepts/core/api/multi-display-semantics.md) の「保証しないこと」節と [結果通知のルール](../../concepts/core/api/result-notification-semantics.md) の「まだ決めていないこと」節への追記候補 (tasks 7.4)
- シナリオ ID の規約と同名テスト規約は、phase-5 以降もテストの命名規約として効き続ける。本表が変更のアーカイブとともに参照対象から外れると、テスト名の ID が指す先が失われる — **規約とシナリオ定義を core の長命層へ引き上げるかの判断を蒸留で行う**

### tasks 7.4 でまとまった追記候補 (2026-08-15)

1. **[多段表示のルール] 「保証しないこと」節へ**: 上から順でない閉じ方の実挙動が **OS で割れる**ことを事実として書く
   (下記は「器が画面から外れたら未確定の結果を cancelled で確定させる」手当てを入れた後の姿。手当て前は iOS で
   上の show が完了しないまま残る宙吊りだったが、それは解消済み)。
   - iOS: 下の1枚へ先に結果報告すると**上下とも器が消え、上の show は cancelled で確定する** (利用者が触っていない
     ダイアログが、下を閉じた巻き添えで cancelled になる)
   - Android: 下の1枚だけが閉じ、**上は表示され続けて後から通常どおり完了できる**
   - どちらも「結果をちょうど1回返す」は満たすため宙吊りの実害はないが、**同じ操作で観察結果が割れる**ことに変わりはない。
     単なる注記で済ませず **ADR 級の判断 (Android 側へ寄せるか / 上から順以外を明示的に禁止するか)** として扱うことを推す。
     **どちらの契約にするかはオーナー判断待ち**であり、上記の手当ては契約の先取りではなく「結果が返らない状態を作らない」
     ための最低限の措置である
2. **[結果通知のルール] 「まだ決めていないこと」節へ**: Android の戻るボタンとソフトキーボードの関係。
   - キーボード表示中の戻るは **OS の IME 閉鎖に消費され、ダイアログには届かない** (ライブラリ側で無視しているのではない)
   - 2回目の戻るで通常どおり cancelled になる。移植元の「キーボード表示中は無視」と観測が一致するため、
     規定化するなら「無視する」ではなく「OS が先に IME を閉じるため 1 段目は届かない」という書き方にする
3. **[結果通知のルール or 多段表示のルール] 補足候補**: 単独表示の外側タップ cancelled は 6 セル全部で実機確認済み。
   委譲経由 (MAUI / KMP) でも Native の挙動がそのまま継承されることの実測根拠として使える
