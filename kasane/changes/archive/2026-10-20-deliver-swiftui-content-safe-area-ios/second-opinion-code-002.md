## 指摘事項

### [🟠 Major] 幅が一度制限されると、ウィンドウを広げても古い配置幅から戻らない

**該当箇所**: `ios/Sources/KsDialogs/SwiftUI/DialogSwiftUIContentView.swift:134`  
関連箇所: 同ファイル `:58`、`:112`

**問題点**:

`placement` に保存した幅を解除する条件が「中身の理想サイズが変わった場合」だけです。ウィンドウ寸法や有効領域が広がっても、中身の理想サイズが同じなら保存した幅を使い続けます。

例えば、既定の可視領域に次の中身を表示します。

```swift
Color.clear.frame(idealWidth: 600, idealHeight: 100)
```

1. 幅 393 の縦長の窓では、理想幅 600 が制限され、`placement.width` に 393 が保存されます。
2. 窓を横長に変え、有効幅が 734 になっても、`intrinsicContentSize` は幅 393 を提案して測定します。
3. 制約側の最大幅は更新されますが、要求幅自体が 393 のため、器は本来置ける幅 600 に広がりません。
4. `preferredContentSize` の通知が来ても、制約なしで測った理想サイズは引き続き 600 × 100 なので、134行目では解除されません。

折り返す本文でも、以前の狭い幅と、それに基づく高さが残ります。共有ホストを使う Loading・Toast にも同じ条件が当てはまります。

これは deviation.md にある初回配置の幅や丸めの差とは別の問題です。現在の幅追従テストは窓を固定して中身だけを変更し、PB-IS-07 は幅が制限されない中身を使っているため、この経路を検出できません。

**推奨修正**:

配置幅のキャッシュを、現在の有効領域の幅と関連付けてください。有効領域が広がった際は理想幅から再測定し、新しい上限で必要な場合だけ折り返し幅を保存する形が必要です。単に `safeAreaInsetsDidChange()` のたびに解除すると、器自身の再配置による通知で循環し得るため、親の配置条件の変化として判定してください。

概念上の変更は次のとおりです。

```swift
// 現状
理想サイズが変わった場合だけ配置幅を破棄

// 修正後
理想サイズまたは有効領域の幅が変わった場合に配置幅を再評価
```

既定の可視領域で、理想幅 600 の中身を縦長で表示してから横長へ変更し、器の幅が 600 に戻る回帰テストを追加してください。現在の実装では以前の幅に残るため、修正の有無を区別できます。

## アクションプラン

1. 有効領域の拡大時に、保存した配置幅を再評価する。
2. 幅が制限された状態から窓を広げる回帰テストを追加する。
3. 既存の幅変更・折り返し・安全領域テストと合わせ、ホスト側で再検証する。
