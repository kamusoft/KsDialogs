# 経緯 (正直な記録):
#   1 回目の撮影 (2026-09-25 20:25) の時点では、この確認をしていなかった。
#   相方レビューの指摘を受け、同日 22:0x に次の手順で確認と撮り直しを行った。
#     1. 作業ツリーで MAUI iOS Sample を Debug で再ビルド
#        (dotnet build -f net10.0-ios -p:RuntimeIdentifier=iossimulator-arm64 -c Debug → 0 警告 0 エラー)
#        再リンクで実行ファイルの md5 が 6519d5b1… → ff75ba1f… に変わった。KsDialogs.Maui.dll と
#        KsDialogs.Binding.iOS.dll の md5 は再ビルドの前後で同じ (4a4763b9… / 496a3c17…)
#     2. Shutdown 状態の Simulator (iPhone Air、iOS 26.5) を boot し、.app を install
#     3. Simulator のアプリコンテナ内に配備された .app を、下の 3 つの判定材料で検査 (結果は下記)
#     4. 同じ配備物で Default Loading を撮り直し、sample-maui-ios-default-loading-*.png を差し替えた
#        (22:02〜22:03 撮影。1 回目の撮影と同じく 処理中 → 完了、撮影後もプロセスは生存)
#     5. Simulator を shutdown
#   1 回目の撮影に使った .app は、1 の再ビルドの前に上書きされずディスクに残っていたが、
#   配備先 (Simulator) のコピーは後の比較ビルドの install で上書きされているため、1 回目の配備物そのものは検査できない。
#   ディスク上の元 .app (再ビルド前、md5 6519d5b1…) には、下の判定材料 (a) (b) (c) がすべて出ていた (同じ nm / strings で確認)。
#
# 判定材料:
#   (a) Native の Loading.start の action 型が @MainActor になっていること。mangled 名の action 部分が
#       変更後は `...YaYbKScMYcXE...` (@Swift.MainActor)、変更前は `...YaYbKXE...`。
#       互換面の MauiLoadingBridge はこの start を呼ぶので、変更後の Native に対してリンクされたことを示す。
#   (b) 互換面の `@concurrent` 化で生じる reabstraction thunk
#       `$sSdIeghy_IghHg_SdIeghy_yts5Error_pIeghHgrzo_TR` があること。
#       互換面自身の closure の mangled 名は @concurrent の有無で変わらない (変更前後の .app で同一) ため、この thunk で判定する。
#       thunk が @concurrent 由来であることは、scratchpad で同じ形の最小コードを
#       `xcrun -sdk iphonesimulator swiftc -target arm64-apple-ios26.0-simulator -swift-version 6 -emit-object` で
#       2 通りにコンパイルして確かめた:
#         `@MainActor @Sendable (@Sendable @escaping (Double) -> Void) async throws -> T` を受ける start へ
#         `{ @concurrent report in ... }` を渡す → 上の thunk (と TA / TQ0_ / Tu 派生) が出る
#         `{ report in ... }` を渡す             → 出ない
#   (c) managed 側 KsDialogs.Maui.dll の metadata に `LoadingActionThread` と `Background` があること
#       (LoadingActionRunner の振り分け)。変更前の dll には無い。
