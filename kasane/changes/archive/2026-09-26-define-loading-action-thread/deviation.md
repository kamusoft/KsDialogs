- design Decision 3 (Android): design では「切り替えを action の呼び出しの内側に入れれば、報告と終了の順序の保証をそのまま保てる」→ Android では成り立たなかった。`withContext` は呼び出し元と同じ dispatcher なら dispatch を省き、UI スレッド外の action が呼び出し元の中断より先に終わるとその場で戻るため、終了の受理が UI スレッドの列に post された報告を追い越した (既定の指定で action の中から別スレッドで報告してすぐ戻る書き方でも起きる)。対策として `LoadingCoordinator.report` を「呼んだその場で 1 本の列 (`Channel`) に積み、UI スレッド上の 1 つの受理コルーチンが順に受理する」形に作り直し、終了の直前に同じ列の末尾へ区切り (`awaitAcceptedReports`) を積んで待つ形にした (iOS の `LoadingReportQueue` と同じ考え方)。あわせて、受理ループは報告 1 件ごとの受理を `scope` (`SupervisorJob`) 直下の子として起動し、利用者の進捗の受け口が投げた失敗がループと区切りの待ちを止めないようにした (失敗は握りつぶさず、変更前と同じくスレッドの未捕捉例外ハンドラへ出る。1 本の列にした作りでは、素直に書くと失敗で以後の終了が永久に待つ)。固定するテスト: `LoadingActionThreadTests` の LD-TH-07 と `既定の指定で_UI_スレッド外から報告して直後に戻っても最終進捗が終了に追い越されない`、`LoadingProgressTests` の `進捗の受け口が失敗しても以後の報告と終了は受理され次の開始が戻る`。理由: LD-TH-07 の保証を満たすため。iOS / MAUI / KMP iOS は報告と終了が元から同じ列に積まれる作りで、同じ追い越しは起きないことを照合済み (2026-09-25)

- [付随修正] `kasane/handbook/cross/test-execution.md` の件数表と件数に依存する記述: この change でテストが増えたため、実装フェーズでは件数表 7 行を完了ゲートの実測値へ更新していた → 蒸留時のオーナー指摘 (「handbook に実測件数を載せること自体が間違い」) により、件数表から実測件数の列を外してコマンドだけの表にし、実測日の但し書きを「本規約は件数の実測値を持たない。件数は変更の証跡に残し、完了判定では件数が 0 でないことと足したテストが結果に現れることを確かめる」に置き換えた。件数に依存していた文 (instrumented の 1 台分の件数・API レベル別の skip の本数・MAUI 互換面 2 ルートの件数・負の検査の本数) からも数を外し、`verification-ci.md` の件数 2 か所も同様に外した。API 30 以上で skip されるテスト (`PB_SB_04`) の説明と、doc-structure lint の既存違反 1 件 (android/ の件数の確認方法の項が 201 字) の言い回しの修正は残した。理由: 件数はテストを足すたびに変わる状態で、規範 (handbook) に置くと古くなる (2026-09-26)
- ios-native「Swift の action の型と、UI スレッド外で始める指定」(と proposal Impact・ADR-0037 の旧本文): spec では「isolation の指定が無い async 関数を名前で渡すと、その関数自身の isolation が優先され、UI スレッド外で始まる」→ 実際は利用者のモジュールの並行性設定しだい。`NonisolatedNonsendingByDefault` が無効 (Swift 6 の既定。このパッケージのテスト) なら UI スレッド外で始まり、有効 (Xcode 26 の新規プロジェクトの既定) なら呼び出し元の isolation を引き継いで UI スレッドで始まる。その場で書いたクロージャと `@concurrent` はどちらの設定でも変わらない。公開 doc コメントと ADR-0037 には、どちらの設定でも正しい「関数自身の isolation が優先される」という規則だけを書いた。理由: 実装時に scratchpad の最小コードで両設定を実測して判明 (2026-09-25)
