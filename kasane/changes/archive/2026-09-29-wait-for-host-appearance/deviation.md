# Deviation: wait-for-host-appearance

- design Decision 4 (待っている Dialog の列の持ち主): design では「Presenter が、提示先を待っている Dialog の列を呼んだ順に持つ」→ 実装判断により、列はアプリ全体で 1 つとし、提示面を通して Presenter に渡す (iOS: `DialogPresentationSurface.hostWaitQueue`。本番の提示面はすべて `DialogHostWaitQueue.application` を共有し、テスト用の提示面は面ごとに専用の列を持つ)。待ちの位置・明け方・列の規則は design のとおり。理由: `Dialog.shared`・DI で作ったインスタンス・KMP 互換面・MAUI ブリッジと Presenter が複数あっても、呼んだ順を保つため。Android も同じ持ち方に揃える (2026-09-27)
- design Decision 4 (列の入口までの順序): design は「呼んだ順」の起点を定めていない → 実装判断により、同じ UI スレッドから続けて呼んだ show が、その順のまま列に並ぶことを入口で保証する (iOS: `Dialog` の show 群を呼び出し元の実行文脈のまま走らせる。`nonisolated(nonsending)` 相当)。別々のスレッドからの呼び出しどうしの順は定めない。理由: iOS の `Dialog.show` が大域の実行器を経由して MainActor へ戻るため、列に並ぶ前に順番が入れ替わり、PB-HW-06 (A、B の順に呼ぶと A、B の順に表示) を満たさないことが実測で分かった (300 回中 6〜14 回。5.4 の MAUI iOS ブリッジのテストの間欠失敗が発端) (2026-09-27)。実装: `Dialog` の show 群と `KsDialog` の要件・拡張を `nonisolated(nonsending)` にした (要件を変えないと DI 経由の呼び出しで順が崩れることと、要件を変えても外部の準拠型がコンパイルできることを実測で確かめた)。UI スレッドへ移るのに Task を作る呼び出し口 (KMP の iOS 互換面 `KsDialogsInteropBridge.show`) は、Task の開始順に頼らないよう、呼び出しの時点で列の順番札を同期で取り (`DialogPresenter.reserveTurn(on:)`)、提示処理はその札の順で列に並ぶ。先に取られてまだ列に着いていない札がある間は、後の札の show を明けない。提示先があって列が空なら、札があっても今までどおり番を持たずにその場で提示する。実測は evidence/ios-dialog-sequential-presentation.md
  - 採らなかった案 (実装ワーカーの停止報告の選択肢。オーケストレーターが判断し、2026-09-27 にオーナーへ報告): show 群を `@MainActor` にする案は、公開プロトコルの隔離が変わり利用側のコンパイルに影響するおそれがあるため採らない。テストの側で A と B の間に待ちを挟んで安定させる案は、穴を隠すだけで PB-HW-06 (呼んだ順に表示) を満たさないため採らない
  - 同じ穴は KMP の iOS 互換面 (`KsDialogsInteropBridge` の show) と MAUI の iOS ブリッジ (`MauiDialogBridge.present`) にもある (Task の開始順に頼る)。Presenter 側に「呼び出しの時点で同期で列の順番札を取る」口を足し、両ブリッジはそれを使う。Android・KMP の Android・MAUI の Android ブリッジ・MAUI の C# (UI スレッドから) は保たれる (姉妹面の照合で確認) (2026-09-27)
  - MAUI の iOS ブリッジは別モジュールで Native の公開 API だけを使うため、内部の順番札の口に届かない → オーナー判断により、iOS Native にブリッジ専用の隠れた口 (`@_spi`) を足し、MAUI の iOS ブリッジはそれを使う。利用者向けの公開面・Skill は増やさない。プロジェクト初の `@_spi` なので、慣習は蒸留時に handbook へ書く。理由: Task の開始順は実測では安定しているが言語の保証が確認できず、iOS 17 の実行環境も未確認のため、公開面を増やさずに保証する (2026-09-28)
- dialog-contract PB-HW-06 (型指定の show の順序): spec は「呼んだ順」が型指定の show の configure の中断に及ぶかを定めていない → オーナー判断により、configure が中断した場合は呼んだ順を保証しない (準備ができた順に列に並ぶ)。実装は変えない。蒸留時に concepts (core/api/multi-display-semantics.md ほか) に書く。理由: 提示先がある場合も、configure が中断している間に後から呼んだ Dialog が先に出る (この change の前からの振る舞い) ので、待ちの有無で見え方を揃える。呼んだ時点で順番を取る案は、configure の遅い Dialog が後ろをすべて待たせ、提示先がある場合と見え方が揃わないため採らない (2026-09-27)
- design Decision 3 (提示面が器を載せられなかった場合): design は、提示先を確認して中身を作った後に、提示面が器を載せられなかった場合 (提示先を再取得できない / UIKit が提示を拒否する) の結末を定めていない → 実装判断により、その show は結果通知のルール 4 (a) の「器の消失」と同じく cancelled で確定し、列の番を返す。iOS と Android で揃える (Android は `IllegalStateException` を投げていた)。理由: 独立レビュー (review-001 と second-opinion-code-001 の突き合わせ) で、show が終わらず共有の列も止まりうることが分かったため (2026-09-28)
  - 実装: iOS は提示面の完了通知に「載せられたか」を持たせ、載せられなかった show は器の消失と同じ経路 (`handleHostLost`) で cancelled に確定して番を返す。UIKit は提示元の遷移中 (閉じる途中の画面の手前など) の提示を拒否せず遷移の終わりまで持ち越し、終わりに結べなかった提示だけを完了通知なしで拒否すると実測で分かったため、提示の直後に提示関係が無ければ、遷移中は遷移の完了通知で、遷移が無ければその場で判定する (MAUI iOS ブリッジのテストホストで実測。直後の判定だけでは持ち越された提示を取り消して器を画面に取り残す)。Android は提示先が得られなければ中身を作らずに cancelled を届ける handle を返す (2026-09-28)。iOS で遷移の完了の見張りを提示機構が受け付けなかった (`animate(alongsideTransition:completion:)` が false を返した) 場合は、その場で提示関係を確かめ直し、結ばれていなければ載せられなかったとして cancelled に確定させる (結ばれていれば提示機構の完了通知を待つ)。iOS で載せられなかったと知らせた後に提示機構が遅れて提示を結んだ場合は、器の確定済みの結果は変えずに、器を提示元から閉じて画面から外す (2026-09-28)
- [付随修正] iOS の既定の並列実行で Toast スイートの先頭のテスト (TS-CO-01・TS-IO-02・TS-TR-01・TS-MX-02 など) が 5〜8 秒の提示待ちで間欠的に落ちる (変更前の HEAD でも 4 回中 3 回再現。handbook cross/verification-ci.md の「手元では既定の並列で全件が安定する」と食い違う): proposal のスコープ外 → オーナー指示により同梱して原因を切り分けて直す。handbook の記述の改訂が要る場合は実装では書き換えず、蒸留時に反映する。理由: オーナー判断 (2026-09-27)。結論: 並列実行の立ち上がりで MainActor が秒単位で混み、期限の短い Toast の受理が期限の後に走って表示が捨てられていた (ライブラリの不具合ではない) ため、Toast のスイートに各テストの前で MainActor の混み合いが引くのを待つ trait を付けて直した (実測は evidence/ios-parallel-toast-flake.md)
