# 直す前の実測と起動順の観測 (wait-for-host-appearance、tasks 1.2・1.3)

## 環境と手順

- 環境: iPhone Air / iOS 26.5 の Simulator (この実測のために新しく作って boot したデバイス)、Xcode 26.5。2 Sample とも Debug ビルド
- Sample: tasks 1.1 の変更後 (自動再生は最初の画面の表示時に始め、シーンの状態を待たない)。ライブラリは変えていない
- 起動: `xcrun simctl terminate` → 1.5 秒待ち → `xcrun simctl launch <bundle-id> --demo <デモID> --loading-step-interval-ms 5000`
- 判定: 起動直後から連続撮影し、指定デモの「起動直後の状態」(sample-parity「安定デモ ID」表) が画面に出たか、プロセスが落ちていないかを見る
  - Dialog・Loading: 約 1 秒間隔で 6〜8 枚 (初回の撮影は起動から約 1.3〜1.6 秒後、最後は約 7〜11 秒後)。落ちたかどうかは、最後の撮影後に起動したプロセスが残っているかで判定
  - Toast: ios の 1〜5 回目は 0.3 秒間隔で 12 枚 (撮影時刻は記録していない)。ios の 6〜8 回目と kmp (iOS) は間隔を空けずに 10〜14 枚 (初回は起動から約 0.6〜0.8 秒後、最後は約 3〜4 秒後)。Toast の写り込みは、各コマを最後のコマと比べた差分で判定し、差分のあるコマは目視で確かめた
- 表の「出た / 試行」は、起動直後の状態が出て落ちなかった回数 / 起動回数

## 1.3 起動順の観測

両 Sample の App の初期化と最初の画面の表示時の処理に一時的な診断出力を入れ、次の時点を記録した。観測後に取り除き、4 ファイルとも診断出力を入れる前とチェックサムが一致することを確かめた。

- 通知: window が key になった (`UIWindow.didBecomeKeyNotification`)、シーンがアクティブになった (`UIScene.didActivateNotification`)、ほかにシーンの接続・前面化・非アクティブ化・背面化と、window の key の解除
- 提示先の条件: ライブラリの提示先を選ぶ規則と同じ条件 (前面でアクティブなシーンの key window があるか) を、各通知の受け取り時点で読み、さらに 2 ミリ秒ごとの見張りで変化した時点を記録した
- 最初の画面の表示時の処理と、自動再生の開始の時点

ログの抜粋は `host-appearance-order.log`。

### 通常の起動 (ios 3 回・kmp (iOS) 3 回)

6 回とも同じ順序だった (起動からの経過は ios の 1 回目)。

| 経過 | 事象 | 提示先の条件 | シーンの状態 |
|---|---|---|---|
| 0 ms | App の初期化 | 満たさない | シーンなし |
| 60 ms | **window が key になった通知** | 満たさない | 未接続 (window は key) |
| 61 ms | シーンの接続・前面化の通知 | 満たさない | 未接続 |
| 100 ms | 最初の画面の表示時の処理 | 満たさない | 前面・非アクティブ |
| 115 ms | 自動再生の開始 (ライブラリの呼び出し) | 満たさない | 前面・非アクティブ |
| 152 ms | **シーンがアクティブになった通知** | **満たす** (通知の受け取り時点で既に満たしている) | 前面・アクティブ |
| 153 ms | 見張りが条件の変化を検出 | 満たす | 前面・アクティブ |

- window が key になった通知は、シーンが未接続のうちに届き、その時点では提示先の条件を満たさない。今の Toast はこの通知だけを待っているので、起動直後に呼ばれた Toast はこの通知では取り付けられない
- 提示先の条件が満たされるのは、6 回ともシーンがアクティブになった通知と同じ時点だった (通知の受け取り時点で既に満たしており、見張りの検出は通知の 1〜2 ミリ秒後)。条件を満たした時点の前後に、2 つの通知のどちらも来ない場面は無かった
- 自動再生の開始 (ライブラリの呼び出し) は、6 回とも 2 つの通知の間 (key の通知の後、アクティブ化の通知の前) にあり、その時点では条件を満たさない

### システムの許可ダイアログが出る起動 (ios 1 回)

App の初期化で通知の許可を求め (診断出力の一部。起動引数で切り替え)、default-loading を自動再生した。

| 経過 | 事象 | 提示先の条件 | シーンの状態 |
|---|---|---|---|
| 70 ms | window が key になった通知 | 満たさない | 未接続 |
| 122 ms | 自動再生の開始 | 満たさない | 前面・非アクティブ |
| 330 ms | シーンがアクティブになった通知 | 満たす | 前面・アクティブ |
| 870 ms | 許可ダイアログが出て、シーンが非アクティブになる通知 | (通知の時点では満たす) | 前面・アクティブ → 非アクティブ |
| 873 ms | 見張りが条件の変化を検出 | 満たさない | 前面・非アクティブ |

- 許可ダイアログが出る前に、一度シーンがアクティブになり条件を満たす時間 (約 0.5 秒) があった。自動再生はそれより前なので、今のライブラリでは Loading は出なかった (`order-ios-system-alert-inactive.png`。結果表示は「処理中」、Loading は出ていない)
- 許可ダイアログが出ている間、window の key は外れない (window が key を外れる通知は来ない)。条件はシーンが非アクティブであることだけで満たさなくなる

### 許可ダイアログが出たまま、背面へ回して前面へ戻す (ios 1 回・kmp (iOS) 1 回)

- 設定アプリを前面にしてから Sample を前面に戻すと、背面化の通知と前面化の通知は来るが、シーンがアクティブになった通知は来ず、条件も満たさないままだった
- 許可ダイアログはシステム側に残り、そのあと別のプロセスで起動し直した ios と kmp (iOS) も、シーンが前面・非アクティブのまま一度もアクティブにならなかった (window が key になった通知は起動直後に届くが、その時点では条件を満たさない)。どちらの場面でも、条件は満たさないままで、通知が来ないまま条件を満たす場面は無かった

### 観測できなかったこと

- **許可ダイアログを閉じた後の順序**: ダイアログの「許可」を押す操作ができなかった (シミュレータの中を操作するツールの使用許可が得られなかった。Simulator.app 側の操作はしない)。閉じるとシーンがアクティブになる通知が来て条件を満たす、という見立ては実測していない。許可ダイアログは Simulator を再起動して消した
- ios の default-toast が 1・2 回目だけ出た理由: 診断出力を入れた 9 回の起動では、window が key になった通知の時点で条件を満たした回は無かった
