# Deviation: add-loading

- LD-CO-11 (dialog-contract / Requirement: Loading の公開面と合流): spec では「旧世代の処理が報告する進捗・メッセージは新しい表示に届かない」→ 指示により遮断対象は**進捗のみ**。メッセージ更新 (setMessage) は世代に紐づかないグローバル操作 (design Decision 2) であり、いつ呼んでも現在の表示に効く (後勝ち)。理由: API 形状上「処理に紐づくメッセージ報告」の経路が存在せず、原典の SetMessage と同挙動 (2026-08-26)
- [付随修正] android `ResumedActivityTracker` / `ResumedActivityProvider`: resumed Activity の入れ替わりを購読できる口 (`observeResumedChange` + observer/registration interface) を追加。理由: Loading 器の Activity 再生成時の再取り付け (design Decision 4) に必須の契機で、既存の破棄購読では新画面の resumed を捉えられないため。既存挙動は不変、LD-WN-01 が回帰ガード (2026-08-26)
- [付随修正] maui 両 OS の `PlatformDialogGateway`: 中身の写し (提示先文脈の解決・platform view 化と測定・添付スナップショットの受け渡し・演出の実行口) を internal 部品 `PlatformDialogContent` へ切り出し、Dialog / Loading の両 gateway で共有。理由: Loading 面の追加で同型実装が二重になるのを回避 (design Decision 4 と同じ判断)。Dialog 側は挙動不変で既存テスト (maui 88 + instrumented) が回帰ガード (2026-08-26)
- LD-MA-01 (maui-binding / C# 公開面の Loading) の帰結: これまで internal だった C# の `DialogOptions` を public に変更 (interop 詳細の `OverlayColorArgb` は internal のまま)。spec の「Options は既存 DialogOptions を再利用」を設定プロパティの型として満たすために必要。負の検査 12 本は影響なしを確認済み (2026-08-26)
- [付随修正] `samples/maui/README.md`: Fast Deployment 残骸のある端末へ `install -r` すると起動時 InvalidCastException になる罠と、`adb uninstall` からの入れ直し手順を追記。理由: 4ルート通し (6.3) の検証中に実測した手順知見で、Sample の挙動には影響しない (2026-08-26)
- [付随修正] ios `DialogTransitionTests`: 演出フックの取り消し記録を待ちなしで観察していた 4 箇所 (PB-TR-12 / PB-TR-23 / PB-TR-28 / PB-TR-29) を `waitUntilCancelled` の待ちに変更。理由: 門で待つフックの `CancellationError` は取り消しの受け口が改めて立てる仕事で届くため、結果の配送との間に順序の保証がなく間欠失敗していた (PB-TR-23 は本変更なしの HEAD でも再現)。テスト専用の変更で本体挙動には触れていない (2026-08-26)
- [付随修正] ios `LoadingStartFailureTests` (新規): 中身の生成に失敗した開始が合流・器を残さないこと、受理直後に呼び出し元が取り消されても合流を数え切ることの回帰ガード 2 本を追加。理由: Android 側に同趣旨のテストがあり、iOS では構造上同じ穴が生じないことをテストで固定するため (2026-08-26)
- 失敗モデルの未定義コーナー (dialog-contract / Requirement: Loading の公開面と合流): 提示先不在で開始したカスタム Loading の遅延 View 生成 (Android のみ存在する経路) が失敗した場合、指示により**表示なしで完走**とする — 表示は諦めて警告ログを残し、action は完走して start は結果を通常どおり返す (「提示環境の不在では表示は成立する範囲で行う」の延長)。理由: factory は通常経路で毎回実行されるため遅延経路でだけ失敗するのは構成依存のまれな開発者バグで、利用者の処理を道連れにしない側に倒す。捕捉は Exception に限定し、致命的 Error は伝播させる (2026-08-26)
- [付随修正] maui `LoadingActionRunner` (新規 internal 部品): 「処理を走らせ成否によらず終了をちょうど1回伝え、進捗を同期転送する」手順を両 OS の `PlatformLoadingGateway` から共通化。理由: 最終進捗の喪失修正 (レビュー採用指摘) の順序保証を1箇所に置き、platform TFM 外の C# テストから検証可能にするため。挙動差分は進捗の非同期投げ直しが無くなる点のみ (2026-08-26)
- 制約の記録 (maui-binding / LD-MA-03): MAUI iOS bridge (Swift) の写し (`MauiLoadingStyle` → Native `LoadingStyle` 等) には自動テストが無い。`KsDialogsMauiBridge.xcodeproj` が framework ターゲットのみでテストターゲット・スキームを持たないため (Dialog 面の bridge も同条件)。値保存・順序の担保は Kotlin 側 bridge テストと C# 共有部品 (`LoadingActionRunner`) のテストが受け持ち、Swift の写しは読み合わせで確認済み (2026-08-26)
- [付随修正] ios `DialogTransitionTests` PB-TR-21: 器の取り付け直後に `.presenting` を待ちなしで観察していた箇所へ出現待ちを追加 (PB-TR-12/23/28/29 と同系統の待ち不足。負荷時に `.attached` のまま評価されて間欠失敗)。テスト専用の変更 (2026-08-26)
- [付随修正] ios `LoadingReportQueue` (新規 internal 部品): 進捗報告の受理を「直前の受理を待ってから次を受理する」鎖に載せ、処理の終了前に `drain()` で発行済みの受理を待ち切るようにした。`Loading` のスコープ形と KMP 互換面 (`KsDialogsInteropLoadingBridge` の報告・終了) が使う。理由: 受理のたびに独立した仕事を投げる形は、受理どうしの順序も報告と終了の前後も言語仕様では保証されず、「最終報告が終了に追い越される」余地が残っていたため (レビュー採用指摘)。互換面の終了通知は発行済みの報告の受理後に届くようになる (2026-08-26)
