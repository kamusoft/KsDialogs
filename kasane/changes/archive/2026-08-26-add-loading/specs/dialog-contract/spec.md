# dialog-contract デルタ (add-loading)

Scenario ID は `LD-<領域>-<NN>` (design Decision 5)。挙動系は両 Native のテスト名に ID を含めて対応付ける (core/ADR-0016)。根拠決定: core/ADR-0022〜0024。

## ADDED Requirements

### Requirement: Loading の公開面と合流

Loading の公開面は契約 interface + 既定シングルトンエントリで提供する (SHALL — core/ADR-0002、命名は原典踏襲)。呼び出し面は、命令形 `show(message?, placement?)` / `hide()` / `setMessage(message)` と、処理ブロックを渡すスコープ形 `start(message?, placement?, action)` (原典 StartAsync 相当) を持つ。スコープ形は action の完了で戻り、action の戻り値をそのまま返す。

多重利用は合流とする (core/ADR-0024): 重なった利用は1つの表示に合流し、表示は最初の開始から最後の終了まで継続する。渡された action は表示状態によらず必ず実行される。action の失敗 (例外・キャンセル) も合流1件の終了として数え、失敗は呼び出し元へ伝播する。明示の `hide()` は合流数によらず表示を即閉じ、走行中の action には干渉しない。合流中のコンテンツ (既定 / カスタム) は最初の開始のものを維持し、後続の要求はメッセージ・進捗にのみ寄与する。メッセージは最新の指定が勝つ (後勝ち)。`setMessage` は合流に関与しない表示中のみの更新で、既定ローディング表示中にのみ効く (非表示中・カスタム表示中は何もしない)。

Loading はユーザー操作では閉じない。表示中、背後の画面への操作は透過しない。

**表示世代**: `hide()` は現在の表示世代を終了させる。旧世代に属する利用の終了・進捗・メッセージは、以後の表示 (新世代) のカウント・表示内容に一切影響しない。旧世代の action 自体は継続して実行され、その戻り値・失敗は元の呼び出し元へ通常どおり返る。

**完了時点**: `show` は操作ブロックが有効になった時点で戻る (入りの演出の完了は待たない)。`hide` と合流最後の `start` は、出の演出と器の撤去の完了まで待って戻る。合流中の非最終 `start` は自身の action の完了時点で戻る (表示は継続する)。入りの途中の `hide` は入りの完了を待たずに出へ移る。出の途中の新しい開始は、出の完了後に新世代として表示される。

**失敗モデル**: 構成ミス (未登録 VM・View factory の失敗) は action を実行せずに失敗として伝播する (結果に化けない — Dialog と同じ fail-fast)。提示環境の不在 (取り付け先ウィンドウ・Activity が無い等) では action は実行され、start はその戻り値・失敗を通常どおり返す (表示は成立する範囲で行う)。「action は必ず実行される」(core/ADR-0024) は「合流・表示状態を理由に実行を保留・放棄しない」の意味であり、構成ミスの fail-fast はこれに反しない。

**状態の共有と直列化**: 合流状態 (カウント・世代・表示中コンテンツ・最新のメッセージと進捗) は 1 OS プロセス内で単一であり、すべての入口 (既定シングルトン・契約 interface から構築した実装インスタンス・ラッパー形態の呼び出し面) が同じ状態を共有する。状態を変える操作は UI スレッド上で受理順に直列化され、「最新 (後勝ち)」は受理順で定義する。呼び出しは任意スレッドから行える (Dialog 面と同じ)。

#### Scenario: [LD-CO-01] show で表示され hide で消える
- **GIVEN** Loading が表示されていない状態
- **WHEN** show を呼び、その後 hide を呼ぶ
- **THEN** show 後に既定ローディングが表示され、hide 後に表示が消える

#### Scenario: [LD-CO-02] スコープ形は処理完了で自動的に閉じ、処理の戻り値を返す
- **GIVEN** 値を返す非同期処理
- **WHEN** スコープ形 start にその処理を渡す
- **THEN** 処理の実行中は表示され、完了後に表示が消え、start が処理の戻り値を返す

#### Scenario: [LD-CO-03] 重なったスコープ形は1つの表示に合流し、最後の完了で閉じる
- **GIVEN** 完了タイミングを個別に制御できる2つの処理
- **WHEN** スコープ形 start を重ねて呼び、先に開始した処理を先に完了させる
- **THEN** 表示は1つで、先の完了では消えず、後の処理の完了で消える

#### Scenario: [LD-CO-04] 表示中でも渡した処理は必ず実行される
- **GIVEN** show で表示中の Loading
- **WHEN** スコープ形 start を呼ぶ
- **THEN** 処理は実行され、完了後も (show の合流が残るため) 表示は継続する

#### Scenario: [LD-CO-05] 処理の失敗は合流1件の終了として数え、呼び出し元へ伝播する
- **GIVEN** 例外を投げる処理
- **WHEN** 単独のスコープ形 start にその処理を渡す
- **THEN** 失敗が呼び出し元へ伝播し、表示は消える (閉じ漏れしない)

#### Scenario: [LD-CO-06] hide は合流数によらず即閉じ、走行中の処理は継続する
- **GIVEN** スコープ形 start の処理が走行中の表示
- **WHEN** hide を呼ぶ
- **THEN** 表示は消え、処理は継続して完了し、完了によって表示が再出現しない

#### Scenario: [LD-CO-07] メッセージは後勝ち
- **GIVEN** メッセージ A で表示中の既定ローディング
- **WHEN** メッセージ B を指定してもう1件の利用を開始する
- **THEN** 表示テキストが B に更新される

#### Scenario: [LD-CO-08] setMessage は表示中のみ有効で合流に関与しない
- **GIVEN** 表示中の既定ローディングと、非表示の状態のそれぞれ
- **WHEN** setMessage を呼ぶ
- **THEN** 表示中は表示テキストだけが更新され (hide の対応は不要)、非表示中は何も起こらない

#### Scenario: [LD-CO-09] コンテンツは最初の開始が決める
- **GIVEN** カスタム View で表示中の Loading
- **WHEN** 既定ローディングのスコープ形 start を重ねる
- **THEN** 表示はカスタム View のまま合流し、両方の終了で表示が消える

#### Scenario: [LD-CO-10] hide 後の新しい表示は旧世代の完了で閉じない
- **GIVEN** スコープ形 start の処理 A が走行中に hide した状態
- **WHEN** 新しくスコープ形 start (処理 B) を開始し、その後 A が完了する
- **THEN** A の完了で B の表示は閉じず、B の完了で閉じる。A の戻り値は A の呼び出し元へ通常どおり返る

#### Scenario: [LD-CO-11] 旧世代の遅延進捗・メッセージは新しい表示に届かない
- **GIVEN** hide で旧世代になった走行中の処理 A と、新世代の表示 (処理 B)
- **WHEN** A が進捗・メッセージを報告する
- **THEN** 新世代の表示内容は変わらない (B の報告だけが反映される)

#### Scenario: [LD-CO-12] hide と最終 start は撤去完了後に戻る
- **GIVEN** 表示中の Loading
- **WHEN** hide (または合流最後の start の action 完了) が戻る
- **THEN** 戻った時点で器は撤去済みで、操作ブロックは解除されている

#### Scenario: [LD-CO-13] 出の途中の新しい開始は出の完了後に新世代として表示される
- **GIVEN** 出の演出の途中にある Loading
- **WHEN** 新しい表示を開始する
- **THEN** 出が完了してから新世代として表示され、旧世代の状態 (メッセージ・進捗) を引き継がない

#### Scenario: [LD-CO-14] 提示環境が無くても action は実行される
- **GIVEN** 取り付け先 (ウィンドウ / Activity) が存在しない状態
- **WHEN** スコープ形 start を呼ぶ
- **THEN** action は実行され、start はその戻り値を返す (表示の不成立を理由に保留・放棄されない)

#### Scenario: [LD-CO-15] 異なる入口からの利用は1つの表示に合流する
- **GIVEN** 既定シングルトンと、契約 interface から構築した別インスタンス (またはラッパー形態の呼び出し面)
- **WHEN** 両方の入口から Loading の利用を重ねる
- **THEN** 表示は1つに合流し、最後の終了で閉じる (入口ごとに別の表示が出ない)

### Requirement: 器メタ属性の適用

レイアウト系の器メタ属性 (layoutArea / dialogMargin / 比率サイズ / overlayColor / placement) は、Dialog と同じ意味・同じ供給規則 (コンテンツ添付 + 表示 API の引数は placement のみ、優先順位も同一 — core/ADR-0015) で Loading にも適用する (SHALL)。既定ローディングは利用者の添付面を持たないため、配置・オフセットは表示 API の placement 引数で指定し、options (overlayColor 等) は Loading シングルトンの設定プロパティ (既存 DialogOptions を再利用、各表示の開始時に読む — 既定コンテンツへの添付相当) で供給する。カスタム View 表示ではこの設定プロパティは使われず、View への添付が正となる。isCanceledOnTouchOutside は Loading では常に無効であり、添付されても効かない。表示中のウィンドウ寸法・insets の変化 (回転を含む) では、Dialog と同じ規則 (凍結済み実効値での再配置) に従い、表示は継続する。レイアウト共通ケース表 (`core/layout-spec/cases.json`) は Loading の器でも全量適合する (isCanceledOnTouchOutside に関わる観察のみ「常に無効」に読み替える)。

#### Scenario: [LD-AT-01] placement 引数で既定ローディングの配置が変わる
- **GIVEN** 既定値と異なる配置・オフセットを持つ placement
- **WHEN** placement 引数付きで既定ローディングを表示する
- **THEN** 表示位置がレイアウト規則どおりに変わる

#### Scenario: [LD-AT-02] カスタム View の添付属性が Dialog と同じ優先順位で効く
- **GIVEN** placement を添付したカスタム Loading View
- **WHEN** 添付のみで表示した場合と、表示 API の placement 引数付きで表示した場合
- **THEN** 添付のみでは添付値が、引数付きでは引数値が (オブジェクトまるごと置換で) 採用される

#### Scenario: [LD-AT-03] 外側タップで閉じず、背後にも透過しない
- **GIVEN** isCanceledOnTouchOutside を真に添付したカスタム Loading View の表示
- **WHEN** 表示の外側をタップする
- **THEN** 表示は閉じず、背後の画面にもタップが届かない

#### Scenario: [LD-AT-04] ダイアログ表示中の Loading は最前面で入力を遮る
- **GIVEN** ダイアログを表示中の画面
- **WHEN** Loading を開始する
- **THEN** Loading がダイアログより手前に表示され、ダイアログへのタップも遮られる (実提示での検証 — 両 OS)

#### Scenario: [LD-AT-05] 設定プロパティの options 変更が次の表示から効く
- **GIVEN** overlayColor を変更した DialogOptions を Loading の設定プロパティへ設定した状態
- **WHEN** 既定ローディングを表示する
- **THEN** 変更後の overlayColor で覆いが描かれる (isCanceledOnTouchOutside を設定しても外側タップは無効のまま)

#### Scenario: [LD-WN-01] 画面の変化をまたいで表示が継続し再配置される
- **GIVEN** 走行中の処理を持つ Loading の表示
- **WHEN** 画面を回転する (Android では Activity の再生成を伴う)
- **THEN** 表示は継続し、凍結済みの実効値と新しい寸法から導いた位置・サイズに再配置され、処理の完了で表示が消える

### Requirement: 進捗通知

スコープ形の action は進捗報告口を受け取る (SHALL)。報告口の形は形態別イディオム (C# = IProgress&lt;double&gt; / Swift = クロージャ / Kotlin・KMP = 関数型) とし、意味は全形態で同一: 値は 0〜1 (範囲外はクランプ、非有限は無視)、表示は最新の報告が勝つ (合流中も同様。「最新」は状態直列化の受理順)。報告口は任意スレッドから呼べるが、VM の進捗受け口とフォーマット関数の呼び出しは UI スレッド上で行われる。既定ローディング表示中の報告は、スタイルのフォーマット関数の結果を表示テキストにする。カスタム View 表示中の報告は、VM が進捗受け口 interface を実装している場合にのみ VM へ転送する (未実装なら転送せず、エラーにもしない)。

#### Scenario: [LD-PR-01] 進捗報告で既定ローディングの表示が更新される
- **GIVEN** メッセージ付きで開始したスコープ形の処理
- **WHEN** 処理が進捗を報告する
- **THEN** 表示テキストがフォーマット関数 (メッセージ, 進捗値) の結果に更新される

#### Scenario: [LD-PR-02] 未報告のあいだはメッセージのみが表示される
- **GIVEN** メッセージ付きで開始したスコープ形の処理
- **WHEN** 進捗を報告しない
- **THEN** 表示テキストはフォーマット関数 (メッセージ, 進捗なし) の結果 (既定実装ではメッセージのみ) である

#### Scenario: [LD-PR-03] 合流中は最新の報告が表示される
- **GIVEN** 合流中の2つのスコープ形の処理
- **WHEN** 両方の処理が交互に進捗を報告する
- **THEN** 表示は常に最後に報告された値を反映する

#### Scenario: [LD-PR-04] 範囲外・非有限の報告値の扱い
- **GIVEN** 表示中のスコープ形の処理
- **WHEN** 1 を超える値・負の値・非有限値 (NaN / 無限大) を報告する
- **THEN** 1 超は 1、負は 0 にクランプして表示され、非有限値の報告は無視され直前の表示が保たれる

#### Scenario: [LD-PR-05] 進捗受け口を実装した VM のカスタム View に進捗が転送される
- **GIVEN** 進捗受け口 interface を実装した VM で登録・表示したカスタム Loading
- **WHEN** スコープ形の処理が進捗を報告する
- **THEN** VM の受け口が同じ値 (クランプ後) で呼ばれる

#### Scenario: [LD-PR-06] 受け口未実装の VM では転送されない
- **GIVEN** 進捗受け口 interface を実装しない VM で登録・表示したカスタム Loading
- **WHEN** スコープ形の処理が進捗を報告する
- **THEN** 何も起こらない (エラーにならず、処理は続行する)

### Requirement: 既定ローディングのスタイル

既定ローディングのスタイル (インジケータ色・メッセージのフォントサイズと色・既定メッセージ・進捗フォーマット関数) は、1つのスタイル値オブジェクトをシングルトンの設定プロパティへ一括設定する口のみで受け付ける (SHALL — core/ADR-0023)。表示 API にスタイル引数は設けない。器はスタイルを各表示の開始時に読み、設定変更は次の表示から効く (表示中の変更は現在の表示に影響しない)。メッセージ未指定の表示では既定メッセージ (defaultMessage 相当) を用いる。進捗フォーマットは関数 `(メッセージ, 進捗値?) → 表示テキスト` とし、ライブラリが既定実装を持つ。

#### Scenario: [LD-ST-01] スタイル変更は次の表示から効く
- **GIVEN** 表示中の既定ローディング
- **WHEN** スタイルを変更し、表示を閉じてから再表示する
- **THEN** 表示中の見た目は変わらず、再表示から変更後のスタイルが観察できる

#### Scenario: [LD-ST-02] メッセージ未指定なら既定メッセージが表示される
- **GIVEN** defaultMessage を設定したスタイル
- **WHEN** メッセージを省略して表示する
- **THEN** 既定メッセージが表示される

#### Scenario: [LD-ST-03] フォーマット関数の差し替えが進捗表示に反映される
- **GIVEN** 独自のフォーマット関数を設定したスタイル
- **WHEN** スコープ形の処理が進捗を報告する
- **THEN** 表示テキストが差し替えた関数の戻り値になる

### Requirement: カスタム View 版の登録と表示

Loading 用のレジストリを Dialog のレジストリと独立に持つ (SHALL — design Decision 3)。登録は VM 型キー → View factory で、従来 View 系 / 宣言的 UI 系の技術別オーバーロード (core/ADR-0011 と同型、結果報告口なし) を持ち、再登録は後勝ち。表示は登録済み VM のインスタンス渡しと、登録せずその場で表示するインライン factory 版を持つ。インライン表示はレジストリを変更しない (core/ADR-0013 と同型)。View は表示のたびに生成する使い捨てとする (core/ADR-0005)。未登録の VM 型の表示は構成ミスとして失敗する。VM 契約は Dialog と同じ参照型 (class) 限定。

#### Scenario: [LD-CV-01] 登録済み VM でカスタム Loading が表示される
- **GIVEN** 従来 View 系の factory で登録した VM 型
- **WHEN** その VM のインスタンスを渡して Loading を表示する
- **THEN** factory が生成した View が Loading として表示され、hide で消える

#### Scenario: [LD-CV-02] 宣言的 UI 系の登録でも同じに働く
- **GIVEN** 宣言的 UI 系 (SwiftUI / Compose) の factory で登録した VM 型
- **WHEN** その VM のインスタンスを渡して Loading を表示する
- **THEN** 従来 View 系と同じ観察可能挙動 (表示・進捗転送・hide) になる

#### Scenario: [LD-CV-03] インライン factory 表示はレジストリを変えない
- **GIVEN** 登録済みの VM 型
- **WHEN** 同じ VM 型を別の View を返すインライン factory で表示し、閉じた後に通常の表示を行う
- **THEN** インライン表示にはインラインの View が使われ、その後の通常表示には登録済み factory の View が使われる

#### Scenario: [LD-CV-04] 未登録 VM の表示は構成ミスとして失敗し action は実行されない
- **GIVEN** Loading レジストリに登録のない VM 型
- **WHEN** その VM のインスタンスを渡して表示 (またはスコープ形 start) を呼ぶ
- **THEN** 構成ミスとして失敗し (表示されない)、start の場合は action が実行されない (失敗モデルの fail-fast)

#### Scenario: [LD-CV-05] Dialog と Loading のレジストリは独立している
- **GIVEN** 同じ VM 型を Dialog と Loading の両レジストリに (異なる View で) 登録した構成
- **WHEN** Loading 側だけを別の View factory で再登録し、Dialog の show と Loading の表示をそれぞれ行う
- **THEN** Dialog には Dialog レジストリの View が、Loading には再登録後の View が使われる (片方の再登録が他方に影響しない)

#### Scenario: [LD-CV-06] View は表示のたびに生成される
- **GIVEN** 生成回数を観測できる factory で登録した VM 型
- **WHEN** 同じ VM インスタンスで表示 → hide を2回繰り返す
- **THEN** factory は2回呼ばれ、毎回新しい View が使われる

### Requirement: 出入りの演出

カスタム Loading View は Dialog と同じ演出の添付スロット (`DialogTransition`) で出入りの演出を差し替えられる (SHALL — core/ADR-0017 の適用)。フックの形 (ホスト View を受け取る統一形・完了通知つき) とプリセット・不成立時の扱いは Dialog と同一。演出未添付のカスタム View と既定ローディングは、ライブラリ既定のトランジションで出入りし、覆いはフックによらず別レイヤで常時フェードする。既定ローディングに演出を差し替える口はない。Dialog の「結果のラッチと配送」に相当する規則は、結果を持たない Loading には適用しない。

#### Scenario: [LD-TR-01] カスタム View の添付演出フックが実行される
- **GIVEN** 実行を観測できる演出フックを添付したカスタム Loading View
- **WHEN** 表示してから hide する
- **THEN** 入りのフックが表示時に、出のフックが hide 時に、それぞれホスト View を受けて実行され、出のフックの完了後に View が撤去される

#### Scenario: [LD-TR-02] 未添付なら既定のトランジションで出入りする
- **GIVEN** 演出を添付しないカスタム Loading View と既定ローディング
- **WHEN** それぞれ表示してから閉じる
