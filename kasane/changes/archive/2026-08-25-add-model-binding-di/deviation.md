# Deviation: add-model-binding-di

- design Decision 4 (型指定 show の Swift シグネチャ): design では configure は `(@MainActor (VM) async -> Void)?` → 実装では `async throws` クロージャ。理由: dialog-contract の MB-TS-05 (configure の例外は提示に進まず呼び出し元へ伝播) を Swift の非 throwing クロージャでは表現できないため。design 自体が「シグネチャの形は spec 化仮」と明記しており、spec の Requirement を優先した実装裁量 (2026-08-25)
- design Decision 3 (VM factory 登録の Kotlin API 名): design では「`register(VM 型, viewModel: factory)` 相当」→ 実装では `registerViewModel(KClass) { VM }` の別名。理由: Kotlin では引数を書かないラムダが arity 0/1 の両方に適合し `register` のオーバーロード解決が壊れるため。同じ理由で別名にした既存の先例 (`registerCompose`) に倣った。iOS の `register(_:viewModel:)` と名前が非対称になる (2026-08-25)
- Android 既存テスト (DialogRegistryTests): 「同一 VM インスタンスの再 show は独立した重ね出しになる」テストは MB-NI-04 と矛盾するため、別インスタンスでの重ね出し検証へ書き換え (iOS 側と同型の判断) (2026-08-25)
- tasks 4.2 (MB-KM-01・MB-KM-04 のテスト置き場): tasks では「iosTest / interop 検証」→ 実装は Swift 側テスト (`ios/Tests/KsDialogsTests/KsDialogsKmpModelBindingTests.swift`)。理由: Swift のジェネリック公開面 (`KsDialogsKmp`) は ObjC 面に出ず Kotlin 側 iosTest から呼べない。共有コードからの show は互換面経由で再現し、Kotlin 実インスタンスの形 (ObjC クラス) も専用 VM 型で押さえた (既存 KMP facade テストと同じ流儀) (2026-08-25)
- tasks 4.2 (MB-KM-02 の自動化の深さ): androidHostTest は提示先の差し替え手段を持たない (Android Native の提示面が internal) ため、「報告結果が show 呼び出し元へ届く」部分は Native 側の同名契約テストと Sample 通し (tasks 5.4〜5.5) に委ねる。完全自動化には KMP モジュールへの instrumented テスト源セット追加が必要で、本変更ではスコープ外とする (2026-08-25)
- ui/brief.md「画面と状態」(Model Dialog 行の遷移記号 `›` なし): 実装は `›` あり。理由: Basic Dialog を含む既存メニュー行はすべて `›` を表示しており、sample-parity 規約も `›` を4ルート一致で課している。同じ文の「既存行と同じ行デザイン」「Basic Dialog 等と同じ扱い」を優先した。オーナー判断 2026-08-25 で `›` ありを承認済み (2026-08-25)
- tasks 5.5 (MAUI ルートの通し確認): MAUI は Android 面のみで通し・視覚照合を実施。iOS 面は環境制約 (.NET for iOS 26.1.10502 が Xcode 26.1 を要求、現行環境は Xcode 26.5) でビルド不可のため未実施と証跡に明記 (2026-08-25)
- [付随修正] Samples の README 群 (samples/README.md と4ルートの README) へのデモ項目行・ファイル表の追随: sample-parity 規約が README を写像と定めるための必然的追随 (2026-08-25)
- [付随修正] kmp-facade のテストダミー (`kmp/ksdialogs-kmp/src/androidHostTest/kotlin/jp/kamusoft/ksdialogs/kmp/AndroidDialogGatewayContractTests.kt` の `RecordingNativeDialogs`): Android Native の公開面変更 (型指定 show 追加) への不可避のビルド追随。既存ダミーと同じ形で `UnsupportedOperationException` を投げる override を追加 (テストのみ・1ファイル) (2026-08-25)
- design Decision 3 (VM factory 登録の C# API 名): design の「register 相当」→ 実装は `RegisterViewModel<TVm>` / `RegisterViewModel<TVm, TResult>`。理由: `Register` への0引数ラムダのオーバーロード追加は補完・解決が読みにくくなるため、Kotlin 側の同名判断 (`registerViewModel`) に揃えた (2026-08-25)
- maui-binding spec (1行登録): spec は `RegisterForDialog<TView, TViewModel>()` のみ → 実装はカスタム結果型向けに `RegisterForDialog<TView, TViewModel, TResult>()` を対で追加。理由: C# では「何らかの `IDialogViewModel<>` 実装」という制約が書けず、既存 `Register` と同じ2形分岐が必要なため。非破壊の追加 (2026-08-25)
- maui-binding spec (Requirement 文言「notifier 取得のジェネリック制約には class を含め」): `vm.Notifier` 拡張プロパティの受け手には class 制約を付けていない。理由: 受け手に `class` 制約を付けると `TResult` が推論できず拡張プロパティとして書けない。値型 VM の拒否は登録と型指定 show の class 制約で成立し、Scenario MB-MA-02 の拒否対象 (struct VM の登録・型指定 show) は満たす。Kotlin の拡張プロパティも value class 検査を持たない同じ構図 (2026-08-25)。※その後のオーナー裁定で実行時検査も追加 (下記「maui-binding spec (値型 VM の拒否点)」参照)
- maui-binding MB-MA-07 (fallback も解決できない場合の失敗タイミング): 失敗は View factory 実行時 (提示処理に入った直後・View 生成前) に発生する。fallback は呼ばないと解決可否が分からないため。観察可能な挙動 (View 未生成・結果に化けず `ViewFactoryNotRegistered` で失敗) は spec どおり (2026-08-25)
- MAUI 既存テスト (DialogRegistryTests): 「同一 VM インスタンスの再 show は独立した重ね出し」テストを MB-NI-04 との矛盾により別インスタンス検証へ書き換え (iOS / Android と同型の判断) (2026-08-25)
- [付随修正] `scripts/scenario-id-coverage.py` の `DEFAULT_ALLOW_MISSING` に MB-SM-01〜03 を理由付きで追加: Sample デモ項目の Scenario は自動テストを持たず実機証跡で受け入れる既存 PB-SM-01〜03 の先例踏襲。実機証跡は evidence/ に4ルート分取得済み (2026-08-25)
- [付随修正] `scripts/scenario-id-coverage.py` の `DEFAULT_TEST_GLOBS` に `maui/*ApiSurfaceCheck` を追加 (下記 android / kmp 分と同じ理由。MB-MA-01/02 の偽の未網羅を防ぐ) (2026-08-25)
- [付随修正] `scripts/scenario-id-coverage.py` の `DEFAULT_TEST_GLOBS` に `android/api-surface-check/src` と `kmp/api-surface-check/src` を追加: テスト実行規約は公開 API 形状検査を api-surface-check モジュールに置くと定めるのに、網羅検査の既定走査先がそこを見ず MB-AN-01 / MB-KM-01 (compile 検査系 Scenario) が偽の「未網羅」になるため。cross 能力のツールだが本変更の横断検証 (task 6.1) の成立に必要な2行追加 (2026-08-25)
- android-native spec (value class 拒否の入口): spec は拒否点を「登録および型指定 show」の2点と記述 → 実装 (レビュー修正サイクル) は共通提示入口での検査に統一し全 show 経路 (インライン factory show・レジストリ経由のインスタンス渡し show を含む) に拡大。理由: dialog-contract / core/ADR-0018 の参照型限定は契約全体に及び、インライン経路の迂回はサイドテーブルの同一性保証を崩すため (review-001 突き合わせの確定 Major への修正)。付随して、レジストリ経由 show に value class を渡した場合の失敗種別が `ViewFactoryNotRegistered` から `ValueClassViewModel` に変わった (参照型限定の失敗が先に立つ順序) (2026-08-25)
- iOS 既存テスト (DialogRegistryTests): 「同一 VM インスタンスの再 show は独立した重ね出しになる」テストは MB-NI-04 (同一 VM インスタンスの並行 show は構成ミス失敗) と矛盾するため、別インスタンスでの重ね出し検証 (`distinctInstancesOfSameViewModelTypeAreShownAsIndependentStack`) へ書き換え。同一インスタンスの挙動は MB-NI-04 のテストが引き継ぐ (2026-08-25)
- maui-binding spec (値型 VM の拒否点): spec は「ジェネリック制約に class を含め、値型 VM をコンパイル時に拒否する」と記述 → 実装は共通提示入口 (`maui/KsDialogs.Maui/Internals/DialogPresenter.cs`) の実行時検査も追加し全 show 経路 (インスタンス渡し・インライン factory・型指定) に拡大。理由: インスタンス渡し `ShowAsync` は interface 受けで class 制約が書けず、View fallback 構成下で struct VM が提示まで到達しうるため、Android の同型修正 (全経路の実行時検査) と対称化する — オーナー裁定 2026-08-25。付随して `DialogException.ValueTypeViewModel` を公開面に追加し、fallback 未設定でのインスタンス渡し show に値型 VM を渡した場合の失敗種別が `ViewFactoryNotRegistered` から `ValueTypeViewModel` に変わった (Android の `ValueClassViewModel` と対称。例外名は各言語の語彙 — Kotlin: value class / C#: 値型 — に合わせた非対称) (2026-08-25)
