# Exploration: add-sample-capture-automation

## 課題 / 動機

Sample の撮影証跡 (視覚照合・4ルート通し) の収集が実装フェーズの最大コストになっている。add-loading の実測では Samples フェーズ約 139 分の大半が「6アプリのビルド+デプロイ」「撮影用の一時改変 (刻み間隔延長・デモ先出し) の出し入れと復元確認」「状態を作る手動タップの再現」で、撮影そのものではなかった。一時改変の復元では実装の巻き戻し事故も発生している (lessons/inbox の verification-temp-edit-restore-by-copy-not-checkout)。

対策の方向 (2本セット):

1. **Sample のデモ駆動モード**: 起動引数 (iOS = launch argument / Android = intent extra 等) で「進捗の刻み間隔を延長」「起動直後に指定デモを自動再生」を Sample 自体が受け付ける。撮影用の一時改変を構造的に不要にする
2. **撮影手順のスクリプト化**: ルート別の「デプロイ → 操作列 → 連続撮影 → 保存」を `scripts/` に落とす (現状は `kasane/config.yaml` の `ui.screenshot` に手順メモがあるだけで、ワーカーが毎回手順を再構築している)

## 検討した選択肢

- 証跡粒度の軽量化 (代表ルートのみフル撮影) は別軸の検証ポリシー判断として本 change には含めない
- 撮影フェーズの並列化 (orchestrator.parallel) も別軸 (Gradle 並行実行の罠の回避設計が前提) として含めない

## 決定事項

- デモ駆動モードと撮影スクリプト化の2本セットを1 change として扱う (2026-08-27)。スクリプト化だけでは一時改変の出し入れが残り、デモ駆動モードだけでは手順の再構築コストが残る補完関係のため
- デモ駆動モードの受け口は起動時の引数渡し (iOS = launch argument / Android = intent extra) とする (2026-08-27)。再ビルドなしで撮影ごとに指定を変えられ、撮影コマンド (simctl launch / adb am start --es) がそのまま引数を運べるため。却下: 環境変数 (Android でアプリへ渡す標準手段がなくパリティ不成立)、ビルドフラグ (指定変更のたびに再ビルドとなり change の目的と衝突)。MAUI も NSProcessInfo / Intent extra で同じ意味論で受けられることを確認済み
- 自動再生デモの指定キーは安定 ID (kebab-case、例 `basic-dialog`) を9デモぶん新設し、4ルートが各自同じ値を書く (2026-08-27)。表示文言とキーを独立させ、文言修正でスクリプトが静かに壊れる事故を防ぐ。却下: メニュー文言をキーに流用 (文言変更 = スクリプト全修正、スペースを含み引用符も要る)。ルート間でキー定義を共有しないのはパリティ規約の既存流儀どおり
- デモ駆動モードは Release 構成から除外せず全ビルド構成で有効とする (2026-08-27)。Sample は配布製品でなく守る対象がない一方、除外は4ルート × 2構成の条件コンパイルを散らせる。一般公開後は利用者の検証機能としても価値がある。引数を渡さない通常起動の挙動は不変が前提
- 撮影スクリプトは `scripts/capture/` 配下に単一の入口スクリプトを置き、「ルート + デモ」を引数で指定する形とする (2026-08-27)。形式は既存 scripts/ の流儀 (Python + 先頭 docstring が使い方の正) に合わせる。simctl / adb の差・デバイス解決・保存規約はスクリプト内側に隠し、ワーカーが覚えるのは1コマンドだけにする。却下: ルート別独立スクリプト (手順再構築の再発 + 共通処理が6箇所に重複)。内部分割は propose で詳細化。パリティ規約の「ルート間コード共有禁止」は Sample アプリコードの話で、リポジトリ側ツールには適用されない
- 座標タップは許容する (2026-08-27)。ただし操作列はスクリプト側の宣言的なデータ定義に集約し、前提とする標準撮影デバイスを docstring に明記する。デモ自動再生の担当は「起動〜表示まで」とし、表示後の少数タップ (結果確定等) がスクリプトの操作列に残る。却下: 座標全廃 (Sample に撮影用シーケンサを作り込むことになり公開デモアプリが汚れる)、文言検索タップ (iOS シミュレータに標準手段がなくパリティ不成立)
- ドキュメント追随3点を本 change に含める (2026-08-27): ① config.yaml `ui.screenshot` は手順の書き写しをやめ「入口スクリプトの docstring が正」へのポインタ + スクリプトで賄えない周辺知識のみに縮約、② sample-parity.md に「撮影支援機構 (画面に出ない・引数なしなら挙動不変) はデモ項目の一致要件の枠外」の扱いを追記、③ samples/README.md に起動引数の説明を反映。却下: ドキュメント後続 change 化 (旧手順メモと新スクリプトの並存でドリフトが始まる)

## 調査所見 (2026-08-27 ksn-scout)

- 起動引数を読む箇所は6アプリとも現状ゼロ。受け口は新設。Android は両ルートともランチャー Activity が exported 済みで `adb shell am start --es` がそのまま通る。MAUI iOS は `Platforms/iOS/Program.cs` が引数を素通し済み
- KMP のデモ起動ロジックは共有 Presenter (`samples/kmp/shared/.../SamplePresenter.kt`) にほぼ集約済み。引数解析だけ各 OS 側で行い、結果を共有の設定型で Presenter に渡す構成が自然。例外は Inline Dialog のみ (プラットフォーム固有 API のため各側に残る)
- デモは9件で、識別 ID は存在せず文言対応のみ (`SampleText` 定数)。→ 安定 ID 新設の決定につながった
- Loading の刻み間隔は4ルートとも 400ms のハードコード (KMP は共有側1箇所、他3ルート各1箇所、計4箇所)。可変化が必要
- `scripts/` は lint / 検査系のみでビルド・デプロイ・撮影の自動化は皆無。`scenario-id-coverage.py` が「先頭 docstring が使い方の正」形式の前例
