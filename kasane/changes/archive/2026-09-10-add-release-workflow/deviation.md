# Deviation: add-release-workflow

- [付随修正] `maui/KsDialogs.Maui/Platforms/iOS/PlatformDialogContent.cs`: 非公開の入れ子クラス `DialogContentView` の型宣言に付いていたコンストラクタ引数の `<param>` タグをコンストラクタへ移動。3.1 で facade の XML ドキュメント生成を有効にして初めて表に出た警告 (CS1572、2 件) の解消で、公開面・挙動には触れない (2026-09-10)
- maui-nuget-distribution / Scenario「XML ドキュメントは facade の 3 TFM に揃う」: spec では「binding 2 件の nupkg には `.xml` が無い」 → 指示により **Android binding の `.xml` は残ることを受け入れる** (iOS binding には無い。facade の 3 TFM と binding 2 件の csproj への `GenerateDocumentationFile` の明示は spec どおり)。理由: .NET Android の binding 用ビルド定義 (`Xamarin.Android.Bindings.Core.targets`) が csproj の `false` の後に `DocumentationFile` を設定し直すため csproj からは止められず、残る `.xml` は Resource designer クラスの説明だけの 389 バイトで利用者に害が無い。KsSettingsView も同じ状態で 2 回リリース済み (対処なし)。SDK 内部の target に依存する除去や Resource designer の停止 (代替案 B / C) は仕掛けと影響が大きいため却下 (`evidence/maui-xml-doc-pack.txt`、オーナー判断 2026-09-10)
- [実装判断] design Decision 4「`develop` を別ディレクトリへ `--depth 1` で clone して置換」 → 実装では `git worktree add --detach origin/develop` で別ディレクトリを作る。理由: 別 clone には checkout action が local config に置いた push 資格情報が付かず token を URL に埋める必要が出るため、資格情報の扱いを checkout action に閉じる。spec (Requirement: README と Skill の version 置換) の「`develop` の先端で置換し commit して push」は満たす (2026-09-10)
- [実装判断] spec (maui-nuget-distribution / Requirement: 発行版の nupkg 名の検査)「nuget.org への push 直前」の 2 回目の検査 → publish job では artifact の download 直後 (SPM commit push より前) に置く。理由: 取り消せない操作 (配信リポジトリへの push) より前に取り違えを止める。push より前である点は満たす。レビューで「直前」の字面を優先すべきと判断されれば push step の直前へ移す (2026-09-10)
- [実装判断] spec (release-workflow / Requirement: 同じ version での再実行)「monorepo の tag が起動 commit にあれば完了済みとして全ステップを skip する」 → skip するのはレジストリと配信リポジトリへの publish (SPM commit / tag、Maven upload / release、NuGet push、monorepo tag) に限り、tag 以降の冪等 step (GitHub Release は既存なら触らない・`develop` への README / Skill 置換) は再実行でも走らせる。理由: tag push の直後に Release 作成が失敗した run を再実行すると Release が無いまま緑になる (second-opinion-code-001 Major)。spec の意図 (重複 publish の禁止) は保つ (2026-09-10)
- release-workflow / Requirement「Maven Central の 2 枠の deployment」の「Android → KMP の順で行い、公開 (PUBLISHED) を待つ」「PUBLISHING なら PUBLISHED になるまで待って release を skip」 → 初回リリース (`0.1.0-beta.1`) で Android 枠の公開待ちが上限 30 分に達して失敗した (Central の同期は Android 枠 約 60 分 / KMP 枠 27 分) ため、後続の S 級 change fix-release-published-wait で、release 要求は Android → KMP の順のまま、公開待ちを 2 枠まとめて 1 本 (上限 90 分) にし、再実行で引き継ぐ PUBLISHING の枠もその step で待つ形へ変えた。spec の当該文は「要求の順序」と「PUBLISHING の枠は release を送り直さず公開の完了を待つ」の動作の指定として読む。記録の本体は同 change の deviation.md (蒸留時の追記 2026-09-10)
