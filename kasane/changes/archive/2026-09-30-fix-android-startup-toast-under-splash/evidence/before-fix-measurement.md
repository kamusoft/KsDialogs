# 直す前の実測 (fix-android-startup-toast-under-splash、tasks 1.1〜1.4)

直す前のライブラリに、Android 系 3 ルートの待ちを外した Sample (tasks 6.1 を済ませた作業ツリー) を載せて撮った。直した後 (tasks 7.1) は、この文書の「測り方」を同じ端末・同じ手順でなぞる。

## 環境

- Android エミュレータ: この change のために新しく作った API 36 (google_apis、arm64-v8a、pixel_7 の定義、1080x2400)。グループ 7 で再利用するので、まだ削除していない。起動は `-no-snapshot -no-boot-anim -no-audio`
- iOS Simulator: iPhone Air / iOS 26.5 を新しく作った (tasks 1.1)。tasks 1.3 の観測 (下記) に使い、グループ 7 で再利用するので、まだ削除していない
- Sample: `samples/android` (以下 android)、`samples/kmp/androidApp` (以下 kmp)、`samples/maui` の Android (以下 MAUI)。3 つとも Debug ビルド。MAUI は `EmbedAssembliesIntoApk=true`
- ライブラリ: この change の実装前 (提示先は resumed な Activity、Toast は受理の時点から数える)
- Sample: 自動再生を最初の画面の表示時の処理から直接呼ぶ版 (android・kmp は `onCreate`、MAUI は `OnAppearing`。最初の描画の後や次の周回へ回す処理を外した)
- 表示時間: default-toast は内蔵既定の 1500 ms。custom-toast は登録経路 (「カスタムトースト」) が 3000 ms、インライン経路 (「インライントースト」) が 2000 ms
- 各 Sample を 1 回ずつ起動してから撮った (作成直後の初回起動の遅さを除くため。数えていない)
- Mac の負荷: load average は Toast の録画の間 8.7〜13.2、Dialog・Loading の撮影の直前は 6.5

## 起動の手順

- コールド起動: `am force-stop <package>` → 1.5 秒待つ → `am start -n <package>/<activity> --es demo <デモID> --es loading-step-interval-ms 5000`
- プロセスが残ったままの再起動: `am force-stop` → 1.5 秒待つ → 引数なしで `am start -W` (最初の画面が出るまで待つ) → 3 秒待つ → `am start --activity-clear-task -n <package>/<activity> --es demo <デモID> ...`。タスクを片付けて Activity を作り直させる形で、プロセスは残る (起動の前後で `pidof` の値が同じことを毎回確かめた)
  - 戻る操作で Activity を閉じる形は使えなかった。Android 12 以降は、ランチャーから開いた根の Activity で戻ると、Activity を破棄せずにタスクを背面へ移すため、次の `am start` で Activity が作り直されない
- 落ちたかどうか: 最後に `pidof` でプロセスが残っていること、crash バッファが空であることを見た

## 測り方 (Toast)

1. 録画: `adb shell screenrecord --time-limit <秒>` を始めてから 1.2 秒後に起動のコマンドを出す。録画の長さは android・kmp が 13 秒、MAUI が 22 秒 (MAUI の 1 回は 40 秒で撮り直した。下記)
2. コマの取り出し: macOS 標準の AVFoundation (AVAssetReader) で全コマを読み、コマの表示時刻 (presentation timestamp) と、縦横 1/4 に間引いた画素 (270x600) を取り出す。screenrecord は画面が変わったときだけコマを出すので、コマの表示時刻は「画面が変わった時刻」として読める
3. 基準のコマ: 録画の最後のコマ (Toast が消えた後のメニュー画面)。最後のコマがメニュー画面で、Toast が写っていないことを、全回で確かめた (上半分の平均色と、下半分の画素の差)
4. 画素の差: RGB の各成分の差の最大が 10 を超える画素を「違う」とする (静止した画面どうしでは、動画の圧縮による差はこの閾値で 0 になった)
5. 起動画面が退いたコマ: 画面 (上端 200 px のステータスバーと、下端 80 px のジェスチャーの帯を除く) のうち、Toast の帯 (次項) を除いた部分で違う画素が 40 以下になり、以降のコマでもずっとそのままであった最初のコマ。**起動画面の退場の演出 (フェード) が終わり切ったコマ**であり、演出の途中で Toast が見え始めていた分は数えない (見えている時間を短めに測る側)
   - MAUI は、起動画面の青が退いた後に、薄い青の名残が 0.2〜0.5 秒ほど画面全体に残る。この名残が消えたコマを退いたコマとした
   - 補い (オーナー判断 2026-09-30、deviation.md): 画面の上半分 (行 50〜300) が基準のコマと一致するコマに挟まれた、3 コマ以下の不一致は無視する (一致とみなす)。Toast の帯を決めるときも、そのコマは使わない。Toast が見えているかの判定では、そのコマは前後のコマがどちらも見えているときだけ見えているとみなす。実機の録画で、Toast が消えた直後の 2〜3 コマだけ色がわずかに揺れる回があり、それを「退いていない」と読んでしまったための補い。この定義を当て直しても、直す前の実測とエミュレータの 2 回分の値は 1 つも変わらない (確かめた)
6. Toast の帯: 起動画面が退いたコマ以降に、画面の下半分で違う画素が出た行を、4 行 (元の画素で 16 px) までの隙間を許してまとめたもの。帯ごとに 1 枚の Toast とみなした。custom-toast は、上の帯 (元の画素で縦 1804〜1916 px 付近) が登録経路、下の帯 (2020〜2124 px 付近) がインライン経路 (Sample が下寄せにずらして出す)。2 枚は動かずに独立して消えることを、コマの一覧で確かめた
7. Toast が見えている: 帯の中で違う画素が 30 を超えるコマ (フェードイン・フェードアウトの途中の薄いコマも含む)
8. 見えている時間: 「起動画面が退いたコマ」と「Toast が最初に見えたコマ」の遅い方の時刻から、「Toast が消えたコマ」(最後に見えたコマの次のコマ) の時刻まで。比は、見えている時間 / 表示時間
   - **合格ライン (表示時間の 2/3 以上) の判定は、この定義で行う** (オーナー判断。deviation.md)。起点は起動画面の退場のフェードが終わり切ったコマ (それより後に Toast が見え始めたときはそのコマ) で、フェードの途中で見えている時間は数えない。直した後 (tasks 7.1・7.4) も同じ定義で測る
9. 判定の確かめ: 数値の出た回のうち、短い回・0 の回・custom-toast のコマの一覧を目で見て、数値の区間と画面の変化が合っていることを確かめた

### 撮り直した回

- MAUI の default-toast の 1 回目は、最初の描画まで 18.3 秒かかり、22 秒の録画の最後のコマが起動画面のままだった (基準のコマが作れない)。この回は捨て、40 秒の録画で撮り直した回を 1 回目とした
- Dialog・Loading を最初に録画で撮った 18 回は、7 回で録画が最初の描画より前に止まっていた (最後のコマが起動画面か、前のアプリの画面)。録画をやめ、Dialog・Loading は下の手順で 18 回すべて撮り直した

### 読み取れること

- 3 ルートとも、待ちを外すと Toast の見えている時間が表示時間の 2/3 に届かない回が多い。合格ライン (core/ADR-0044 の Revisit When) を全回で満たすデモは無い
- MAUI が最も短い。default-toast は 5 回中 2 回、起動画面が退いた後の画面に一度も写らなかった。その 2 回は、起動画面の退場の演出 (青が薄くなる途中) の下に「Hello Toast!」が写り、名残が消えたコマで消えていた (`before-maui-default-toast-under-fade.png`)。custom-toast のインライン経路も 2 回、退いた後に写らなかった
- MAUI の custom-toast の登録経路は、起動画面が退いてから 0.28〜0.78 秒遅れて写り始めた。他のルートと違い、退場の演出の最中には写っていない
- android の default-toast のプロセスが残ったままの 1 回目は、最初の描画まで 2.4 秒かかった回で、退いた後はフェードアウトの途中の 1 コマ (128 ms) だけ写った
- 表示時間が長いほど比は高い (登録経路 3000 ms > インライン経路 2000 ms > 既定 1500 ms)。受理から起動画面の退場までの一定の時間が、表示時間から引かれている形である
- Dialog・Loading は全回で出た

## 対象外とした場面

### kmp・MAUI のプロセスが残ったままの再起動 (tasks 1.2 の一部)

対象外とした理由は deviation.md を参照 (オーナー判断で測る対象から外した)。


kmp と MAUI の Sample は、自動再生の取り出しを「プロセスの起動につき 1 回だけ」にしている (`SampleCaptureAutoPlay`。引数なしの起動でも取り出しを消費する)。プロセスが残ったまま Activity を作り直させても自動再生が起きない。1 回ずつ試し、録画に Toast が一度も写らないことを確かめた (default-toast。kmp は `Displayed` 0.5 秒、MAUI は 2.8 秒で、メニューだけが出た)。

android は、引数なしの起動では取り出しを消費しない作りなので撮れた。Sample に手を入れずに kmp・MAUI のこの場面を作る手段が無いので、この 2 ルートのプロセスが残ったままの再起動は撮っていない。

## iOS: 割り込みの最中に受け付けた Toast (tasks 1.3)

### 場面の作り方 (一時変更)

iOS 系 3 ルートの Sample は、どれもシステムの許可ダイアログを出す処理を持たない。そこでオーナー判断 (deviation.md) に従い、`samples/ios` の 1 ルートだけに一時変更を入れて撮った。ライブラリ (`ios/` 配下) には手を入れていない。

- 一時変更の対象: `samples/ios/KsDialogsSample/KsDialogsSampleApp.swift` だけ
- 一時変更の要点 (App の初期化に足した):
  - 通知の許可を求め、許可ダイアログを出す
  - シーンが非アクティブになる通知 (許可ダイアログの出現) の 0.5 秒後に、既定の Toast (`Toast.shared.show(message:)`、表示時間は内蔵既定の 1500 ms) を 1 回だけ出す
  - 起動からの経過ミリ秒を付けて、診断出力を標準エラーへ書く (初期化・シーンの非アクティブ化とアクティブ化・Toast の呼び出し・許可の結果)
- 自動再生の引数は渡さずに起動した (Toast は上の一時変更からだけ出る)
- 戻したこと: 撮影の後に、変更前に退避したファイルで上書きして戻した
- 一致の確認: 変更前と戻した後の SHA-256 が一致した。`git diff` もこのファイルに差分が無い
- 注意: 手元の DerivedData にある Sample の .app は一時変更を積んだビルドのまま (追跡外)。グループ 7 で ios ルートを撮る前にビルドし直す

### 手順

- 端末: tasks 1.1 で作った iPhone Air / iOS 26.5
- 各回とも、Simulator を shutdown / boot してから Sample を消して入れ直し、許可の状態を初期化してから起動した (`simctl uninstall`・`simctl privacy reset all`・`simctl install`)。handbook cross/runtime-behavior-verification の「iOS Simulator でシーンの状態を観測するとき」のとおり
- 録画: `simctl io recordVideo` で起動の 2 秒前から録った。許可ダイアログが出ている間は、スクリーンショットを撮っていない
- 閉じる操作: シミュレータ制御ツールのタップで、許可ダイアログの「許可しない」を押した
  - 「許可しない」を選んだのは、閉じたのがタップであることを結果で確かめるため。操作なしに許可ダイアログが閉じる事象 (handbook の同じ小節) では、許可の結果が true で届く
  - 3 回とも `granted=false` が届いたので、閉じたのはタップである
- 判定: 録画のコマを、Android と同じく AVFoundation で取り出した。最後のコマ (メニュー画面) を基準に、画面の下半分 (Toast の出る範囲) で違う画素を数え、許可ダイアログが消えた後に Toast が写ったかを見た

### 結果

受理と許可ダイアログの前後関係は、診断出力 (起動からの経過) と録画のコマの時刻で確かめた。3 回とも、許可ダイアログが出てシーンが非アクティブになった後に Toast を受理している。

| 回 | 非アクティブ化 (許可ダイアログの出現) | Toast の受理 | 許可の結果 (タップ) | 再びアクティブ | 受理から閉じるまで | 閉じた後に Toast が見えた時間 |
|---|---|---|---|---|---|---|
| 1 | 500 ms | 1025 ms | 9889 ms (`granted=false`) | 10291 ms | 約 8.9 秒 | 0 ms (写らない) |
| 2 | 508 ms | 1031 ms | 4948 ms (`granted=false`) | 5349 ms | 約 3.9 秒 | 0 ms (写らない) |
| 3 | 509 ms | 1034 ms | 4891 ms (`granted=false`) | 5297 ms | 約 3.9 秒 | 0 ms (写らない) |

- 録画では、メニュー画面が出た約 0.1 秒後に画面が暗くなり始め (許可ダイアログの出現)、約 0.3 秒で出そろった。Toast の受理はその後になる (診断出力の時刻を、録画のアクティブ化・許可ダイアログの消え始めのコマに重ねて確かめた)
- 許可ダイアログが消えた後 (消え始めから約 0.3 秒で消え切る) のコマで、画面の下半分の違う画素は 8 以下で、Toast は一度も写らなかった。録画は閉じた後も約 11〜12 秒続けた (画面が変わらない間はコマが出ないので、最後のコマの後は静止していた)
- 読み取り: 今のライブラリは、許可ダイアログの間 (前面だが提示先が無い) に受け付けた Toast を受理の時点から数える。1500 ms の表示時間は許可ダイアログの下で尽き、閉じた時点では満了して捨てられている
- 予備の 3 回 (数えていない): 最初は「許可」をタップして撮った。うち 1 回は、許可の結果がタップより前に届いたとみられる (経過時刻の突き合わせで約 1 秒先行)。閉じたのがタップだと言い切れないので、「許可しない」で撮り直した 3 回だけを数えた。予備の回でも、閉じた後に Toast は写らなかった (1 回目を録画で確認)
