# 蒸留への申し送り: add-presentation-behavior

実装フェーズで見つかった、ksn-distill (蒸留) で扱うべき事項。実装中は concepts を書き換えない。

- **test-execution.md の負の検査表**: iOS の負のコンパイル検査が 4 本 → 8 本に増えた (`KSDIALOGS_NEGATIVE_CHECK_SHOW_TRANSITION` → `extra argument 'transition' in call` / `KSDIALOGS_NEGATIVE_CHECK_OPTIONS_TRANSITION` → `value of type 'DialogOptions' has no member 'transition'` / `KSDIALOGS_NEGATIVE_CHECK_NONE_ARGUMENT` → `argument passed to call that takes no arguments` / `KSDIALOGS_NEGATIVE_CHECK_DEFAULT_DURATION` → `'defaultDuration' is inaccessible due to 'internal' protection level`)。表の「17 本」(→ iOS 8 / Android 7 / MAUI 9 (既存 6 + 新規 3) / KMP 3 = 27 本) と実測件数 (iOS 90 → 137 tests / 25 suites、最終値は完了報告の表を正とする) を実測で更新する。Android: 負の検査 4 本 → 7 本 (`ksdialogs.negativeCheck.showTransition` → `None of the following candidates is applicable:` と `No parameter with name 'transition' found.` (show のオーバーロードで 2 件) / `ksdialogs.negativeCheck.optionsTransition` → `Unresolved reference 'transition'.` / `ksdialogs.negativeCheck.noneArguments` → `Too many arguments for 'fun none(): DialogTransition'.`)。実測件数: android unit 50 (不変) / instrumented 94 → 138 (`ksdialogs` 105 + `ksdialogs-compose` 33) / `maui/android/native` 9 → 12。MAUI / KMP 分の増分は各グループ完了時に追記
- **design Decision 3 の iOS factory `@MainActor` 化** — **オーナー承認済み (2026-08-22)**: iOS のプリセット factory 4 本は `@MainActor` が確定形。ADR-0017 の蒸留時に「iOS の既定 easing (`UICubicTimingParameters`) が MainActor 隔離のため factory は MainActor で呼ぶ」を Consequences に 1 行、transition-semantics.md は既に実装どおり (プリセット節の箇条書き) なので変更不要。`none()` は UIKit を触らないため `@MainActor` を外す余地あり (対称性を優先して現状維持、需要が出たら非破壊で緩和できる)
- **design Decision 10 (attached 中のコンテンツ非表示) の iOS 暫定差分はオーナー却下 → design どおりへ修正** (2026-08-22、実機で 100% 再現するちらつき)。修正後は iOS / Android とも design Decision 10 どおりで、ADR-0017 / transition-semantics.md に乖離の記述は不要
- **`DialogContainerViewController.observeResultChannel()` は提示層 (`DialogPresenter`) が明示的に呼ぶ設計** (`DialogResultChannel.onSettle` がハンドラ 1 本の上書き方式で、init 内登録だと器を直接組み立てるテストの登録を潰すため)。器を直接生成するテストでは状態機械が動かない — 将来の落とし穴として concepts (実装境界) かコードコメントで十分かを判断
- **Android の JVM テスト用提示面 (`DialogTestPresentationSurface`) は配送を即時にしている** (JVM では器がウィンドウに載らず状態機械が `created` から進まないため。「配送は撤去の後」の契約は instrumented PB-TR-10/13 が担保)。test-execution.md の「黙って空振りする範囲」に「PB-TR 系は JVM では 1 本も走らない (全件 instrumented)」を追記する候補
- **Android の `RecordingDialogPresentationSurface` (androidTest) は `ActivityDialogPresentationSurface` の組み立てを一部写している** (器へ到達するための割り切り。doc コメントに差分3点を明記)。本番面が変わったときの追随漏れリスクとして認識しておく
- **test-execution.md へ「証跡撮影は `adb shell am instrument` で直接回す」を追記する候補**: Gradle の `connectedDebugAndroidTest` は実行後にテスト APK をアンインストールするため、テストがアプリの外部ファイル領域へ保存したスクリーンショットが消える。証跡を取り出すには `assembleDebugAndroidTest` → `adb install` → `am instrument` → `adb pull` の順で回す (2026-08-21 実測、system-bars-android の証跡で使用)
- **API 29 の実行環境が増えた**: エミュレータ `ksn_api29` (pixel_4 / `system-images;android-29;google_apis;arm64-v8a`) を導入。旧経路 (systemUiVisibility) の Scenario はこの環境でしか実行できないため、test-execution.md の instrumented 節へ「API レベル別に走る/走らない Scenario がある (`assumeTrue` によるスキップ)」を追記する候補 (2026-08-21)
- **MAUI: 負の検査 6 本 → 9 本** (`KsDialogsNegativeCheckShowTransition` → CS1739 / `KsDialogsNegativeCheckOptionsTransition` → CS0117 (`Dialog.GetTransitionDuration` が無い。MAUI の `DialogOptions` は internal で検査側から見えないため、演出を静的メタ属性へ畳み込んだ場合に生えるはずの添付スカラーを的にした) / `KsDialogsNegativeCheckNoneArguments` → CS1501)。実測件数: maui `dotnet test` 44 → 62 (最終)
- **design Decision 8 の実行口に overlayDuration が漏れていた**: 公開 API の `OverlayDuration` をブリッジで運ぶため、互換面の install に overlayDuration の口を追加した (実装フェーズで補完)。ADR-0017 / transition-semantics.md に MAUI ブリッジを書く際は「運ぶもの = フック2本 + overlayDuration」で記述する
- **MAUI プリセットの動きの正しさは tasks 8.4 の実機確認が唯一の受け皿**: MAUI のアニメーション API はハンドラに載っていない View では `Unable to find IAnimationManager` で fault し (アダプタが吸収)、ユニットテストは経路までしか検証できない。test-execution.md の「黙って空振りする範囲」候補
- **KMP / iOS の実測件数 (KMP グループ完了時点)**: kmp `./gradlew allTests --rerun-tasks` 48 → **51** (iosSimulatorArm64 26 → 29 + androidHostTest 22 不変)、ios `xcodebuild test` **129 tests / 25 suites** (KMP 登録コンテンツの添付テスト2本を含む)。KMP の負の検査は 3 本のまま (共有コードに API 増なし・診断も不変)
- **KMP 経路のキャンセル追随で `kmp/ADR-0005` の「負の帰結」が解消した**: ADR-0005 の Consequences にある「Kotlin 側 suspend 経路は未追随のまま残り、契約不適合が Kotlin 経路に限定して継続する」は解消済み。ADR-0005 への追記か、後続 ADR での言及かを蒸留で判断する
- **KMP 層で実提示まで見られない制約**: KMP の iOS テストは `UIApplicationMain` を通らない実行体で走るため key window が存在せず、提示先が常に不在になる (既存の `InteropBridgeContractTests` と同じ制約)。Kotlin 側は委譲面 (`IosDialogShowSurface`) の差し替えで配管だけを見て、実提示は ios/ 側のテストが担保する — test-execution.md の「黙って空振りする範囲」へ「kmp の iosSimulatorArm64Test では実提示が起きない」を追記する候補
- **Scenario ID の網羅検査 `scripts/scenario-id-coverage.py` を追加した**: `python3 scripts/scenario-id-coverage.py` (未網羅があれば終了コード 1、`--selftest` で検査自身の確認) をローカルで回す位置づけ。仕様の Scenario 見出しの ID とテスト名の ID を表記ゆれを吸収して突合する検査で、実行や依存グラフを見る既存の検査とは別軸。test-execution.md へ「仕様とテストの対応の検査」として追記する候補 (CI ワークフローは本リポジトリに無いためローカル実行と明記する)
- **PB-KC-03 のテストは ios/ ビルドルートにある**: KMP の登録面 (Swift・kmp/ADR-0003) と添付面 (`UIView.ksDialogTransition`) はどちらも Swift 側にあり、Kotlin からは触れないため、`ios/Tests/KsDialogsTests/KsDialogsKmpTransitionTests.swift` に置いた (先例: `KsDialogsKmpFacadeTests` / `KsDialogsKmpCancellationTests`)。ID 網羅検査スクリプト (tasks 1.5) は PB-KC-03 を ios/ のテスト名から拾う必要がある
- **`registration-show-semantics.md` の「宣言的 UI での属性の添付」表に transition (第3スロット) の記載が無い** (矛盾はしない)。transition-semantics.md への参照行を足すか、表に第3スロットを加えるかを蒸留で判断
- **concepts 本文の `PB-` ID は change の specs に依存**: archive 後の参照の持ち方 (ADR-0016 の枠組み + テスト名で辿る前提でよいか、`scripts/scenario-id-coverage.py` が archive の specs も既定で探索することで足りるか) は蒸留での判断事項
- **sample-parity.md への反映時の表記整理**: Transition デモ画面の表示ボタンは承認モック・brief の文言表どおり `表示` (日本語)。既存 Layout Dialog パネルの表示操作は `Show` (英語) で、画面間で表記がそろっていない。蒸留で sample-parity の文言表へ Transition デモの文言表・規範表を追加する際に、オーナーへ「どちらかへ統一するか / 画面ごとの表記差を許容するか」を確認する (統一する場合は別 change の S 級 UI 微調整)。**オーナー決定 (2026-08-22): 蒸留時に判断**
- **`samples/README.md` (sample-parity の利用者向け写像) の更新**: デモ項目表に `Transition Dialog` (6項目目) の行、Transition デモ画面の文言・規範 (ui/brief.md の文言表・規範表 + 「実装で決めた値」: Custom Hook 固定 300ms 等) を、sample-parity.md の更新と同時に反映する。4ルート完了前に書くと不正確になるため実装フェーズでは未更新
- **実測件数の更新 (MAUI 不具合修正後)**: maui `dotnet test` 62 / `maui/android/native` 15。ADR-0017 / transition-semantics.md の MAUI 記述には「配送の合図はブリッジの閉鎖通知 (撤去後)。`ResultChannel.Result` はラッチであって配送ではない」を `DialogPresentationCompletion` (Settle / Deliver の分離) の形で反映する。design Decision 8 にこの結線が書かれていなかったことは lessons/inbox に捕捉済み
- **`DialogPresentationCompletion.Deliver()` の防御**: 撤去までに報告が 1 つも無ければ cancelled として確定してから配送する保険が入っている (現行の結線では到達しない)。契約「報告のないまま閉じた = cancelled」と整合するが、余計と見るなら蒸留で削除を判断
- **未再現の観測 (MAUI iOS、`None` プリセットの退場)**: 「覆いが消えたコマに中身が残り、結果表示が既に切り替わっている」コマが 1 度だけ撮れ、2 回目は再現しなかった (verification/sample-walkthrough/README.md 所見4)。契約違反とは断定できないため finding にしていない。再現したら `None` の退出 (中身は即完了・覆いのフェード完了を待って撤去) と配送順序の結線を疑う
- **フック未完了警告の有効条件の非対称 (review-001 Suggestion)**: iOS は `#if DEBUG` (ライブラリ自身のビルド構成。SPM ソース配布では利用者の Debug と一致)、Android は提示先アプリの `FLAG_DEBUGGABLE`。プリビルド xcframework 配布へ変える際は iOS 側の判定を見直す。transition-semantics.md の「デバッグビルド」の主語を明記する候補
- **Android の成立しない duration (review-001 Suggestion)**: Android は `kotlin.time.Duration` をミリ秒に落とすと 0 になる正の微小値 (例 0.5ms) も即完了扱い (iOS は 0.5ms のアニメーションを組む)。transition-semantics.md の成立しない値の列挙に「Android ではミリ秒に落とすと 0 になる長さ」を並記する
- **sample-parity.md「パネル操作部の読み上げ」の状態列挙に「無効状態」を含めるか**: Transition パネルの a11y 証跡 (verification/panel-accessibility/) で、MAUI iOS だけ調整部の無効状態がイージングチップの読み上げに乗らない (他 5 形態は `Disabled` / `enabled="false"` が付く。MAUI の `IsEnabled` 伝播が `ContentView` 越しの `UIButton` に届かないため)。規約は選択状態・ON/OFF・現在値までしか列挙しておらず違反ではない。**オーナー決定 (2026-08-22): 起票しない** — 既知の制限として受け入れ、蒸留で再提起しない。sample-parity.md の状態列挙に無効状態を加える改訂も行わない (加えるなら MAUI iOS が不一致になるため)
- **test-execution.md の実測件数の最終値 (verify-001 時点)**: ios 137 tests / 25 suites (review-005 Minor 1 のテスト追加後)、android unit 50、instrumented 138 (`ksdialogs` 105 + `ksdialogs-compose` 33、API 別 skip あり)、kmp 51 (ios 29 + androidHost 22)、maui 62、maui bridge 15、負の検査 27 本。蒸留時に再実測して確定する。`verification/kmp-cancellation/README.md` の「ios 129 tests」は執筆時点の値 (鮮度差、証跡なので書き換えない)
- **任意テストの候補 (review-003 S-2)**: iOS の「撤去要求〜完了通知の窓で器が解放される」順序を直接固定するテストは未配置 (`deliveryOutlivesContainerRelease` が器を直接組み立てて同じ機構を固定しており、機構同一のため任意)。後続で `DialogTestPresentationSurface` の要求/完了分離と弱参照観察を組み合わせれば書ける
- **iOS の「表示とフック開始の同時性」の成立条件 (review-004 S-1 / second-opinion-code-004)**: iOS 17 制約下では `Task.immediate` (iOS 26+) が使えず、同時性は「フック型が `@MainActor` で宣言されているため同一アクター上の直接 `await` が最初の中断点まで同期実行される」性質に依存する。ADR-0017 (Decision 10 の統合先) の Consequences に明記し、最低対応 OS を iOS 26 へ上げる時点で `Task.immediate` への置き換えを検討する
- **ちらつき防止の固定はデルタスペックではなく回帰テストが担う** (review-004 S-2): spec は UI lint でアニメーション/フレームの記述を禁じているため Scenario 化できない。ADR 統合本文に 1 行残す (`DialogTransitionTests` の「中身の表示と presentation フックの開始の間に描画の機会がない」)
- **覆いの開始を同期化する候補** (second-opinion-code-004 Minor、降格): 覆いのフェードは `async let` の child task で始まるため `none` / 同期完了フックでは最初の描画フレームで 1 フレーム分遅れ得る (alpha 0 → 約 4% で視覚的には判別不能)。構造的に揃えるなら `UIViewPropertyAnimator` を親 Task 内で同期開始して完了だけを待つ形。後続候補
- **回帰テスト (MainActor FIFO 依存) の位置づけ** (second-opinion-code-004 Minor、降格): 5 連続実行で安定し直前の `alpha == 0` 期待が前提を見張るが、厳密には実行順の保証が無い。smoke test として保持し、`CADisplayLink` 等で最初の描画フレームを観察する実描画テストへの置き換えは後続候補
- **design Decision 10 の遷移表と実装が一致しないマスが 1 つ (verify-004)**: created / attached 行の「外側タップ / 戻る」は表では「(まだ受け付けない)」だが、iOS 実装は attached の間 (覆いも中身も alpha 0 の 1 MainActor ターン) も受け付けて cancelled をラッチし、演出なしで removed (同行の報告列と同じ終わり方)。Android の同箇所の挙動も蒸留時に確認し、ADR-0017 へ統合する際に「受け付けない」を厳密に固定する (実装を揃える) か、表側を「受け付けても結果は報告列と同じ」に改めるかを判断する (deviation.md 実装メモ参照)
- **iOS の「提示前の確定」を担う 2 機構の一本化候補 (review-005 Suggestion)**: `beginLifecycle()` の `scheduleImmediateRemoval()` (入口判定) と lifecycle Task 先頭のガード (`!Task.isCancelled && .attached && !isResultSettled`) の 2 か所が同じ「提示前の閉鎖は演出なしで撤去」を担う。片方だけ直す保守ハザードがあるため、後続で Task 先頭ガードへ一本化する候補
- **Swift Testing の単体指定は括弧付き** (テスト追加ワーカーの申し送り): `xcodebuild test -only-testing:KsDialogsTests/<Suite>/<func>()` のように**関数名に `()` を付けない**と filter が空振りして「0 tests / TEST SUCCEEDED」になる (偽の green)。test-execution.md の「黙って空振りする範囲」へ追記する候補
- **UI 最終承認: 2026-08-22 オーナー承認済み** (ui/brief.md に記入)。蒸留の sample-parity 反映はこの承認を前提に進めてよい
