# 実装乖離メモ: add-presentation-behavior

実装フェーズで発生した、デルタスペック / design との差分の記録。spec 本体は書き換えない (逆流修正禁止)。
「オーナー確認済みの項目」は、実装フェーズ中に暫定採用としてオーナーへ提示し、2026-08-22 に承認 (Decision 3) または却下 → design どおりへ修正 (Decision 10) の判断が付いたもの。

## オーナー確認済みの項目 (旧「オーナー確認待ち (暫定採用)」)

- **design Decision 3 (iOS プリセット factory のシグネチャ)** — **オーナー承認済み (2026-08-22、合意済み差分)**: design では `public static func fade(duration:easing: any UITimingCurveProvider = .standard)` 等を isolation 注釈なしで固定 → 実装では **factory 4本 (`fade` / `slide` / `zoom` / `none`) を `@MainActor`** にした。理由: Swift 6 言語モードで `UICubicTimingParameters.init(animationCurve:)` が MainActor 隔離のため、nonisolated な既定引数 `.standard` がコンパイルエラーになる (`.standard` を nonisolated にすると恒久警告が残る)。Hook 型・引数名・引数順・戻り型・`none()` 無引数は design どおり。実用上の呼び出し点 (UIView 添付・SwiftUI body) はすべて MainActor。代替案: (b) 警告を許容して nonisolated へ戻す / (c) `easing` の既定を `nil` にし内部で解決 (API 形が変わる) (2026-08-21)
- **design Decision 10 (attached 中のコンテンツ非表示)** — **オーナー却下 (2026-08-22): 実機で 100% 再現するちらつきとして不具合扱い、design どおりへ修正** (修正内容は下の「実装メモ」に追記): design では「attached の間はホスト View 非表示 (alpha 0 相当) → presenting でオーバーレイのフェード開始と同時に表示しフック開始」 → iOS 実装では **凍結 (初回レイアウトパス完了・属性採用) 時点で alpha を同期的に復帰し、presentation フックは直後の MainActor ホップで開始**する。理屈上、フック開始前に最終位置が 1 フレーム見える可能性が残る。非表示期間は「レイアウトパス〜宣言的 UI の添付到達待ち」をカバーしており、主目的 (添付の取りこぼし防止とその区間のちらつき防止) は満たす。同期復帰にした理由: alpha 0 のままだと `hitTest` が中身を返さず、器を直接組み立てる既存の外側タップ判別テストが壊れるため。同一フレーム開始が要件ならレビュー/オーナー判断で再設計 (2026-08-21)

## 実装メモ (契約の範囲内、公開面に影響なし)

- **design Decision 10 のオーナー却下への修正内容 (iOS の入場ちらつき)**: 上の却下を受け、**design どおり「presenting に入る時点で表示とフック開始が同時」へ修正**した (2026-08-22)。採った案は「alpha 復帰を進行タスクの中へ移し、presentation フックを `async let` の子タスクではなく直接 `await` で呼ぶ」形。これにより alpha 復帰とフックの最初の同期処理 (slide なら画面外への transform、zoom なら 0.8 倍、カスタムフックなら利用者の最初の処理) が同一の同期区間に入り、間に描画が挟まらない。`beginPresentation` は進行 Task の起動だけを行う。Task 本体は、取り消し・`.attached` 状態・結果未確定を最初の中断点より前に確認し、通過後に `.presenting` へ進めて中身の表示と presentation フックを開始する (通過しなければ演出なしで撤去)。この形は review-004 / second-opinion-code-004 の指摘 (`.presenting` を同期で立てると Task 開始までの 1 ターンの窓で閉鎖信号が presenting 規則で扱われる) を受けた 2 段階目の修正で確定した。覆いのフェードは従来どおり `async let` の子タスクで並走する (覆いは alpha 0 から始まるため、開始が 1 ターン遅れても見えるものが変わらない)。**`Task.immediate` (SE-0472) 案は不採用** — `@available(iOS 26.0, *)` であり、`ios/Package.swift` の最低対象 OS (iOS 17、cross/ADR-0002) では使えない (`if #available` で分岐すると OS 版で挙動が割れるため不可)。**`layer.opacity` で隠す案 (C') も不採用** — `UIView.alpha` は `layer.opacity` と同じ記憶域であり、`layer.opacity = 0` にすると `alpha` も 0 になって `hitTest` が中身を返さなくなる (回避にならない)。器を直接組み立てて hitTest を観察する既存テスト2本は、中身が見える状態になるまで待ってから観察する形へ変更した (本体の挙動は変えていない)。実機での再現確立と解消確認は `verification/first-frame-ios/` を参照

- **design Decision 5-3 (`DismissalOrigin` の列挙)**: design の列挙は report / outsideTap / backPress / callerCancellation / hostLost → iOS の内部列挙 `DialogDismissalOrigin` は **`backPress` を持たない** (iOS に戻るボタンの閉鎖経路がなく到達不能な case になるため。doc comment に明記)。内部型であり公開契約には出ない (2026-08-21)
- **design Decision 2 (オーバーレイの階層位置、Android)**: design では「コンテンツのホスト View の兄弟レイヤ」 → Android 実装では `DialogLayoutHost` の子として `overlayView` を置き、ホスト View を包む外形 `DialogContentHolder` の兄弟になっている (字面より1段外側)。狙い (覆いのフェードが中身の演出を巻き込まない・時間 / イージングが独立に観察できる・フックは覆いに触れない) は満たしている。iOS は器の view 直下でホスト View と兄弟 (2026-08-21)
- **design Decision 10 (attached 中のコンテンツ非表示、Android)**: Android は design どおり (凍結まで alpha 0 → presenting で復帰と同時にフックを `CoroutineStart.UNDISPATCHED` で開始) に実装できており、iOS の暫定項目は Android には適用されない (2026-08-21)
- **Android のテスト名は ID をアンダースコア区切りで含める**: iOS は `[PB-MD-01] …` の表記だが、Android は Kotlin の関数名に `[` `]` を書けないため `PB_MD_01_…` とする (G2a で入った `PB_TR_01_…` / `PB_AA_01_…` と同じ形。JVM テストも同形に揃えた)。ID 網羅検査スクリプト (tasks 1.5) は両表記を正規化して突合する必要がある (2026-08-21)
- **`DialogOutsideTapTests` に「ウィンドウがフォーカスを得るまで待つ」を追加**: API 29 エミュレータで外側タップ 3 本が安定して失敗した (タップが背後の画面へ抜ける / 結果が返らない)。原因は待ち合わせ点で、最初の描画は器がまだ出現の演出前 (覆いも中身も透明) の時点であり、ウィンドウが入力の宛先として登録される前にタップを注入していたこと。テスト側で `rootView.hasWindowFocus()` を待ってから注入するようにして解消 (API 29 で 3 回連続 green、API 33 / 36 も green)。**本体の挙動は変えていない** — 実利用ではダイアログ出現の数ミリ秒後にタップが届くことはないため、契約側の問題ではないと判断した (2026-08-21)
- **`DialogSystemBarsTests` は器が表示状態 (shown) になるまで待ってから観察する**: 出入りの演出が終わるまで覆いも中身も透明なため、待たずに撮った証跡が真っ白になった。Scenario の「ダイアログを表示する」に忠実な待ち合わせでもある (2026-08-21)
- **PB-KC-01 の Kotlin 層での観察点**: spec の THEN「ダイアログが閉じ、呼び出し元は CancellationException を観察する」のうち、KMP の iOS テスト実行体 (`iosSimulatorArm64Test`) は `UIApplicationMain` を通らず key window が無いため実提示に到達できない。Kotlin 層のテストは「当該 show の取り消し操作がちょうど1回届き、他の show には届かない + CancellationException の伝播」に読み替え、実際に閉じることは Swift 側 (`ios/Tests/KsDialogsTests/KsDialogsKmpCancellationTests.swift`) が担保する (design Decision 7 の層別: KMP は配管のパススルー検証)。テストのために内部の継ぎ目 `IosDialogShowSurface` / `IosDialogShowCancellation` (internal、公開 API 増なし) を導入 (2026-08-21)
- **PB-KC-03 のテストは ios/ ビルドルートに置いた**: KMP の登録面 (Swift、kmp/ADR-0003) も添付面 (`UIView.ksDialogTransition`) も Swift 側にあるため、既存の KMP 面テスト (`KsDialogsKmpFacadeTests` 等) と同じ置き場。Android 側の KMP 経路は suspend を素通しで委譲し、添付は View タグ経由のため KMP モジュールの JVM テストでは往復せず、instrumented ターゲットも無いので未配置 (2026-08-21)
- **design Decision 3 (MAUI プリセットの経路、中身の親)**: MAUI の中身は ViewModel ごとの factory が新規生成し、器へ渡すのはその platform view だけなので、これまで MAUI 側の親を持たないまま提示していた。MAUI の iOS 実装 (`Microsoft.Maui.Platform.TransformationExtensions.UpdateTransformation`) は **親を持たない View に transform (移動・回転・拡大縮小) を反映しない**ため、`Slide` / `Zoom` と利用者のフックで透明度しか動かない症状が出ていた (実機で観測。証跡は `verification/sample-walkthrough/maui-ios-transform-probe.log`)。→ 実装では提示 1 回分の入れ物 (`DialogPresentationContent`) が **中身だけを抱える親 `DialogContentHost` (internal、`Element` 派生)** を持ち、中身を MAUI の要素ツリーへ載せてから器へ渡す。親はスタイルも BindingContext も持たないため中身の見た目と結び付きには影響しない。プリセットは design どおり C# の `TranslateTo` / `FadeTo` / `ScaleTo` のままで、カスタムフックと同じ 1 経路を通る。公開 API の増減なし。Android は元から transform をレイアウトと独立に反映するため症状は無かったが、形態間で中身の置かれ方を揃えるため親は両形態で与える (2026-08-21)
- **design Decision 5-1 (iOS の「器の撤去の後」の観察点が2つある)**: 提示面 `DialogPresentationSurface.dismiss` を完了通知つきにし、UIKit の `dismiss(animated:completion:)` の完了を受けてから中身の解放と配送へ進む形にした。これに加えて、器自身の `viewDidDisappear` (自分から要求した撤去が画面上で完了した合図) からも同じ後始末へ入る。後始末は 1 回しか進まないので、先に届いた方が撤去完了の合図になる。2 経路にしたのは、提示機構の完了通知が届かない状況で show が返らなくなるのを避けるため。`viewDidDisappear` 側は提示関係が解けている (`presentingViewController == nil`) ことまで確認してから進むので、通常の撤去では完了通知が先着し、**View が消えて提示関係まで解けたのに completion だけ届かない場合に限って** 2 経路目が効く (提示関係が残ったまま配送すると次のダイアログ提示との競合を再導入するため、nil 確認は外さない)。なお、**シーンを持たないテストランナーでは `dismiss(animated: false)` の completion が呼ばれず提示関係も解けないまま View だけが window から外れる**ことを実測したが、このケースは `presentingViewController` が残るため 2 経路目の対象外であり、テストでは要求と完了を分離できるテスト用提示面 (`DialogTestPresentationSurface`) で代替する。OS 発の器消失の経路は design 5-2 どおり完了を待たずに即配送する (2026-08-21)
- **design Decision 5-1 (配送口を器から切り離した)**: 撤去の要求から完了通知までの待ち合わせの間に提示機構が器を手放すと、配送口が器の中にある限り呼び出し元が取り残される。→ 実装では確定した結果を届ける口を器とは別の内部オブジェクト `DialogOutcomeDelivery` (internal、公開 API の増減なし) が所有し、器はそこへ結果を渡すだけにした。器が撤去まで進めないまま解放される場合は器の `deinit` が同じ口へ引き継ぐため、どの経路でも show は返る。`viewDidDisappear` の 1 回分の後始末は器を強く捕まえて進め、撤去まで到達させる (2026-08-22)
- **design Decision 10 (`removed` になる時点)**: 撤去の要求から完了通知までの間は退出中 (`dismissing` 等) のままとし、要求済みかどうかは内部フラグで持つ。`removed` は「器を撤去し outcome を配送した」段階の定義どおり、撤去の完了と後始末まで進んだ時点で立てる。撤去要求後に入力を受け付けない扱いは、状態ではなくこのフラグで判定する (2026-08-22)
- **design Decision 3 (MAUI プリセットの実装 API 名)**: design は `TranslateTo` / `FadeTo` / `ScaleTo` と書いているが、MAUI 10 ではこれらが旧形式 (CS0618) で `TranslateToAsync` / `FadeToAsync` / `ScaleToAsync` が正式名。実装 (`Contract/DialogTransition.cs`) と api-surface-check の利用例は `*Async` を使う (挙動は同一、公開 API には影響なし)。オーケストレーターが直接改名 (12 箇所、2026-08-21)
- **design Decision 10 (created / attached 中の外側タップ)**: 遷移表は created / attached 行の「外側タップ / 戻る」を「(まだ受け付けない)」とするが、iOS の `reportOutsideTap` は `.created` / `.attached` の間も受け付けて cancelled をラッチし、演出なしで removed にする (同じ行の「報告」列と同じ終わり方)。`DialogOutsideTapTests.swift:18-33` は `.created` でのこの挙動を明示的に固定している。製品経路 (器 root View の `UITapGestureRecognizer`) ではタップ成立に 2 run loop ターンが要り、覆いも中身も alpha 0 の 1 ターンの窓では成立し得ないため、結果・フック非実行・配送は遷移表と一致し実装は変えていない。契約として「受け付けない」を厳密に固定する場合は 1 行では済まず、既存テスト 4 本以上 (外側タップ判別の直接組み立て系) の書き換えを伴う (2026-08-22)
