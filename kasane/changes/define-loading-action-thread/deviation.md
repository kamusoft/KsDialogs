- design Decision 3 (Android): design では「切り替えを action の呼び出しの内側に入れれば、報告と終了の順序の保証をそのまま保てる」→ Android では成り立たなかった。`withContext` は呼び出し元と同じ dispatcher なら dispatch を省き、UI スレッド外の action が呼び出し元の中断より先に終わるとその場で戻るため、終了の受理が UI スレッドの列に post された報告を追い越した (既定の指定で action の中から別スレッドで報告してすぐ戻る書き方でも起きる)。対策として `LoadingCoordinator.report` を「呼んだその場で 1 本の列 (`Channel`) に積み、UI スレッド上の 1 つの受理コルーチンが順に受理する」形に作り直し、終了の直前に同じ列の末尾へ区切り (`awaitAcceptedReports`) を積んで待つ形にした (iOS の `LoadingReportQueue` と同じ考え方)。あわせて、受理ループは報告 1 件ごとの受理を `scope` (`SupervisorJob`) 直下の子として起動し、利用者の進捗の受け口が投げた失敗がループと区切りの待ちを止めないようにした (失敗は握りつぶさず、変更前と同じくスレッドの未捕捉例外ハンドラへ出る。1 本の列にした作りでは、素直に書くと失敗で以後の終了が永久に待つ)。固定するテスト: `LoadingActionThreadTests` の LD-TH-07 と `既定の指定で_UI_スレッド外から報告して直後に戻っても最終進捗が終了に追い越されない`、`LoadingProgressTests` の `進捗の受け口が失敗しても以後の報告と終了は受理され次の開始が戻る`。理由: LD-TH-07 の保証を満たすため。iOS / MAUI / KMP iOS は報告と終了が元から同じ列に積まれる作りで、同じ追い越しは起きないことを照合済み (2026-09-25)
