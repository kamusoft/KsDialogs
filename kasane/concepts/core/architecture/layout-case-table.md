# レイアウト共通ケース表と OS 差の統制

この文書を読むと、[レイアウトのルール](../api/layout-semantics.md) の規則から導いた期待値を単一の正として固定している共通ケース表の形・読み方・運用と、OS 間で揃えられない差異を承認つきで記録する統制の仕組みが分かる。レイアウト規則そのものは同文書が定めるので、先にそちらを読むと分かりやすい。

**この文書は利用者向けの契約ではなく、Native 2 実装のレイアウト検証機構の記述である。** 表の期待値がどう決まるかは規則の側 (core/api) が正であり、この文書が定めるのは表の形と、表を巡る運用だけである。

## なぜ表が要るか

規則を文章で書くだけでは、曖昧さがそのまま実装差になる。そこで規則と対になる**共通ケース表**を単一の正として置く: リポジトリルートの `core/layout-spec/cases.json` ([core/ADR-0009](../../../decisions/core/0009-layout-spec-test-case-table.md))。

表全体は `{ "tolerance": <許容誤差>, "cases": [ <ケース>, … ] }` の形をしている。

## ケースの読み方

| 要素 | 内容 |
|---|---|
| 1 ケースの組 | 「screen / insets / contentSize / attributes → 期待 rect (x, y, w, h)」。期待値はすべてレイアウト規則の手順から機械的に導いてある |
| `screen` | 本表では window のサイズを指す (物理画面ではない) |
| `attributes` | **供給を合成したあとの実効値**。書かれていない属性は既定値 |
| ケース ID | `C` + 連番 (C01, C02, …)。本文から個々のケースを指すときはこの ID を使う |
| `tolerance` | 座標比較の許容誤差。表全体に 1 つ設定する (Android の整数丸めを吸収するためのもの) |

`attributes` が実効値なのは、合成がオブジェクト単位の選択 — 置き場所は show 引数があればそれ、なければ添付、どちらも無ければ既定値 — であり、フィールド単位のマージではないためである。ケース表は供給経路によらずレイアウト規則だけを検証するので、どこから渡された値かは書かない。

ID は**参照の安定を優先して欠番方式**で運用する。廃止された属性のケースを取り除いても残りのケースを振り直さないため、連番に穴が空く。

基準領域に可視領域を選ぶケースでは、insets を期待値の分岐ではなく**入力として与える** — 可視領域の実体は OS ごとに違う (iOS は safe area、Android はシステムバーを除いた領域) ため、環境差を入力の差として表現する。

## 規則とケースの対応 (代表例)

レイアウト規則のうち間違えやすい箇所は、どのケースが固定しているかを控えておくと突き合わせが速い:

| 規則 | 固定しているケース |
|---|---|
| 属性を何も渡さないダイアログの rect (可視領域基準・余白 24・中央) | `C19` |
| 比率指定が fill に勝ち、位置は中央扱いになること | `C05` |
| 有効領域へのクランプ | `C10` |
| offset が有効領域の外を許容すること | `C07` |
| 余白を控除しすぎて有効領域の長さが 0 になったときの位置 | `C22` |

## 誰が全量検証を課されるか

**全量検証を課すのは Native 2 実装だけである。** iOS は XCTest がシミュレータ上でレイアウト完了後の実 frame を、Android は instrumented test が実 View の rect を測る。rect を計算する関数だけを単体検証しても、レイアウト機構への反映漏れを見逃すため、実測でなければ受け入れ条件を満たさない。

MAUI / KMP はケース表を読まず、属性が値のまま Native へ届くことだけを検証する。

## OS 差の統制 (`approvedDiff`)

**OS 差は該当ケースに置く `approvedDiff` でしか表現できない。** OS ごとに、差し替える期待値と、理由 (`reason`)・本ライブラリの意思決定者 (オーナー) による承認 (`approvedBy`) を記録する。`expected` に書いたフィールドだけがその OS で上書きされ、書かなかったフィールドは共通の期待値のまま残る:

```json
{ "id": "C19", "expected": { "x": 60, "y": 320, "w": 280, "h": 180 },
  "approvedDiff": { "android": { "expected": { "y": 316 }, "reason": "<なぜ揃えられないか>", "approvedBy": "<承認者>" } } }
```

`reason` と `approvedBy` のないエントリは無効であり、それ以外の期待値分岐は認めない。「OS が違うから」で期待値を枝分かれさせる逃げ道を塞ぐための統制で、これがないとケース表が実装の追認になり、規則の一本化が崩れる。

## 保証すること

- **同じ入力なら iOS と Android で同じ rect になる** (`approvedDiff` として承認・記録された差異を除く)。両 Native 実装は表の全ケースに `tolerance` の範囲で適合する。これが崩れると「規則を 1 本化し実装は各 OS へ委ねる」構成そのものが成立しない
- **ケース ID は表の寿命の間ずっと同じケースを指す**。欠番方式で振り直さないため、本文・テスト・レビュー記録からの参照が後から別のケースを指すことはない

## してはいけないこと

- **承認のない OS 差の期待値分岐を持ち込まない**。分岐は `approvedDiff` に `reason` と `approvedBy` を添えた形だけが有効である
- **共通ケース表の期待値を実装に合わせて書き換えない**。実装がケースを通らないなら、直す対象は実装かレイアウト規則であって、期待値ではない。期待値そのものを変える必要が生じた場合は、変更フローの中でオーナーの判断を経る
- **MAUI / KMP にケース表の全量検証を課さない**。パススルーの層に計算の検証を課すと、レイアウト計算を再実装する動機が生まれる
