# トランジションのルール (出入りの演出と結果が返る時点)

この文書は、全形態 (iOS Native / Android Native / MAUI / KMP) 共通の「ダイアログがどう現れて、どう消えるか」と「その演出が結果の受け取りにどう影響するか」のルールを定める。読むと、出入りの演出を自分のコードに差し替えたときに何が起きるか、何も書かなかったときに起きること、show の結果がいつ返るか、演出が失敗したり終わらなかったりしたときに何が起きるかが分かる。

先に [結果通知のルール](result-notification-semantics.md) を読むと分かりやすい (show が completed / cancelled をちょうど1回返すという原則と、中身のコードが結果報告口で結果を**報告**するという形は同文書が定める)。演出は**器**の属性と同じ**添付**という経路で供給するため、[レイアウトのルール](layout-semantics.md) の「属性の渡し方と優先順位」も前提になる。

- **器**とは、ライブラリが中身 (利用者が書いたダイアログの表示物) を載せて画面に出すための入れ物である。背後を覆うオーバーレイと、中身を載せる View を抱えており、出入りの演出を駆動するのもこの器である
- **この文書が正であり、実装はここに合わせる**。根拠決定は [core/ADR-0017](../../../decisions/core/0017-animation-hooks-transition-attachment.md) (accepted 済み。ADR が持つのは「なぜそう決めたか」で、「何が成り立つか」の正はこの文書側にある)
- 本文中の**原典**は AiForms.Maui.Dialogs (本ライブラリの移植元) を指す。参照ルールは [移植元 AiForms.Maui.Dialogs の参照](../../../handbook/cross/aiforms-origin-reference.md)
- core は「全形態が共有する契約」の層 (層の区分は [concepts 配置ルール](../../rules.md))。添付の面の書き方・フックの型・プリセットの綴り・コード例は各形態の公開面が持つ (末尾の「形態別の公開面」)

ここに書いた観察可能な挙動には `PB-` で始まる **Scenario ID** が振られており、同名のテストで固定されている ([core/ADR-0016](../../../decisions/core/0016-behavior-spec-scenario-tests.md))。本文では該当箇所に ID を添える。2文字目のまとまりが対象を表し、この文書に出るのは TR = 全形態共通の演出契約 / IA = iOS の添付面 / AA = Android の添付面 / MA = MAUI の添付面 / KC = KMP 経由 の5つである。

## 演出は中身に添付する (第3の添付スロット)

出入りの演出は **`DialogTransition`** という値にまとめ、ダイアログの**中身** (factory が返す表示物) の定義に**添付**して供給する。静的メタ属性 (その View の性質として決まる属性) / 置き場所と並ぶ**第3の添付スロット**であり、供給経路も採用時点も既存の2つと同じ規律に乗る ([レイアウトのルール](layout-semantics.md))。

`DialogTransition` が持つのは次の3つだけである:

| 項目 | 意味 |
|---|---|
| presentation | 出現時の演出。省略可 |
| dismissal | 閉鎖時の演出。省略可 |
| overlayDuration | 背後を覆う面 (**オーバーレイ**。本文では「覆い」とも呼ぶ) のフェード時間。省略時は器の既定値 (250 ミリ秒) |

添付の書き方は**形態** (iOS Native / Android Native / MAUI / KMP の4つの入口) と**技術系** (従来 View 系 / 宣言的 UI 系) ごとに違うが、意味は同一である。書き方そのものは各形態の公開面が定める。形態による違いのうち、利用者が観察する範囲は次の2つである:

- **MAUI の添付は code-behind からに限られる**。演出の値がクロージャを含むため宣言的なマークアップには書けず、MAUI には宣言的 UI 系の添付経路もない (MAUI の View が唯一の中身の形。添付の綴りは [MAUI のトランジション公開面](../../maui/api/transition-surface.md) の「code-behind での添付」)
- **KMP の共有コードには添付の面が無い** (共有コードは演出を運ばない)。KMP から登録・表示した中身も各 OS では通常の View として組み立てられるため、その中身に対して各 OS の面で添付すれば同じように効く ([KMP の Dialog 公開面](../../kmp/api/dialog-surface.md) の「共有コードには添付の面が無い」。`PB-KC-03`)

**採用される値は、初回のネイティブレイアウトパス完了時点** — 器を画面に載せたあと OS が最初にサイズと位置を確定させた瞬間 — **で添付されている `DialogTransition`** である ([レイアウトのルール](layout-semantics.md) の「いつの値が使われるか」と同じ1点)。実用上は **show を呼ぶ前に添付しておけば必ず効く**と考えてよい。この時点より後に添付を書き換えても、表示中のダイアログの演出は変わらない (`PB-TR-04`)。宣言的 UI では、初回の組み立てで実行されない場所 (遅延評価されるスコープの中や、イベントハンドラの中) に書くと効かない — 属性と同じ注意である ([登録と表示の呼び出し面のルール](registration-show-semantics.md))。

演出は **show の引数では渡せない**。置き場所と違って呼び出しごとに変えたい要求がなく、供給点を増やさないためである。

## フックの形は全形態で1つ (統一形)

presentation / dismissal は、どちらも「**中身のホスト View を受け取り、演出が終わったら戻る非同期の関数**」である。ここでいう**ホスト View** とは、**その形態のコードから見て中身を代表する View** — 器の中で中身を載せている View — を指す。宣言的 UI で書いた中身も器の中では必ずプラットフォーム View に包まれているため、技術系によらず同じ形になる。関数の型の綴りと、渡ってくる View がその形態の何にあたるかは、各形態の公開面が定める。

フックについて、全形態で次が成り立つ:

- **UI スレッドで開始される**。フックの中でスレッドを気にする必要はない (`PB-TR-01`・`PB-IA-01`・`PB-IA-02`・`PB-AA-01`・`PB-AA-02`・`PB-MA-01`)
- **呼ばれた時点で、ホスト View はウィンドウに載っていてレイアウト済み**であり、器が採用する属性もすでに確定している。つまり最終的な位置とサイズが決まった状態から演出を始められる
- **器はフックの完了を待つ**。dismissal フックが終わるまでダイアログは撤去されず、結果も呼び出し元へ渡らない。原典のような「一定時間で打ち切る」暗黙の同期は持たない (待たずに先へ進む例外は後述の「終了しないフックは利用者の責務」の2経路だけである)
- **どちらか片方だけ書いてよい**。書かなかった側には器の既定の演出が適用される (`PB-TR-02`)
- フックが受け取るのは**ホスト View だけ**で、背後を覆うオーバーレイには触れない

## ダイアログがたどる状態

演出が入ると、ダイアログには「まだ見えていない」「出ている途中」「出ている」「消えている途中」の区別が生まれる。以降の規則はこの4つの状態で場合分けするため、先に一覧しておく:

| 状態 | 何が起きているか | ライブラリ発の閉鎖信号 (報告・外側タップ・戻る・呼び出し元キャンセル) が来たときの扱い |
|---|---|---|
| **表示前** | show が呼ばれ、器と中身を組み立てている。中身はまだ見えていない | 両フックとも実行せず、演出なしで撤去して結果を配送する (`PB-TR-19`・`PB-TR-20`) |
| **出現中** | オーバーレイのフェードと presentation フックが走っている | 報告・外側タップ・戻るは、出現を**完走させてから**退出へ進む (`PB-TR-05`)。呼び出し元キャンセルだけは presentation を打ち切って退出へ進む (dismissal は実行される。`PB-TR-28`) |
| **表示中** | 出現が終わり、利用者の操作と報告を受け付ける | 退出を始める |
| **退出中** | dismissal フックとオーバーレイの消滅が走っている | 入力は無視され、二度目の閉鎖信号も何もしない (`PB-TR-06`・`PB-TR-22`)。呼び出し元キャンセルだけは実行中の dismissal を打ち切って撤去へ進む (`PB-TR-29`) |

退出が終わると器は撤去され、そこで初めて結果が呼び出し元へ渡る (後述の「結果はいつ返るか」)。OS 発の器の消失 (画面の破棄など) だけは、どの状態からでも直ちに撤去へ進む。

## 既定の演出と、オーバーレイの扱い

何も添付しなければ、器は中身とオーバーレイの**クロスフェード (250 ミリ秒)** で出入りする (`PB-TR-03`)。OS 既定のトランジションは使わない — Android の既定は実質無演出で、既定の見え方が OS 間で割れるためである。

**添付したフックは、既定の演出を置き換える (合成しない)**。slide を指定したのに既定のフェードが重なる、といったことは起きない。片側だけ添付したときも、書いた側は完全に差し替わり、書かなかった側だけが既定になる。

**オーバーレイは中身とは別のレイヤで、器が常に出入りさせる**。フックの有無にかかわらず必ず現れて消え (フェード時間は overlayDuration に従う)、フックからは触れない。

- オーバーレイのフェード**時間**は overlayDuration に従い、中身側の演出と時間を揃えられる。duration を取るプリセット (fade / slide / zoom) は自分の duration を overlayDuration にも設定するため、指定なしで揃う (`PB-TR-16`)
- オーバーレイのフェードの**イージングは器が固定**しており、利用者は指定しない (覆いの出現はモーダルであることの表現で、中身の演出とは責務が別だからである)
- **中身の演出とオーバーレイのフェードは並行して走る**。出現は両方の開始が同時で、**両方が終わって初めて「表示中」**になる。退出も両方を並行に走らせ、両方の完了を待って撤去する (`PB-TR-21`) — 片方が 300 ミリ秒、もう片方が 200 ミリ秒なら、待ち時間は合計ではなく長いほうの 300 ミリ秒になる

## プリセット

定番の演出は**プリセット factory** で一発生成できる。**プリセットが返すのは `DialogTransition` 一式** — presentation / dismissal / overlayDuration がすべて埋まった値 — であり、presentation と dismissal は対称なペアになる (下辺から滑り込んだら下辺へ滑り出す)。片側だけプリセットにしたいときは、プリセットが返した値から presentation か dismissal を取り出し、自作のフックと組み合わせた `DialogTransition` を作ればよい (取り出し方と綴りは各形態の公開面)。

| プリセット | 内容 | 引数 |
|---|---|---|
| fade | 透明度で出入りする | duration / easing |
| slide | 指定した辺から滑り込み、同じ辺へ滑り出す | 出入り口になる辺 + duration / easing |
| zoom | 少し縮んだ状態 (0.8 倍) から等倍へ広がり、同じ倍率へ縮んで消える | duration / easing |
| none | 中身側は無演出。フックは何もせず直ちに戻る | **なし** |

- **duration の既定は 250 ミリ秒**。duration と easing の表し方は形態のネイティブ表現に従い、形態横断の抽象は作らない (綴りと型は各形態の公開面)。easing を省略すると「加速して減速する」標準の曲線になる
- **slide の辺は4つ** — 上 / 下 / 行の始まり側 / 行の終わり側。**行の始まり側 / 終わり側はレイアウト方向に追随**し、右から左へ読む環境では左右が入れ替わる。上 / 下は物理方向で変わらない
- **none は中身側だけを無演出にする**。オーバーレイは既定どおりフェードするため、閉鎖の完了待ちはオーバーレイの分だけ残る (`PB-TR-17`)。覆いまで消したい要求は現時点では受け付けていない

**成立しない duration を渡しても、例外にもオーバーフローにもならず、演出を省いて最終状態へ直ちに飛ぶ。** 0・負値・NaN・無限大、および形態のアニメーション API が扱えない大きさが該当する (どの大きさが扱えないかは形態で違い、各形態の公開面の「framework 固有の注意」が定める)。ミリ秒に落とすと 0 になる正の微小値を同じ扱いにする形態もある (その長さのアニメーションを組む形態との間に、観察できる差はない)。overlayDuration も同じ規則で、この場合オーバーレイは**フェードせずに即座に現れて即座に消える** (覆いそのものが無くなるわけではない) (`PB-TR-18`・`PB-TR-26`・`PB-TR-27`)。

プリセット factory の綴り・引数の型・辺の綴りは各形態の公開面が定める ([iOS](../../ios/api/transition-surface.md) / [Android](../../android/api/transition-surface.md) / [MAUI](../../maui/api/transition-surface.md) の「プリセット factory」)。

## 結果はいつ返るか (ラッチと配送)

演出の完了を待つ以上、「ダイアログが閉じた」と「show が結果を返した」は同じ瞬間ではない。そこで結果の扱いを**ラッチ**と**配送**の2段に分けて定める。

- **ラッチ** — 結果 (completed / cancelled) が**最初の報告で不可逆に確定**すること。**報告**とは、中身のコードが結果報告口を通じて「完了 (結果つき)」か「キャンセル」を伝えることである。以後の報告は何もしない (結果は一度きりという [結果通知のルール](result-notification-semantics.md) の基本ルール3)
- **配送** — ラッチ済みの結果が show の呼び出し元へ**渡る**こと。配送は「dismissal フックとオーバーレイの消滅 (この2つは並行に走る) の両方が完了 → 器の撤去」が済んだ**後**に行う (`PB-TR-10`)

この分け方から次が従う:

- **show が返ったときには、ダイアログはもう画面にない**。撤去前に配送すると、結果を受けて次のダイアログを出す典型的な流れで前のダイアログがまだ見えている状態が生まれる
- **演出を何も添付していなくても、show の完了は既定の退出処理の分 (250 ミリ秒) だけ遅れる** (`PB-TR-13`)。既定も同じ経路を通るためで、show が即座に返ることを前提にしたコードは影響を受ける
- **退出中に二重に報告しても、配送されるのは最初の値**である (`PB-TR-11`)。退出の途中で画面が壊れても、ラッチ済みの値がそのまま配送される (`PB-TR-12`)

## フックが実行される閉鎖と、されない閉鎖

dismissal フックが実行されるのは、**ライブラリが閉鎖を実行する経路**だけである (状態による違いは「ダイアログがたどる状態」の表も参照):

| 閉鎖のきっかけ | dismissal フック |
|---|---|
| 結果の報告 (completed / cancelled) | 実行する |
| 外側タップ (`PB-TR-07`) | 実行する |
| Android の戻るボタン | 実行する |
| 呼び出し元のキャンセル — **表示中**に起きた場合 (`PB-TR-08`) | 実行し、**最後まで完遂する** (キャンセルの通知が伝播する形態でも、待機を打ち切ったあとで完遂する。`PB-AA-03`) |
| 呼び出し元のキャンセル — **出現中**に起きた場合 (`PB-TR-28`) | presentation を打ち切って退出へ進み、**dismissal は実行する** |
| 呼び出し元のキャンセル — **すでに退出中**に起きた場合 (`PB-TR-29`・`PB-TR-24`) | 実行中の dismissal を**打ち切って**撤去へ進む (脱出口。後述) |
| OS 発の器の消失 — 画面の破棄や、ライブラリを経由せずに提示関係が解かれた場合 (`PB-TR-09`) | **実行しない** |

OS 発の消失で実行しないのは、器がすでに画面を失っており演出が物理的に成立しないためである。この経路では、未確定なら cancelled をラッチし、実行中のフックがあれば打ち切って (待つのをやめて) 直ちに撤去・配送する (`PB-TR-23`)。ダイアログが重なって出ているとき、iOS で下の段を先に閉じると上の段が消えるが、それもこの経路にあたる ([多段表示のルール](multi-display-semantics.md))。

実行の順序については次が成り立つ:

- **表示前 (中身が見える前) の閉鎖では、両フックとも実行しない**。演出なしで撤去して配送する — 中身を作る factory の中で即座に報告した場合や、show 直後のキャンセルがこれにあたる (`PB-TR-19`・`PB-TR-20`)
- **出現の途中で報告・外側タップ・戻るが来ても、出現を完走させてから退出を始める** (`PB-TR-05`)。途中で折り返すと、中断位置からの退出演出が定義できないためである (呼び出し元キャンセルだけは例外で、出現を打ち切って退出へ進む。`PB-TR-28`)
- **dismissal フックは高々1回**。報告の直後に外側をタップするなど複数の閉鎖信号が来ても、最初の1つだけが退出を始める (`PB-TR-06`)
- **退出中の入力は無視される** (外側タップ・戻る・中身の操作。`PB-TR-22`)

## 演出が失敗したとき

**演出の失敗は結果の失敗ではない。** フックが投げた失敗 (その形態の言語規約での例外・エラー) は器が吸収し、開発中のログに残すだけで、show を失敗させない。

- presentation フックが失敗しても、ダイアログは「表示中」へ進んで報告を受け付ける (`PB-TR-14`)。フックが途中まで変えた見た目 (透明度や位置) を**ライブラリは元に戻さない** — 中途半端な状態が残るのは利用者の責任である
- dismissal フックが失敗しても、器の撤去は続行し、ラッチ済みの結果を配送する (`PB-TR-15`・MAUI は `PB-MA-03`)

利用者が報告済みの業務上の結果を、演出のバグで失わせないための規則である。

## 終了しないフックは利用者の責務

**フックが有限時間で完了することは、利用者が守る前提条件である。ライブラリはタイムアウトを設けない。** 完了しないフックは契約違反であり、その間ダイアログは撤去されず結果も配送されない (症状は「ダイアログが閉じない」として画面に見える)。

上限で打ち切る設計を採らないのは、正しく書かれた長い演出まで打ち切られる別の誤動作が生まれ、原典の「250 ミリ秒を超える演出は中断されうる」という脆さを値を変えて再生産することになるためである。

代わりに、契約違反に陥っても次の2経路では器がフックを見捨てて先へ進む (**脱出口**)。呼び出し元のキャンセルは**すでに実行中のフック**を打ち切る経路で、この経路を持つ形態でのみ働き (後述)、キャンセル時点の状態で効き方が変わる。

| 脱出口 | 起きること |
|---|---|
| 呼び出し元のキャンセル (**退出中**) | 実行中の dismissal を打ち切り、完了を待たずに撤去・配送する (`PB-TR-24`・`PB-TR-29`) |
| 呼び出し元のキャンセル (**出現中**) | presentation を打ち切って退出へ進む (この場合 dismissal は通常どおり実行される。`PB-TR-28`) |
| 呼び出し元のキャンセル (**表示中** — フックが走っていない状態) | 脱出ではなく通常の退出で、dismissal は最後まで実行される |
| **OS 発の器の消失** | 上記のとおり直ちに撤去・配送する (`PB-TR-25`) |

**MAUI には呼び出し元キャンセルの経路がないため、脱出口は OS 発の消失だけ**である。

開発支援として、**デバッグビルドではフックが一定時間 (現在は 5 秒) を超えたときに警告ログを出す**。これは気づきのための閾値であって契約ではなく、打ち切りもしない。「デバッグビルド」の主語は形態で違う — iOS は**ライブラリ自身**のビルド構成 (ソース配布では利用者アプリの構成と一致する)、Android は**提示先アプリ**がデバッグ可能かどうかで決まる。MAUI はそれぞれのネイティブ側の判定に従う。

## 呼び出し元のキャンセルはどう観察されるか

呼び出し元がキャンセルされたときの見え方は、その形態の言語規約に従う (`PB-TR-08`)。これは [結果通知のルール](result-notification-semantics.md) の「呼び出し元をキャンセルしたときの見え方」と同じ差であり、ここでは演出との関わりだけを述べる:

| 形態 | 呼び出し元が観察するもの |
|---|---|
| iOS Native | show が結果として cancelled を返す (失敗としては伝わらない) |
| Android Native / KMP | 言語のキャンセル規約どおりキャンセルの通知が伝播する (内部の結果は cancelled でラッチ済み) |
| MAUI | **この経路がない** — show が呼び出し元のキャンセル手段を引数で受け取らない |

キャンセルの通知がどの型で届くか、iOS で返る結果の綴りがどうなるかは、各形態の Dialog 公開面の「失敗とキャンセルの形」が定める ([iOS](../../ios/api/dialog-surface.md) / [Android](../../android/api/dialog-surface.md) / [MAUI](../../maui/api/dialog-surface.md) / [KMP](../../kmp/api/dialog-surface.md))。

**表示中**にキャンセルされたときは、キャンセルの通知が伝播する形態でも dismissal フックと撤去を最後まで完遂する (`PB-AA-03`)。「キャンセルしたら演出だけ中途半端に残る」ことがないようにするためである。**出現中**なら presentation だけを打ち切って退出へ進み (dismissal は実行される)、**すでに退出中**なら実行中の dismissal を打ち切る (前節の脱出口)。

## 保証すること

- **演出を何も添付していない呼び出しは、書き換えなしでそのまま動く** (この演出機構を導入する前から書かれているコードも同じ)。ただし観察できる変化が2つある — 既定の演出が OS 既定からライブラリのクロスフェードに変わること、show の完了が既定の退出処理の分だけ遅れることである
- **添付したフックは、そのダイアログの出入りを完全に置き換える**。既定と混ざらないため、指定した演出がそのまま見える
- **show が結果を返したとき、ダイアログはすでに撤去されている**。ラッチと配送を分けているため、退出中に何が起きても配送される値は最初に確定した結果である
- **出現まで進んだダイアログは、ライブラリ発のどの閉鎖経路でも退出演出を実行してから閉じる** (出現中に閉鎖信号が来た場合も含む。例外は脱出口が働いたときだけで、まだ表示前なら演出そのものが始まっていない)。キャンセル系 (外側タップ・戻るボタン) はアプリ側から割り込めない閉鎖であり、ここで演出できないと「OK のときだけ演出がある」非対称な見え方になる
- **フックがどう失敗しても、show は結果を返す**。演出の失敗もダイアログの結果には影響しない
- **中身を従来 View 系と宣言的 UI 系のどちらで書いても、フックの形と観察できる挙動は同じ**である ([登録と表示の呼び出し面のルール](registration-show-semantics.md))

## してはいけないこと

- **show の引数で演出を渡す形を作らない**。供給点は添付だけに保つ
- **静的メタ属性の値オブジェクトに演出のプロパティを持たせない**。静的メタ属性は等値比較できる値オブジェクトとして定義されており、関数を混ぜるとその契約が壊れる ([core/ADR-0015](../../../decisions/core/0015-attribute-supply-content-attachment.md))
- **無演出のプリセットに引数を持たせない**。無演出に時間やイージングを与える意味がない
- **添付した演出を既定の演出と合成しない**。指定したとおりに動かなくなり、予測可能性が壊れる
- **フックにオーバーレイを渡さない**。覆いの見え方まで利用者責務にすると、モーダルであることの表現が形態ごとに割れる
- **フックの完了に上限を設けて打ち切らない** (前節の理由)。同じく、フックの失敗で show を失敗させない
- **初回レイアウトパス完了後の添付変更に追随させない** (属性と同じ規律)

## 用語

| 用語 | 意味 |
|---|---|
| 形態 | 本ライブラリを利用できる4つの入口 (iOS Native / Android Native / MAUI / KMP) |
| 技術系 | 中身を書く技術の2系統。従来 View 系と宣言的 UI 系 (それぞれの実体は各形態の公開面) |
| 器 | ライブラリが中身を載せて画面に出すための入れ物。オーバーレイと中身を載せる View を抱え、出入りの演出を駆動する |
| 中身 | ダイアログとして表示される、利用者が書いた表示物 (factory が返すもの)。本文では中身の描画対象を指して「中身側」とも書く |
| ホスト View | 器の中で中身を載せている View で、フックが受け取るもの。宣言的 UI の中身では宣言的 UI を包むプラットフォーム View がこれにあたる |
| フック | 出入りの演出の実体になる非同期の関数 (presentation / dismissal) |
| オーバーレイ (覆い) | ダイアログの背後を覆う面。色は器の静的メタ属性で決まり ([レイアウトのルール](layout-semantics.md))、出入りのフェードは器が常に行う |
| プリセット | 定番の演出一式 (`DialogTransition`) を一発生成する factory (fade / slide / zoom / none)。中身を作る factory とは別物 |
| 報告 | 中身のコードが結果報告口を通じて「完了 (結果つき)」「キャンセル」を伝えること ([結果通知のルール](result-notification-semantics.md)) |
| ラッチ | 結果が最初の報告で不可逆に確定すること |
| 配送 | ラッチ済みの結果が show の呼び出し元へ渡ること。退出と撤去の後に行う |
| 添付 | ダイアログの中身の定義に属性や演出を結びつける供給経路 ([レイアウトのルール](layout-semantics.md)) |
| 原典 | 移植元の AiForms.Maui.Dialogs |
