# Loading のルール

この文書は、全形態 (iOS Native / Android Native / MAUI / KMP) 共通の「処理中に画面全体の操作をブロックしてインジケータを表示する機能」のルールを定める。読むと、呼び出し面がどんな操作で構成されているか、複数の処理が同時に使ったときに何が起きるか (合流)、ダイアログとの重なり、見た目のカスタマイズの2経路 (styling とカスタム View) で何が保証されるかが分かる。ダイアログ側の [登録と表示の呼び出し面のルール](registration-show-semantics.md) と [レイアウトのルール](layout-semantics.md) を先に読むと分かりやすい。

- **この文書が正であり、実装はここに合わせる**。core は「全形態が共有する契約」の層 (層の区分は [concepts 配置ルール](../../rules.md))
- 公開名の綴り・署名・コード例・framework 固有の注意は各形態の公開面が持つ (末尾の「形態別の公開面」)

用語 (ダイアログ側の概念文書と共通):

| 語 | 意味 |
|---|---|
| **器** | コンテンツを画面に載せる提示コンテナ。覆い (背景を暗くする層)・配置・出入りの演出を担い、中身の View とは分離されている |
| **添付** | コンテンツ定義 (View / ViewModel) に属性オブジェクトを付けて器メタ属性を供給する方法 (詳細は [レイアウトのルール](layout-semantics.md)) |
| **VM** | ViewModel。表示に使う状態の運び手 |
| **移植元** | 本ライブラリの前身 AiForms.Maui.Dialogs |

## 公開面の構成

公開 API は Dialog と同じ流儀 (契約 interface + 既定シングルトン — core/ADR-0002) で、Dialog とは別の面として提供する。契約の型は全形態で `KsLoading` である (MAUI だけ interface の接頭辞が付く)。既定シングルトンの綴りは形態ごとに違い、各形態の公開面が定める。

操作は4つで、意味は全形態で同じである:

| 操作 | 意味 |
|---|---|
| 表示 (show) | 合流1件ぶんの表示を開始する。メッセージ省略時は styling の既定メッセージ (未設定ならインジケータのみでメッセージは表示しない) |
| 閉鎖 (hide) | 合流数によらず**即閉じる**。走行中の処理は継続する |
| メッセージの差し替え (setMessage) | 表示中のメッセージを差し替える (後勝ち)。合流には関与しない (「合流のルール」参照) |
| スコープ形 (start) | 処理ブロックを渡す形 (移植元 StartAsync 相当)。開始→処理実行→終了が対になり、処理の戻り値をそのまま返す |

スコープ形の処理には**進捗報告口** (進捗値を渡すコールバック) が渡る。形は形態ごとのイディオムに従い、綴りは各形態の公開面が定める。値は 0〜1 (範囲外は 0〜1 に丸める)、表示への反映は後勝ち。ストリーム API (逐次列の受け取り) は持たない。

表示の指定は置き場所 (`DialogPlacement`) を引数で渡せる。呼び出しは任意スレッドからできる (内部で main へ移す — Dialog 面と同じ)。

カスタム View 版の表示とスコープ形には、VM の**インスタンス**を渡す形・登録せずに factory を渡す**インライン**の形に加えて、VM の**型**だけを渡す**型指定**の形がある (core/ADR-0035。Dialog の型指定 show と同型 — [ViewModel 主導の呼び出しのルール](model-binding-semantics.md))。型指定の形では、ライブラリが専用レジストリの VM factory で VM を生成し、configure (省略可・非同期可) を完了させ、進捗受け口を紐付けてから、登録済みの View factory で中身を作って表示する。置き場所は型指定でも引数で渡せる。

## 合流のルール (多重利用)

重なった利用は**1つの表示に合流**し、表示は最初の開始から最後の終了まで継続する (core/ADR-0024)。状態の正は OS プロセス内に1つの内部 coordinator が持ち、既定シングルトン・DI 用インスタンス・MAUI bridge・KMP actual のどの入口から使っても同じ表示に合流する (core/ADR-0027)。

**世代** = 1回の表示のまとまり (最初の開始から、閉鎖または合流数 0 による表示消滅まで) を識別する単位。

- 渡された処理は表示状態によらず**必ず実行される**。「必ず」は合流・表示状態を理由に保留・放棄しないという意味で、構成ミス (未登録 VM・カスタム View factory の失敗等 — 後者は core/ADR-0033 で開始そのものの失敗に合流) は実行前に fail-fast で失敗してよい
- 提示環境が無い (画面が出せない) 場合、表示は行われないことがあるが、処理は実行されスコープ形は結果を通常どおり返す
- 処理の失敗も合流1件の終了として数え、例外は呼び出し元へ伝播する
- 閉鎖は現在の世代を終わらせる: 閉鎖後に始まった表示は新しい世代 (合流数は 1 から数え直し) で、旧世代の処理の完了で閉じず、旧世代の遅延進捗も受け取らない。メッセージの差し替えだけは世代に紐づかず、常に現在の表示に効く (メッセージ更新を世代に紐づける API 経路が存在しないため)
- 「最新の報告が勝つ (後勝ち)」の「最新」は coordinator の**受理順** (UI スレッド上の直列化) で定義される。処理の終了通知は、その処理が発行済みの進捗報告の受理後に届く

構成ミスの失敗が Swift 側へどう届くかは KMP の公開面が定める ([KMP の Loading 公開面](../../kmp/api/loading-surface.md))。

### 型指定の形と合流

型指定の形は VM の生成と configure を先に済ませ、そのあとは**インスタンス渡しとまったく同じ合流判定**に入る。判定は要求が coordinator に受理された時点、つまり configure 完了後である。非同期 configure の間に別の開始が先に表示を確定していれば、その呼び出しは合流側になる — 生成した VM は表示に使われず (中身は最初の開始のもの)、View factory も呼ばれない。進捗は既存の規則どおり表示中のコンテンツへ受理順の後勝ちで届く。

VM factory と configure の失敗 (キャンセルを含む) は提示前の失敗であり、表示にも合流にも進まず呼び出し元へ伝播する。型指定のスコープ形では処理ブロックも実行しない (fail-fast)。型指定経路は VM factory と View factory の両方を呼び出し時点で解決するので、どちらが欠けていても構成ミスとして失敗する。種類は区別し (「VM factory 未登録」と「View factory 未登録」)、判定は VM factory が先である。

KMP の共有コードの型指定の形は、VM の生成と configure を共有コード側 (呼び出し元の文脈) で済ませてから既存のインスタンス渡しの経路へ渡す。したがって合流判定はインスタンス渡しと同じ時点で行われ、VM factory / configure の失敗は上と同じく呼び出し元へ伝播する。VM factory の登録先が共有コード側であることと View factory の解決が各 OS 側で後から起きることは [ViewModel 主導の呼び出しのルール](model-binding-semantics.md) の「KMP での見え方」が持つ。

## 器の性質 (ダイアログとの重なり)

Loading の器は、Dialog の器の提示経路 — ダイアログを重ねて出すときの OS の重なり管理 ([多段表示のルール](multi-display-semantics.md)) — に**参加しない**専用オーバーレイで、ダイアログ表示中は視覚・入力の双方で**ダイアログより手前**に出る (core/ADR-0022。実装形は iOS = key window 直貼り / Android = 専用の全画面透過 Window — core/ADR-0026)。[Toast](toast-semantics.md) と同時に表示された場合も、起動順によらず常に Loading が前面 (core/ADR-0030)。

- レイアウト系の器メタ属性 (基準領域・余白・比率サイズ・覆いの色・置き場所) は Dialog と**同じ意味・同じ供給経路と優先順位** ([レイアウトのルール](layout-semantics.md)) で効く
- 外側タップで閉じる属性だけは常に無効 — **Loading はユーザー操作では閉じない** (外側タップは背後にも透過しない)
- 演出はカスタム View 版のみ `DialogTransition` 添付で差し替えられる ([トランジションのルール](transition-semantics.md) の出入りフックがそのまま効く。同ルールの「結果のラッチと配送」は、結果を返すダイアログ向けの仕組みなので Loading では出番がない)。既定ローディングはライブラリ既定のクロスフェード固定

## 既定ローディング (内蔵コンテンツ) と styling

引数なしで出せる既定ローディング (スピナー + メッセージ + 進捗表示) は、カスタム View 版と同じ共有部品に載るライブラリ同梱コンテンツとして実現されている (core/ADR-0023)。styling は値オブジェクトにまとめ、シングルトンの設定プロパティで一括設定する。表示 API にスタイル引数は無い。

- styling の項目: インジケータ色 / メッセージのフォントサイズと色 / 既定メッセージ / 進捗フォーマット。既定値は白インジケータ・白 14pt・既定メッセージなし (内蔵コンテンツのメッセージは太字固定で、太さは styling の項目ではない)
- 進捗フォーマットは書式文字列ではなく**フォーマット関数** (メッセージと進捗を受け取って表示テキストを返す。進捗は未報告時に空値)。既定実装はメッセージ + 改行 + パーセント表示 (小数なし)
- 器メタ属性は、既存の静的メタ属性の値オブジェクトを再利用した設定プロパティで受ける — 既定ローディングには利用者の添付面が無いため、これが「添付」相当になる (外側タップで閉じる属性は設定しても無効のまま)。置き場所は設定に含まれず、表示 API の引数だけで指定する
- styling・器メタ属性とも器は**各表示の開始時に読む**。設定変更は次の表示から効き、表示中の変更は効かない
- KMP の共有コードには styling / 器メタ属性の API を公開しない — 色型が OS 共通コードとの境界を渡らないため (設定は各 OS 側・呼び出しは共有コード側、という静的メタ属性と同じ非対称。[KMP の Loading 公開面](../../kmp/api/loading-surface.md))

## カスタム View 版 (登録と進捗配送)

カスタム View は Dialog とは別の **Loading 専用レジストリ**に登録する (core/ADR-0025)。レジストリのエントリは VM 型キーごとに **View factory と VM factory の 2 スロット** (core/ADR-0035) で、再登録はスロット単位の後勝ち、表示時の解決は呼び出し時点のスナップショットによる (表示中の再登録は出ている表示の中身と進捗転送先を変えない)。生成は使い捨て — 表示のたびに factory で作り、閉じたら破棄する (core/ADR-0005 踏襲)。View factory の登録形は Dialog と同型の技術別オーバーロード (従来 View 系と宣言的 UI 系) だが、結果を返す口は無い — Loading は結果を持たないため。表示は VM を渡す形・インライン factory 版・型指定の形 (VM factory が要る)。

進捗のカスタム View への配送は、**VM が `LoadingProgressReceiver` (進捗値を受け取る 1 メソッドだけの面) を実装している場合にライブラリが UI スレッド上で転送する**。未実装なら転送されない (エラーにもならない)。宣言的 UI では VM の観測がそのまま表示更新になる。型指定の形で生成した VM も同じで、紐付けは configure 完了後・View 生成前に行われる。

## 持たない機能

| 持たないもの | 理由 |
|---|---|
| 表示スコープ (移植元の「現在のページだけを覆う」指定) | Loading は常にウィンドウ全体を覆う。移植元で iOS のみ有効の半端な機能で、必要なら既存 API を壊さず後から追加できる |
| 表示中の回転ロック (移植元の iOS 向け指定) | 移植元の Loading では事実上ノーオペだった。表示中の回転は既存の再配置規則 ([レイアウトのルール](layout-semantics.md)) に従う |
| 既定ローディングへの演出指定 | 演出の供給経路を `DialogTransition` 添付1本に保つ。差し替えたければカスタム View を使う |
| 進捗のストリーム API | スコープ形の報告口で足りる |

## 保証すること

- どの入口 (シングルトン / DI インスタンス / MAUI / KMP) から使っても、同一プロセス内の Loading 表示は同時に1つ
- 渡された処理は必ず実行され、要求が黙って消えることはない
- 閉鎖の戻りと、合流を 0 にする最後のスコープ形の戻りは、器の撤去完了後 (戻った時点で操作ブロックは解除済み)
- 表示の戻りは操作ブロックが成立した時点で、入場の演出の完了は待たない。合流を 0 にしない終了 (先に終わった参加者) は器の撤去を待たずに戻る
- 型指定の形で VM factory または configure が失敗した開始は、表示にも合流にも進まず、スコープ形の処理ブロックも実行しない

## してはいけないこと

- **Loading をユーザーが閉じられる前提の UI にしない**: 閉じる手段は閉鎖操作 / 処理の完了だけ。キャンセルさせたい処理は、キャンセル操作を持つ Dialog を使う
- **閉鎖を「処理の中断」として使わない**: 閉鎖は表示を消すだけで、走行中の処理は続く。表示なしで走り続けることの妥当性は呼び出し側の責任
