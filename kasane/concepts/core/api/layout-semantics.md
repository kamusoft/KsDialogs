# レイアウトのルール (ダイアログのサイズと位置の決まり方)

この文書は、全形態 (iOS Native / Android Native / MAUI / KMP) 共通の「ダイアログがどれだけの大きさで画面のどこに出るか」と「外側をタップしたら閉じるか」のルールを定める。読むと、ダイアログの器に渡せるメタ属性とその既定値、属性をどこから渡せて競合したらどれが勝つか、最終的な位置とサイズがどう導かれるかが分かる。

**この文書が正であり、実装はここに合わせる**。根拠決定は [core/ADR-0007](../../../decisions/core/0007-layout-spec-not-shared-code.md)・[core/ADR-0008](../../../decisions/core/0008-layout-attributes-deliberate-deviations.md)・[core/ADR-0009](../../../decisions/core/0009-layout-spec-test-case-table.md)・[core/ADR-0014](../../../decisions/core/0014-contract-keeps-only-container-meta-attributes.md)・[core/ADR-0015](../../../decisions/core/0015-attribute-supply-content-attachment.md) (いずれも最初の実装での検証を経て accepted 済み)。

読む前に押さえておく前提:

本文中の**原典**は AiForms.Maui.Dialogs (本ライブラリの移植元) を指す (参照ルールは [移植元 AiForms.Maui.Dialogs の参照](../../../handbook/cross/aiforms-origin-reference.md)、リポジトリの在り処は [参考リポジトリの在り処](../../cross/reference/reference-repositories.md) が定める)。本文中の**現行実装**は、この契約を導入する前の本ライブラリのコード (原典から移植して動いている状態) を指す。原典と現行実装は別物で、既定値の根拠としてどちらを採ったかは節ごとに明示する。

- 規則と対になる**共通ケース表**を単一の正として持ち、本文の規則から機械的に導いた期待値を固定している (表の形と運用は [レイアウト共通ケース表と OS 差の統制](../architecture/layout-case-table.md))
- core は「全形態が共有する契約」の層 (層の区分は [concepts 配置ルール](../../rules.md))。公開名・署名・コード例は各形態の公開面が持つ (末尾の「形態別の公開面」)

レイアウト計算の実体を持つのは iOS / Android の Native 2 実装だけで、MAUI / KMP は属性を無変換で渡すパススルーである ([core/ADR-0001](../../../decisions/core/0001-native-independent-thin-wrappers.md))。実装機構は各 OS の自由で、ここに書かれた観察可能な結果を満たせばよい。

## 前提: ダイアログの呼び出し方

本文を読む前に、このライブラリのダイアログの使い方だけ押さえておく (詳細は [結果通知のルール](result-notification-semantics.md))。利用者はダイアログの中身になる View をあらかじめ**登録 (register)** しておき、**show** で表示して結果を待つ。結果は **completed (OK で閉じた。結果値を持つ)** と **cancelled (取り消された。結果値を持たない)** の2種類しかなく、そのどちらかがちょうど1回返る。結果と状態を運ぶのが **ViewModel** で、show にはこの ViewModel を渡す。

この文書が扱うのは、その表示が「どれだけの大きさで画面のどこに出るか」と「外側をタップしたら閉じるか」だけである。

## 器が持つメタ属性

契約が持つのは、**器 (ダイアログコンテナ) にしか実現・計算できないメタ属性だけ**である ([core/ADR-0014](../../../decisions/core/0014-contract-keeps-only-container-meta-attributes.md))。角丸・枠線・自分自身の大きさのように、ダイアログの中身の View が自力で表現できるものは View の責務であり、契約には持たない。器が引き受けるのは「画面のどこに、画面の何割の大きさで置くか」「背後をどう覆うか」「外側タップで閉じるか」— いずれも画面 (window) を知っている器にしか決められないことだけである。

ここでいう「属性」は設定値のことであり、C# の Attribute や Kotlin のアノテーションのような言語機能ではない。

メタ属性は2つの値オブジェクトに分かれる。分ける基準は**呼び出しごとに変えたいニーズがあるか**である:

- **静的メタ (6個)** — その View の性質として決まるもの。表示のたびに変えるものではない
- **置き場所 `DialogPlacement` (動的メタ 4個)** — 置き場所 (fill を選んだ軸ではサイズも決まる)。同じ View を呼び出しごとに違う位置へ出したいニーズがある

どちらも全フィールドに既定値があり、何も渡さなければすべて既定値で動く。数値はいずれも倍精度浮動小数点数で、長さを表すもの (余白・offset) は**論理単位** (iOS = pt / Android = dp)、比率は無次元である。

### 静的メタ属性

| 属性 | 既定値 | 意味と無効値の扱い |
|---|---|---|
| layoutArea | 可視領域 | サイズ・位置計算の基準領域 (後述)。ウィンドウ全体か可視領域かの2択 |
| dialogMargin | 全辺 24 | 基準 rect の各辺から控除する余白。辺ごとに違う値でよい。負の値の辺は、その辺だけ 0 に丸める |
| proportionalWidth / proportionalHeight | -1 (未指定) | 基準 rect R の軸長に対する比率。0 < 値 ≤ 1 で比率指定が成立する。1 を超える値は 1 に丸め、**0 以下はすべて (既定の -1 を含む) 未指定**として扱う |
| overlayColor | 黒 40% | ダイアログの背後を覆う色。色の表現は形態ごとのネイティブ色型で、境界を渡るときは ARGB 32bit 整数になる |
| isCanceledOnTouchOutside | true | 外側タップで閉じるか (後述の「外側タップで閉じる」) |

### 置き場所 (動的メタ属性)

| 属性 | 既定値 | 意味 |
|---|---|---|
| horizontalAlignment / verticalAlignment | 中央 | 配置。`DialogAlignment` が持つ4値 (先頭寄せ / 中央 / 末尾寄せ / fill) から選ぶ。fill は位置だけでなくサイズも有効領域 (基準領域から dialogMargin を控除した矩形。後述) いっぱいに広げる |
| offsetX / offsetY | 0 | 配置後の平行移動。+X が右 / +Y が下 |

数値に共通の規則として、**非有限値 (NaN / ±Infinity) はその値の既定値**として扱う。dialogMargin では辺ごとに判定するため、NaN の辺は既定の 24 に戻り、負の辺は 0 になる (非対称に見えるが、前者は「値が壊れている」ので既定へ、後者は「負の余白」に意味がないので下限へ、という別の理由による)。上の表の個別規則 (比率の丸め・負の Margin 辺) は、この一般規則に加わる具体化である。

属性の綴りは形態ごとの言語慣習に従う (識別子の写像は [cross/ADR-0005](../../../decisions/cross/0005-public-identifier-mapping.md)) が、**意味と既定値は全形態で同一**である。具体的な綴りと型は各形態の公開面が持つ (末尾の「形態別の公開面」)。この文書が名前を挙げるのは、4 形態すべての公開面に同じ綴りで存在する型 (`DialogPlacement` / `DialogAlignment`) だけで、それ以外は日本語で書く。

### 原典と既定値が違う3つ

overlayColor (原典は透明 → 黒 40%)・dialogMargin (原典 0 → 全辺 24)・layoutArea (原典はウィンドウ全体相当 → 可視領域) の3つは、原典と既定値が異なる。理由はいずれも**現行実装の挙動をそのまま既定として維持する** (オーナーがそう判断した) ためで、「属性を何も指定しなければ今までどおりに出る」が全 OS で成り立つようにしている ([core/ADR-0008](../../../decisions/core/0008-layout-attributes-deliberate-deviations.md))。isCanceledOnTouchOutside は原典の既定 (true) をそのまま踏襲する — 現行実装にはこの機構自体が無く、維持すべき現行挙動が存在しないためである。

## 属性の渡し方と優先順位

属性は**ダイアログの中身 (View) の定義に添付して渡す**のが主経路である ([core/ADR-0015](../../../decisions/core/0015-attribute-supply-content-attachment.md))。原典の思想と同じく「View が自分の性質を持つ」形にし、登録 (register) と表示 (show) の呼び出しを軽いまま保つ。

添付の面 (拡張プロパティ・modifier・宣言関数・添付プロパティ) の書き方は形態と UI 技術ごとに違い、各形態の公開面が定める。書き方は違っても、**優先順位も採用時点も全形態で同一**である。宣言的 UI (SwiftUI / Compose) では、添付を初回表示までに評価される場所に書く必要がある点にだけ注意する (遅延評価されるスコープの中に書くと初回表示に効かない) — 詳細は [登録と表示の呼び出し面のルール](registration-show-semantics.md)。

**優先順位は「show 引数 > コンテンツ添付 > 契約既定値」**。渡せるものには非対称がある:

- **置き場所は添付でも show 引数でも渡せる**。show 引数で渡した値は、添付された置き場所を**オブジェクトまるごと置換**する。フィールド単位では合成しない — 全フィールドに既定値がある値オブジェクトでは「省略した」と「既定値を明示指定した」を区別できず、部分合成にすると呼び出し側が意図しない値を拾う
- **静的メタ属性は添付でしか渡せない**。show に静的メタの引数は設けていない。背後の覆いや外側タップの扱いを呼び出しごとに変える誤用を、供給点の側で構造的に防いでいる
- KMP の共有コードから渡せるのも置き場所 (`DialogPlacement`) だけで、静的メタ属性は共有コードの境界を渡らない — 中身の View が各 OS 側で組み立てられるため、添付も各 OS の面で行う ([KMP の Dialog 公開面](../../kmp/api/dialog-surface.md) の「共有コードには添付の面が無い」)
- ダイアログの **ViewModel には属性を一切持たせない**。ViewModel は結果と状態の運び手であり、UI の置き場所を持たない ([結果通知のルール](result-notification-semantics.md))

### いつの値が使われるか

基準になる時点は**初回のネイティブレイアウトパス完了時点** — 器を画面に載せたあと、OS が最初にサイズと位置を確定させる処理が終わった瞬間 — の1点だけである。

- **器が採用する実効値は、この時点で添付されている値**である。実装がいつ読み取るかは自由だが、どのタイミングで読んでも「この時点の添付値と一致する」ことが契約であり、採用される値は一意に決まる
- したがって、**show を呼んだあとでもこの時点までに書き換えた値は採用され得る**。この時点より後に添付を書き換えても、位置・見え・外側タップの挙動は変わらない
- ダイアログの中身のサイズ (後述の**内容サイズ**) も、同じレイアウトパスの中で確定する

サイズが決まる時点と属性が決まる時点をこの1点にそろえているため、「表示されたときには実効値も内容サイズも確定済み」を1つの境界だけで保証できる。

### 表示中に画面のほうが変わったとき

凍結されるのは**属性の実効値**であって、計算結果の rect ではない。表示中にウィンドウの寸法や可視領域の insets が変われば、**凍結済みの実効値のまま新しい寸法・insets で同じ手順を回し直し、ダイアログを再配置する**。対象になるのは次の変化で、いずれも Scenario ID を持つ ([core/ADR-0016](../../../decisions/core/0016-behavior-spec-scenario-tests.md))。Scenario ID は挙動を固定するテストの識別子で、rect の期待値を固定する共通ケース表のケース ID とは別の体系である:

- 画面の回転 (`PB-WN-01`) — 原典 iOS の「提示後はサイズを固定する」挙動は継承しない
- insets は変わらずウィンドウ寸法だけが変わる場合 (マルチウィンドウのリサイズなど。`PB-WN-02`)
- ウィンドウ寸法は変わらず insets だけが変わる場合 (システムバーの出入りなど。`PB-WN-03`)

**ソフトキーボード (IME) による領域の変化は対象外である。キーボードが出てもダイアログは動かない** — 位置をずらす・縮めるといったキーボード回避は行わない。原典にもない機能であり、入れると「どの入力欄を見せるか」という別の関心をライブラリが抱え込むことになる。

## 基準領域

layoutArea は、サイズと位置の計算をどの矩形を基準に行うかを選ぶ。選べるのは次の2つで、既定は可視領域である:

| 選択肢 | 基準になる矩形 |
|---|---|
| ウィンドウ全体 | ダイアログを載せるウィンドウの全体 |
| 可視領域 (既定) | window から insets (システムバーなどが占める4辺の幅) を控除した領域 |

可視領域の実体は OS で違う — iOS は safe area、Android はシステムバーを除外した領域がこれにあたる。cutout などの細部は各 OS の標準的な定義にそのまま従い、本文書では規定しない。

原典はこの選択を真偽値のプロパティで持っていた。真偽値では「何を基準にするのか」が名前から読めず、両 OS とも垂直方向にしか効かない半端な実装の温床になっていた。列挙に置き換えたうえで**水平・垂直の両軸に効かせる** ([core/ADR-0008](../../../decisions/core/0008-layout-attributes-deliberate-deviations.md))。将来 3つ目の基準が必要になっても、既存の指定を壊さずに足せる。

## 最終 rect の決め方 (軸ごとの手順)

水平・垂直の**各軸で独立に**、次の順で一意に決まる (軸をまたぐ依存はない):

| 手順 | 決めること | 規則 |
|---|---|---|
| 1 | 基準 rect R | layoutArea に従い、ウィンドウ全体か可視領域 (= window − insets) |
| 2 | 有効領域 A | R からその軸の先頭側・末尾側の dialogMargin を控除した範囲 (下の数式) |
| 3 | サイズ s の選択 | 比率指定 > fill 配置 > 内容サイズ の優先順で、最初に指定のあるものを使う |
| 4 | クランプ | A の軸長を超えないように s を切り詰める |
| 5 | 位置 p | 配置 (先頭寄せ / 中央 / 末尾寄せ) から求める。サイズ側で fill が選ばれなかった軸の fill 配置は中央として扱う |
| 6 | offset の適用 | p に offset を加える。**クランプしない** |
| 7 | 最終 rect | 得られた (p, s) がその軸の最終 rect |

各手順の数式は次のとおり (先頭側 = 水平なら左 / 垂直なら上、末尾側 = 右 / 下):

```
A.min      = R.min + 先頭側 margin
A の軸長   = max(0, R の軸長 − 先頭側 margin − 末尾側 margin)
A.max      = A.min + A の軸長

s (比率指定) = 比率 × R の軸長
s (fill)     = A の軸長
s (クランプ) = min(s, A の軸長)

p (先頭寄せ) = A.min
p (中央)     = A.min + (A の軸長 − s) / 2
p (末尾寄せ) = A.max − s
p (offset)   = p + offset
```

サイズ側で fill が選ばれた軸では s = A の軸長なので、上のどの位置の式でも p = A.min に一致する。余白を控除しすぎて A の軸長が 0 になっても A.min は上の式のまま定義され、以降の手順が成立する (このとき s = 0 で位置は A.min に確定する)。View 自身が宣言する大きさは「内容サイズ」として扱う (器に明示サイズを渡す属性は持たない — [core/ADR-0014](../../../decisions/core/0014-contract-keeps-only-container-meta-attributes.md))。

比率サイズの基準は R (dialogMargin 控除前) で、fill とクランプの基準は A (控除後) である。比率は「ウィンドウ / 可視領域に対して何割」の意味を保ち、dialogMargin は必ず最後に上限として効く。

```
window                              layoutArea = 可視領域のとき
┌─────────────────────────┐
│  insets.top             │         R = window − insets (システムバー除外)
│  ┌──── R ────────────┐  │         A = R − dialogMargin
│  │  ┌─── A ───────┐  │  │         s = 手順3〜4 で決まるサイズ
│  │  │   ┌─rect─┐  │  │  │         p = 手順5 の位置 (+ offset)
│  │  │   │      │  │  │  │
│  │  │   └──────┘  │  │  │         layoutArea = ウィンドウ全体なら R = window
│  │  └─────────────┘  │  │
│  └───────────────────┘  │
│  insets.bottom          │
└─────────────────────────┘
```

### 座標系と方向

- **座標はすべて window の左上を原点**とし、+X が右 / +Y が下。基準領域に可視領域を選んでも原点は動かない (上の図のとおり、可視領域の上端に置いた rect の y は insets.top の値になる)
- **offset の符号は配置によらず一定**で、末尾寄せでも +X は右へ動く (原典 Android は末尾寄せのときに符号が反転するが、これは仕様バグとみなして継承しない — [core/ADR-0008](../../../decisions/core/0008-layout-attributes-deliberate-deviations.md))
- 先頭寄せ / 末尾寄せは**物理方向** (左 / 右) を指す。RTL の論理方向への追随は現時点では扱わない

### 例1: 属性を何も渡さないダイアログ

window 400 × 800、insets = top 50 / bottom 30 / left 0 / right 0、内容サイズ 280 × 180 で、属性がすべて既定値 (可視領域・dialogMargin 24・中央) のとき:

- 水平: R = 0〜400 → A = 24〜376 (長さ 352) → s = min(280, 352) = 280 → p = 24 + (352 − 280) / 2 = 60
- 垂直: R = 50〜770 → A = 74〜746 (長さ 672) → s = min(180, 672) = 180 → p = 74 + (672 − 180) / 2 = 320

結果は rect = (x 60, y 320, w 280, h 180)。この計算は共通ケース表の対応するケースが固定している ([レイアウト共通ケース表と OS 差の統制](../architecture/layout-case-table.md))。

### 例2: 比率・fill・offset がぶつかる水平軸

間違えやすいのは「比率の基準は R、fill とクランプの基準は A」という食い違いである。window 400 × 800、insets なし、layoutArea = ウィンドウ全体、dialogMargin 全辺 24、幅の比率 0.9、水平配置 fill、offsetX = 40 のときの水平軸を追う:

- R = 0〜400 (長さ 400)、A = 24〜376 (長さ 352)
- s の選択: 比率が fill に勝つ → s = 0.9 × 400 = 360 (**基準は R なので A の長さ 352 を超える**)
- クランプ: s = min(360, 352) = 352
- 位置: サイズ側で fill が負けたので中央扱い → p = 24 + (352 − 352) / 2 = 24
- offset: p = 24 + 40 = 64

結果は x 64・w 352 で、右端は 416 と window の外へ出るが**クランプしない**。この例は規則から導いたもので、比率が fill に勝つこと・A へのクランプ・offset が領域外を許容することは、それぞれ共通ケース表の対応するケースが固定している。

## 外側タップで閉じる

isCanceledOnTouchOutside が true (既定) のとき、**ダイアログ外形 rect の外側** (背後を覆うオーバーレイの領域を含む) へのタップで、キャンセル操作と同じ経路 — show の結果は cancelled — でダイアログが閉じる。false のときは外側タップで何も起こらず、タップは背後の画面へ透過しない (モーダル性を保つ)。ダイアログ内側のタップはこの機構に関与しない。

結果を cancelled にそろえているのは、結果通知の型契約 ([結果通知のルール](result-notification-semantics.md)、[core/ADR-0003](../../../decisions/core/0003-result-notification-async-typed.md)) に第3の結果種別を増やさないためである。

この機構は overlayColor の値と**独立**に働く。overlayColor に透明を指定しても、外側タップの扱いは変わらない。

## 保証すること

- **メタ属性を何も渡していない既存の呼び出しは、変更なしでコンパイルが通り、見た目も変わらない** (例1 と同じ手順で決まる rect のままになる)。属性はすべて既定値付きの追加である。**ただし操作面に1つだけ追加がある** — 外側タップは既定 true で cancelled を返して閉じる。現行実装にはこの機構自体が無かったため、ここだけは挙動が増える
- **同じ入力なら iOS と Android で同じ rect になる** (承認・記録された差異を除く)。両 Native 実装は共通ケース表の全ケースに許容誤差内で適合する ([レイアウト共通ケース表と OS 差の統制](../architecture/layout-case-table.md))。これが崩れると「規則を1本化し実装は各 OS へ委ねる」構成そのものが成立しない
- **表示されたときには実効値は確定している**。添付と show 引数のどちらを採るかは初回レイアウトパス完了時点の値で決まり、以後は動かない。属性の書き換えで表示中の位置がひとりでに変わることはなく、位置が変わるのはウィンドウ寸法・insets が変わったとき (前述の再配置) だけである
- **画面が変わっても配置規則は成り立ち続ける**。回転・リサイズ・システムバーの出入りのあとも、凍結済みの実効値と新しい寸法から同じ手順で導いた位置・サイズになる。キーボードの出入りでは動かない
- **dialogMargin は最大サイズだけでなく位置決めにも効く**。先頭寄せ / 末尾寄せでは端から margin の分だけ離れる (原典は最大サイズの算出にしか効かず、端に貼り付いた。直感との一致を原典挙動の継承より優先した意図的な差異)
- **overlayColor に透明を指定しても、システムバーの見えは変わらない**。現行実装の Android では、透明を指定してもダイアログ表示中だけステータスバー領域が暗転していた。この契約ではそれを起こさず、透明のときだけ配置規則が変わる特殊分岐も持たない

## してはいけないこと

- **MAUI / KMP でレイアウト計算を再実装しない**。属性を無変換で Native へ渡すだけにする ([core/ADR-0001](../../../decisions/core/0001-native-independent-thin-wrappers.md))。計算が共通層と各 OS の3箇所に散っていた原典の負債を再生産することになる
- **View が自力で表現できる属性を契約へ戻さない** (明示サイズ・角丸・枠線)。器と View の双方が同じ見た目を決められる状態になり、どちらが勝つかという規則を新たに抱え込む
- **ViewModel に属性を持たせない・show に静的メタの引数を作らない**。前者は ViewModel に UI の関心が混入し、後者は「その View の性質」であるはずの静的メタを呼び出しごとに書き換えられるようにしてしまう
- **offset を有効領域の内側へクランプしない**。画面外へはみ出す配置 (通知風の見せ方など) を意図的に選べる余地を塞ぐ理由がなく、原典も加算のみである
- **初回レイアウトパス完了後の添付変更に追随させない**。静的メタの定義と矛盾するうえ、監視機構のコストに見合う要求がない (**画面側の寸法・insets の変化への追随はこれとは別**で、そちらは行う)
- **ソフトキーボードに合わせてダイアログを動かさない**。キーボード回避は原典にない機能追加であり、入力欄の可視性という別の関心を器に持ち込む
- **共通ケース表の統制を迂回しない** — 統制の内容は [レイアウト共通ケース表と OS 差の統制](../architecture/layout-case-table.md) が定める

## まだ決めていないこと (実物と一緒に決める)

- **クランプで rect が内容サイズより小さくなったときの、中身の見え方** — 内容がクリップされるのか縮むのかは、この契約では規定していない。rect (外形) がケース表どおりになることだけを課している

## 用語

### 文書全体で使う語

| 用語 | 意味 |
|---|---|
| 形態 | 本ライブラリを利用できる4つの入口 (iOS Native / Android Native / MAUI / KMP = Kotlin Multiplatform)。レイアウト計算の実体を持つのは前2つだけ |
| 原典 | 移植元の AiForms.Maui.Dialogs |
| 現行実装 | この契約を導入する前の本ライブラリのコード (原典から移植して動いている状態) |
| 論理単位 | iOS の pt / Android の dp。属性値もケース表の数値もこの単位で表す |

### 属性と供給に関する語

| 用語 | 意味 |
|---|---|
| メタ属性 | 器 (ダイアログコンテナ) にしか実現・計算できない設定値。契約が持つのはこれだけで、中身の View が自力で表現できるものは含まない |
| 添付 | ダイアログの中身の定義に属性を結びつける供給経路。書き方は形態と UI 技術ごとに違う (各形態の公開面) |
| 実効値 | show 引数・添付・既定値を優先順位で解決した (フィールド単位で混ぜるのではなく、どれか 1 つを選んだ)、器が実際に採用する値 |
| 初回のネイティブレイアウトパス | 器を画面に載せたあと、OS が最初にサイズと位置を確定させる処理。実効値と内容サイズが決まる基準時点 |

### 領域とサイズに関する語

| 用語 | 意味 |
|---|---|
| 基準 rect R | layoutArea が選ぶ矩形 (ウィンドウ全体または可視領域)。比率サイズの基準になる |
| 有効領域 A | R から dialogMargin を控除した矩形。クランプと配置の基準になる |
| insets | window の各辺から可視領域を狭めるシステム領域の幅 (上下左右の4辺、論理単位)。システムバーや cutout が占める分 |
| 可視領域 | window から insets を控除した領域 (iOS = safe area / Android = システムバー除外領域) |
| 内容サイズ | ダイアログの中身が要求するサイズ。ViewModel の初期状態を適用したうえで、初回のネイティブレイアウトパスの中で確定する (以後の内容変化には追随しない) |
