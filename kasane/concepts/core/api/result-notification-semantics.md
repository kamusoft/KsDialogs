# 結果通知のルール (show が返すもの)

この文書は、全形態 (iOS Native / Android Native / MAUI / KMP) 共通の「ダイアログを表示した呼び出し元が、結果をどう受け取るか」のルールを定める。読むと、show の呼び出しが何を返し、「OK で閉じた」と「キャンセルされた」がどう区別され、結果がいつ確定していつ呼び出し元へ届くかが分かる。

本文中の**移植元**は AiForms.Maui.Dialogs (本ライブラリの移植元) を指す。参照ルールは [移植元 AiForms.Maui.Dialogs の参照](../../../handbook/cross/aiforms-origin-reference.md)、リポジトリの在り処は [参考リポジトリの在り処](../../cross/reference/reference-repositories.md) が定める。

**この文書が正であり、実装はここに合わせる**。根拠決定は [core/ADR-0003](../../../decisions/core/0003-result-notification-async-typed.md) (accepted 済み。ADR が持つのは「なぜそう決めたか」で、「何が成り立つか」の正はこの文書側にある)。

core は「全形態が共有する契約」の層 (層の区分は [concepts 配置ルール](../../rules.md))。公開名・署名・コード例は各形態の公開面が持つ (末尾の「形態別の公開面」)。

## 基本ルール

show は「**completed(結果) または cancelled を、ちょうど1回返す非同期操作**」である。呼び出し元は show を待つだけで、ダイアログが閉じたときの結果を受け取れる (構成ミスのときだけは結果を返さず失敗する — ルール5)。

### ルール1: 結果の型は ViewModel が宣言する

show の呼び出し側が結果型を指定するのではなく、ダイアログの ViewModel が `DialogViewModel` の契約で結果型を宣言し、show は ViewModel の宣言から戻り値の型を導出する。契約に結果型をどう書くか (型引数か、それに相当する言語機能か) は形態ごとに違う。

ダイアログ側で結果を報告する部品 —「完了 (結果つき)」「キャンセル」の2操作を持つ `DialogNotifier` (名前は移植元踏襲) — も同じ結果型に固定され、show 1回ごとに新しいものが View factory (ViewModel の型から対応する View を生成する登録済みの生成関数) へ渡る。

**呼び出し側が結果型を指定する形では守れない**: View factory のレジストリは ViewModel の型しか見ないため、同じ ViewModel を別々の結果型で show できてしまい、「報告した型と受け取る型が食い違って実行時エラー」(移植元は結果を型消去して運ぶためこれが起こりうる) を防げない。ViewModel 宣言方式なら、食い違う書き方はそもそもコンパイルできない。

### ルール2: 「OK で閉じた (completed)」と「キャンセルされた (cancelled)」は型で区別する

completed と cancelled は `DialogResult` の別々の枝として表現する。cancelled は結果値を持たない。移植元は「キャンセル時は結果型の既定値 — 整数なら 0、真偽値なら偽 — を返す」方式のため、「キャンセルされた」のか「0 や偽という結果で完了した」のか区別できない — この弱点を直す。

枝をどの言語機能で表すか (直和型の綴りと分岐の書き方) は形態ごとに違う。

### ルール3: 結果はちょうど1回だけ確定する (ラッチ)

最初の「完了」または「キャンセル」の報告だけが有効で、2回目以降の報告は何もしない (no-op)。この不可逆な確定を**ラッチ**と呼び、確定した結果が呼び出し元へ渡ること (**配送**) とは時点が別である (後述の「結果が確定する時点と、呼び出し元へ渡る時点」)。移植元には二重報告への防御がない。

### ルール4: 器が消えたときと、呼び出し元が待機を打ち切ったときも、未確定なら cancelled で確定する

報告を経ずに show が終わる経路が2つある。

- **(a) 器の消失** — ダイアログを載せている表示コンテナ (本文では**器**と呼ぶ) だけが消える経路。iOS の画面表示の連鎖 (presenting / presented) や Android の Activity が破棄されたときに起きる
- **(b) 呼び出し元の打ち切り** — show を待っている呼び出し側が待機をやめた場合。ダイアログも閉じる。これは KMP の共有コードから iOS 上で表示した場合を含めて成り立つ

どちらも未確定なら cancelled で確定する。この手当てがないと show が永久に返らない (宙吊り) ため、ルール3の「ちょうど1回」はこの手当てとセットで成立する。ただし (b) は**呼び出し元から見える形が形態ごとに違い、MAUI にはこの経路自体がない** (後述の「呼び出し元をキャンセルしたときの見え方」)。

### ルール5: 構成ミスは結果ではなく失敗で返す

View factory が未登録の ViewModel 型で show した場合と、ダイアログを出す先の画面が存在しない場合は、cancelled を返さず失敗する。cancelled に化けると「エンドユーザーが閉じた」と区別できず、登録漏れが画面上で観察できないまま素通りする。このとき View は生成も表示もされない。

失敗をどう伝えるか (例外を投げるか、失敗した非同期操作として返すか) と、失敗の型・名前は形態ごとに違う。KMP の共有コードから Swift 側へ失敗が届くときの追加の約束は [KMP の Dialog 公開面](../../kmp/api/dialog-surface.md) が定める。

### ルール6: 別インスタンスの ViewModel なら、show は独立した別のダイアログとして重なる

ViewModel が別インスタンスなら、等価比較が一致していても互いに干渉しない。View も `DialogNotifier` も show ごとに新規である。ただし**同一 ViewModel インスタンスの並行 show は構成ミスとして失敗する** (ルール5と同じ扱いで、cancelled に化けない) — show 中の ViewModel には結果報告口がインスタンス同一性で1本だけ紐付くため、2本目を張れない ([ViewModel 主導の呼び出しのルール](model-binding-semantics.md))。表示中の先行 show には影響しない。二度押しなどの UX ガードは従来どおりアプリ側の責務。移植元は Android (すぐキャンセル相当を返す) と iOS (防御なし) で挙動が割れていたが、本ルールは両 OS で同じ挙動を保証する。

### ルール7: コールバック (完了時に呼ばれる関数を渡す形) は公開 API にしない

待って受け取る形だけを公開する。コールバックは KMP→Swift 連携の内部変換層にだけ存在を許す。

## どの操作がキャンセルになるか

次のどの操作でも、呼び出し元には同じ cancelled が返る:

- ダイアログ側 (ビュー / ViewModel) からの明示的なキャンセル呼び出し
- ダイアログの外側をタップ (外タップキャンセルの設定が有効なとき。**KsDialogs では移植元と同じく既定で有効**)
- Android の戻るボタン

これらのエンドユーザー操作に加えて、ルール4の2経路 (器の消失と呼び出し元の打ち切り) も cancelled になる。

iOS には戻るボタンに相当するキャンセル経路を設けない (移植元も同様)。「どの操作でキャンセルされたか」の内訳は返さない — 移植元にもなく、必要になったら後から足せる。

### ソフトキーボード表示中の戻るボタン

**ソフトキーボード (IME) が出ているときの戻るボタンの扱いは、OS の既定処理に委ねる (ライブラリとしては保証しない)。** 実測 (2026-08-15 / Android Emulator API 35) では、1回目の戻るは OS がキーボードを閉じるのに使い、ダイアログは結果未確定のまま残って2回目の戻るで cancelled になった — 移植元と同じ観察結果である。ただしこれは OS の既定の戻る処理がキーボード閉鎖に消費された結果にすぎず、「キーボード表示中は cancelled にしない」というライブラリのルールとしては明文化しない。移植元にはこれを明示的に実装する仕組み (キーボード監視) があったが、その唯一の実効果がこの OS 既定と同じ観察結果だったため、移植せず OS に任せる。

### 呼び出し元をキャンセルしたときの見え方

呼び出し元の待機を打ち切ったときに何が観察されるかは形態ごとに異なる。iOS と Android / KMP はそれぞれの言語の非同期規約に従い、MAUI にはこの経路がない:

| 形態 | 呼び出し元が観察するもの |
|---|---|
| iOS Native | show が結果として cancelled を返す (失敗としては伝わらない) |
| Android Native / KMP | 言語のキャンセル規約どおりキャンセルの通知が伝播する (内部の結果は cancelled で確定済み) |
| MAUI | **この経路がない** — show が呼び出し元のキャンセル手段を引数で受け取らない |

Android / KMP でキャンセルの通知を握りつぶして cancelled を返す形にはしない。構造化並行性 (親のキャンセルが子へ伝わる仕組み) を壊すためである。キャンセルの通知がどの型で届くか、iOS で返る結果の綴りがどうなるかは、各形態の公開面の「失敗とキャンセルの形」が定める ([iOS](../../ios/api/dialog-surface.md) / [Android](../../android/api/dialog-surface.md) / [MAUI](../../maui/api/dialog-surface.md) / [KMP](../../kmp/api/dialog-surface.md))。なお、待機を打ち切ったあとでもダイアログの退出アニメーションは最後まで完遂される ([トランジションのルール](transition-semantics.md))。

## 表示 API の動詞

移植元の「結果を返さない表示 / 結果を返す表示」で動詞を分ける形は**導入しないことが確定した** — 結果型は ViewModel が宣言する (ルール1) ため動詞を分ける理由がなく、表示 API の動詞は show 1本に統一されている ([core/ADR-0020](../../../decisions/core/0020-show-verb-unification.md))。移植元との名前の対応は [MAUI の Dialog 公開面](../../maui/api/dialog-surface.md) が持つ。

ViewModel の型を渡す起動モード (型指定 show) は [ViewModel 主導の呼び出しのルール](model-binding-semantics.md) が定める。ダイアログが重なっているときも、各 show は独立にこのルールで結果を返す ([多段表示のルール](multi-display-semantics.md))。

## 結果が確定する時点と、呼び出し元へ渡る時点

ダイアログは閉じるときに退出アニメーションを行うため、「結果が決まった瞬間」と「show が結果を返した瞬間」は同じではない。2つを次のように呼び分ける:

- **ラッチ** — 最初の報告で結果が**不可逆に確定**すること (ルール3)。退出の途中で二度目の報告が来ても、画面が壊れても、確定した値は変わらない
- **配送** — ラッチ済みの結果が show の**呼び出し元へ渡る**こと。退出アニメーションが終わり、器が画面から撤去された**後**に行う

したがって **show が返ったときには、ダイアログはもう画面にない**。演出を何も指定していなくても、既定の退出アニメーション (クロスフェード 250 ミリ秒) の分だけ show の完了は遅れる — show が即座に返ることを前提にしたコードは影響を受ける。アニメーションの差し替えと、退出中に何が起きたときにどう配送されるかは [トランジションのルール](transition-semantics.md) が定める。

## まだ決めていないこと (実物と一緒に決める)

- **Loading / Toast の結果の扱い**: Loading (移植元は結果を返さない) は Loading 機能の実装時に、Toast (移植元で廃止予定のため新実装) は Toast 再構築時に決める
