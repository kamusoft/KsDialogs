# phase-7-loading 議論履歴

## 2026-08-25: カスタム View 版と Dialog 機構の共有範囲

Loading の機構を Dialog とどこまで共有するかを議論。土台として原典 Loading 仕様を調査し [artifacts/origin-loading-survey.md](artifacts/origin-loading-survey.md) に保存 (発見: LoadingConfig は既定専用 / isCurrentScope は iOS のみ有効 / Sample の AutoRotateForIOS 指定は Loading では事実上ノーオペ / iOS は既定・カスタムとも Window 直貼りで Dialog 機構を通らない)。

選択肢:
- A. 原典踏襲の独立機構 — Loading を Dialog と切り離した軽量オーバーレイとして実装
- B. Dialog 機構に統合 — 「閉じられない・結果を返さない特殊ダイアログ」として同じ提示経路に載せる
- C. 器は独立・部品は共有 — 画面への載せ方は Loading 専用オーバーレイ、コンテンツの載せ方・レイアウト規則・演出の添付は Dialog の core 仕様を再利用

採用: **案C**。理由: (1) Loading はダイアログの重なり順管理から独立している必要があり、OS の提示スタックに載せると多段表示の意味論 (core/ADR-0006) に巻き込まれる — 原典も iOS では意図的に Window 直貼り。(2) レイアウト規則 (layout-semantics) と演出フック (core/ADR-0017) は既に core 仕様があり、再利用で Native 2実装の重複が消え利用者の書き味も揃う。(3) 案B は「show は結果をちょうど1回返す」(core/ADR-0003)・使い捨て (core/ADR-0005) の契約と Loading のライフサイクル (開ける→進捗→呼び出し側が閉じる・結果なし) が不整合。

→ core/ADR-0022 として proposed 起票。付随整理: 論点「Sample 通し」は完了条件のため TODO へ移動 (8論点→7論点、分割トリガー回避)。

## 2026-08-25: 既定ローディングの実現方式 (論点1前半)

共有範囲の決定 (案C) を受けて、既定ローディングをその共有部品の上にどう作るかを議論。

選択肢:
- A. 内蔵コンテンツ方式 — ライブラリ同梱のローディングコンテンツ (スピナー + メッセージ) を共有部品に載せる。styling はコンテンツの公開属性
- B. 原典踏襲の native 直組み — 各 OS がスピナー + ラベルを直接組み、styling は Loading 専用の設定オブジェクト

採用: **案A**。理由: (1) 共有部品 (ホスティング・レイアウト・演出) がそのまま使え、native 直組みだとオーバーレイ内の組み立て・配置を二重実装することになる。(2) 既定とカスタムで経路が同じなら演出・スコープ・単一性の議論が Loading 全体で1つの答えで済む — 原典は既定だけ別経路にしたため LoadingConfig がカスタムに効かない歪みがあった。(3) styling を内蔵コンテンツの属性として自然に表現でき、原典 LoadingConfig の「初期化一度きりでしか効かない」弱点を持ち込まずに済む。

→ core/ADR-0023 として proposed 起票。論点1の残り (styling の受け口) は継続。

## 2026-08-25: 既定ローディングの styling の受け口 (論点1後半、これで論点1解消)

styling の対象整理: オフセットは DialogPlacement (offsetX/Y)、覆いの色は DialogOptions (overlayColor、原典 Opacity もアルファ込みで吸収) が既にカバー。残る内蔵コンテンツ固有の項目 = インジケータ色・メッセージのフォントサイズ/色・既定メッセージ・進捗フォーマット。

選択肢:
- A. 一括設定のスタイル値オブジェクト — アプリ側で一度設定し、各表示の開始時に読む
- B. show / StartAsync の引数で都度指定
- C. styling 面を持たない (カスタム View へ誘導)

採用: **案A**。理由: (1) 原典 LoadingConfig の継承として素直で、「アプリ全体でローディングの見た目は1つ」という静的性質に合う — DialogOptions を show 引数にしない core/ADR-0015 と同じ誤用防止の発想。(2) 各表示の開始時に読む方式で、原典の「初期化一度きりでしか効かない」弱点を解消 (設定変更は次の表示から効く)。(3) 案C は「Loading の主要機能の移植完了」ゴールに対する仕様の削り込み。付随決定: 色を含むため KMP 共有コード (commonMain) からは設定不可、各 OS 側で設定する (DialogOptions と同じ非対称)。

→ 同日の core/ADR-0023 (proposed) に styling 受け口を含めて追記。

## 2026-08-25: 表示スコープ (論点5)

原典 isCurrentScope 相当 (全画面か現在ページ内か) を移植するかを議論。

選択肢:
- A. 移植しない — 常にウィンドウ全体を覆う。スコープ指定は設けない
- B. 全 OS で契約化 — 「現在ページ内だけ覆う」を iOS / Android 両方で実装
- C. 原典踏襲 — iOS のみ有効の引数として移植し OS 差を容認

採用: **案A**。理由: (1) 原典で iOS のみ有効・Android は引数を無視しており、仕様として成立していなかった。(2) OS 間挙動同一の統制方針 (approvedDiff / core/ADR-0016) と OS 専用機能は衝突する。(3) Loading の本務 (操作ブロック) に対しページ内スコープは中途半端で、部分表示はアプリが View 埋め込みで実現できる。(4) 後から非破壊で追加できるが、一度入れた契約を外すのは破壊的。オーナー証言: 原典でも使った記憶がない。

ADR 化はせず (可逆な判断のため3基準に届かない)、Loading 契約の concepts に「持たない」と明記する方針。

## 2026-08-25: 単一性の担保 — 多重利用の契約 (論点4)

原典の多重抑止は OS でバラバラ (iOS: 黙って無視 + StartAsync は 1.25 秒待って諦めると action 自体を実行しない / Android: 前の破棄を待って必ず表示) で、呼び出し側から見えない失敗を含む。継承せず契約を立て直す前提で議論。

選択肢:
- A. 先勝ち・後は無視 (原典 iOS 改良 — action 未実行だけは直す)
- B. 合流 — 重なった利用は1つの表示に合流し、最初の開始から最後の終了まで表示継続
- C. エラー — 表示中の再表示要求は失敗として通知

採用: **案B**。理由: (1) 複数の非同期処理からの同時利用は現実に起こり、先勝ち無視だと先の完了で表示が消えてブロックの役目を果たせない。(2) 黙った無視・黙った未実行は予測不能な silent failure — 合流なら「渡した処理は必ず実行」「表示は最初の開始から最後の終了まで」と観察可能な意味論で言い切れ、Scenario テスト (core/ADR-0016) で固定できる。付随決定: メッセージ・進捗は後勝ち、明示の hide は合流数によらず即閉じ。

→ core/ADR-0024 として proposed 起票。

## 2026-08-25: 進捗通知の各形態表現 (論点3)

選択肢:
- A. スコープ形 + 形態別イディオム — 処理ブロックを渡す形 (StartAsync 相当) を主経路とし、報告口は C# = IProgress<double> / Swift = クロージャ / Kotlin・KMP = 関数型
- B. 共通 reporter 型を全形態に定義
- C. ストリーム受け (Flow / AsyncSequence / IObservable)

採用: **案A**。理由: (1) スコープ形は開始・終了が必ず対になり、合流モデル (core/ADR-0024) のカウント管理と自然に噛み合う。(2) 「意味は同一・形は言語慣習」は識別子写像 (cross/ADR-0005) 以来の確立済みの流儀で、関数型なら KMP commonMain からそのまま使える。(3) ストリームは購読・完了・エラーの管理が増えるわりに、必要なのは「report(0〜1) を随時呼ぶ」だけで得るものがない。値は 0〜1、表示は後勝ち。

ADR 化はせず (確立済み流儀の適用で新しい決定軸がない)、Loading 契約の concepts に明記する方針。

## 2026-08-25: 出入りの演出の Loading への適用 (論点6、phase-5-3 申し送りの決着)

選択肢:
- A. カスタム View 版には載せる・既定ローディングは既定演出固定
- B. 載せない (既定・カスタムとも固定クロスフェード)
- C. 既定ローディングにも演出設定の口を開放

採用: **案A**。理由: (1) カスタム Loading は共有部品 (core/ADR-0022) の上に載るため `DialogTransition` の第3スロット添付がほぼタダで効き、載せないほうが「カスタム View なのに演出だけ添付が効かない」例外を作る。(2) 原典もカスタム View のみ演出差し替え可 (RunPresentationAnimation 等)・既定は固定フェードで、同じ構造。(3) 原典の既定演出 (0.25 秒アルファフェード) はライブラリ既定のクロスフェード (core/ADR-0017) とほぼ同じで、既定の見えを保てる。

適用範囲の整理: ADR-0017 のうち Loading に効くのは両フック (ホスト View 統一形・完了通知つき)・既定クロスフェード・覆いの別レイヤ常時フェード。「結果のラッチと配送」は結果を持たない Loading には対象外。スタイル値オブジェクトに演出は入れない (添付との二重供給を避ける)。

→ core/ADR-0022 (proposed) に適用範囲として追記。付随して「器メタ属性の適用範囲」が未決着と判明し、論点8として agenda に追加。

## 2026-08-25: 回転ロックの要否 (論点7、phase-5-3 申し送りの決着)

申し送りの前提「原典 Sample の主用途が Loading の回転ロック」が調査で崩れた: Sample の AutoRotateForIOS="False" 指定を読むのは Dialog 側実装だけで、Loading の iOS 実装 (ViewController を作らない Window 直貼り) では事実上ノーオペ。原典の Loading に回転ロックは実挙動として存在しなかった。

選択肢:
- A. 導入しない — 表示中の回転は既存の再配置規則 (PB-WN-01) に従う
- B. 器メタ属性として導入 — supportedInterfaceOrientations 系で iOS 実現

採用: **案A**。理由: (1) 継承すべき実挙動が存在しない。(2) 回転時の挙動は再配置規則で確立済みで、共有部品に載る Loading はそれに乗るだけ。(3) iOS 専用スイッチは OS 間挙動同一の統制方針と衝突 (表示スコープを落としたのと同じ理由)。(4) 必要になれば器メタ属性 (core/ADR-0014) として非破壊追加できる。phase-5-3 の Dialog 側決定 (移植しない) と整合。

ADR 化はせず、Loading 契約の concepts に「持たない」と明記する方針。

## 2026-08-25: 器メタ属性の Loading への適用範囲 (論点8、これで全論点解消)

選択肢:
- A. 全面適用 + 外側タップキャンセルのみ常に無効
- B. 添付のみ (表示 API に placement 引数を設けない)
- C. Loading 専用の縮小オプション型を新設

採用: **案A**。理由: (1) レイアウト系 (layoutArea・dialogMargin・比率・placement・overlayColor) は「器にしか決められないこと」(core/ADR-0014) で Loading でも意味がそのまま通り、供給経路も core/ADR-0015 (添付 + show 引数は placement のみ) を踏襲すれば新規則が不要。(2) 既定ローディングは利用者の添付面がないため、原典 LoadingConfig の OffsetX/Y 相当は表示 API の placement 引数で受ける — ADR-0015 の規則がそのまま受け口になり閉じる。(3) isCanceledOnTouchOutside は Loading の本務 (操作ブロック) と矛盾し原典も閉じられない固定のため、「常に無効 (添付されても効かない)」と契約に明記。

→ core/ADR-0022 (proposed) に適用範囲として追記。全論点解消につき、次は ksn-propose での提案化を案内。

## 2026-08-25: 提案化 (add-loading) — ADR-0020 との整合確認

ksn-propose の自己レビュー上位層チェックで、Loading のスコープ形 `start` が core/ADR-0020「表示 API の動詞は show 1本」と形式上衝突して見える点をオーナーに確認。**衝突しないと整理して進む** (案A) で確定: ADR-0020 が統一したのは「同じ操作 (表示して結果を待つ) の呼び出し経路違い」であり、Loading の start は経路違いではなく別の複合操作 (処理の実行を包み表示を付随させる)。Loading の純粋な表示は show 動詞を使う。原典も Show / StartAsync を別動詞にしていた。却下案: B. スコープ形を show に寄せる (意味論が濁る) / C. ADR-0020 の supersede (本文変更は不要と判断)。
