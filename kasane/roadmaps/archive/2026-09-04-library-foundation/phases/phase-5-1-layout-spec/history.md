## 2026-08-17: レイアウト属性一式の取捨

ksn-scout で原典の属性全量 (型・既定値・iOS/Android 実装差) を実測し、artifacts/scout-origin-layout-attributes.md に保存。選択肢は「原典フル踏襲 (歪みごと)」「原典踏襲 + 問題箇所のみ規則確定」「縮約セット」で、**原典踏襲 + 問題箇所の規則確定**を採用。判断軸は移植互換性・3形態の実装/テストコスト・規則の記述精度 (ADR-0007 の弱点回避)。

アシスタント提案に対するオーナー修正3件:
1. OverlayColor 透明時の Android ステータスバー暗転回避は、原典ハックの意図を継承して正式対応を模索 (提案は「継承せず挙動差を記録」だった)
2. UseCurrentPageLocation は落とさず歪みを正して維持 (提案は「落とす」だった)。両軸対応・基準はシステムバー除外領域・改名可。「システムバー以外の部分の座標で指定したいニーズは外せない」
3. 動的リサイズの真の課題は「描画後 VM Bind で内容依存の高さが反映されない」こと。Bind 完了後のサイズ確定 (初期化順序) で解決し、Bind 後の継続リサイズは必須としない (提案は「初版範囲外と明記」のみだった)

確定した意図的乖離: Offset 座標系統一 (End 時符号反転廃止) / DialogMargin の位置決め適用 / Border 内側描画統一 / 上記オーナー修正3件。AutoRotateForIOS は 5-3 へ移送、IsCanceledOnTouchOutside の規則詳細も 5-3 系論点扱い。ADR: core/0008 を proposed で起票。

## 2026-08-17: レイアウト共通仕様テストの器

phase-4 の現状 (同名テストを ios/android/maui/kmp にミラーし、各形態が DialogTestHarness 等の Support 群を持つ) を確認のうえ、選択肢は A. 共通ケース表 (期待値データを1箇所に置き各形態が読み込む) / B. 同名テスト手書きミラーの延長。判断軸は形態間の期待値一致の保証・ケース追加コスト・導入コスト・可読性。**A を採用** — レイアウトは属性×画面サイズ×配置のマトリクス検証でデータ駆動の本領、期待値の単一ソース化が ADR-0007 の弱点 (規則の曖昧さ・テスト不在) への構造的な答えになるため。

併せて責務分担を確定: レイアウト計算の実体は Native 2実装のみ (core/ADR-0001) のため、ケース表の全量検証は iOS/Android に課し、MAUI/KMP は属性パススルーの同型テストに留める。実行環境の詳細は spec 化で詰める。ADR: core/0009 を proposed で起票。

## 2026-08-17: MAUI iOS ダイアログ内ボタンの当たり判定の扱い

事象 (add-vertical-slice verification-matrix 2026-08-15 記録): 描画中心 (261,480pt) への合成タップで反応せず上端寄りで反応。器の当たり判定ではなく中身の配置・測定側の疑い、phase-4 の退行ではない。選択肢は A. 共通ケース表に hit-test 検証 (期待 rect 中心への合成タップでハンドラ発火) を含めて捕捉し原因究明は実装タスク送り / B. いま原因特定してから仕様を決める。**A を採用** — 要求 (当たり領域 = 描画領域の一致) は原因に依存せず、議論モードでの動的デバッグはコスト過大。ケース表の位置検証と同じ器で構造的に検出されるため、修正は仕様テストが担保する。ADR なし (ADR-0009 の増分)。

## 2026-08-17: Sample UI の未決4件

phase-4 申し送りの4件を一括議論 (オーナー許可のもとまとめて提示)。

1. 初期状態の結果表示エリア非表示 — 実装者判断 (ui/brief.md で未確認のまま残置) を**正式採用**し、モックへ昇格
2. ボタンタップ領域 38pt — **モック改訂で HIG 44pt / Material 48dp 以上へ引き上げ**。当たり領域の仕様テスト化 (hit-test) と方向を揃え、公開ライブラリの Sample がガイドライン未満をお手本にしない
3. surface-variant トークン — **モック側のトークン定義へ昇格** (モック = 見た目の正の照合の穴を塞ぐ)
4. samples Android の View 技術 — アシスタント提案 (素の View 継続・Compose は要否判断を phase-9 送り) は**オーナーが棄却**し、要件を上方修正: **ライブラリ本体がコンテンツ View 技術の両対応を必須とする**。Compose / SwiftUI でダイアログを書ける対応は必須、Android.View / UIView 対応も必須 (これがないと MAUI と連携できない)。参考: KsSettingsView。ADR core/0010 を proposed で起票し、登録 API・ホスティングの設計論点を phase-5-2 (API 表面) の論点に追加。5-1 のレイアウト検証 Sample は現行 View 構成のまま進める
