## Context

Dialog・Loading・Toast の提示先は、iOS は前面でアクティブなシーンの key window、Android は resumed な Activity である。Android のライブラリは、利用者の Activity をサブクラス化せず、利用者の初期化コードも求めずに、Application のライフサイクル通知で resumed な Activity を追跡している。追跡役は 3 機能で共有している。core/ADR-0041 は、この定義を変えないことを範囲の外に置いた。

Android の起動直後は「画面が resumed になる → 最初の描画 → 起動画面の退場」の順に進む。そのため、器は起動画面の下に載る。

- Toast: 表示時間の短いものほど、見えないまま終わる回があった (Sample の自動再生での実測)
- Dialog・Loading: 寿命が表示時間で切れないので全回表示されたが、入りの演出は起動画面の下で終わっている

core/ADR-0043 で、アプリが前面にいるのに提示先が無い間に受け付けた Toast は、画面が利用者に見えた時点から表示時間を数えることになった。Android でも「見えた」を判定する合図が要る。

合図の候補:

- 起動画面の退場: アプリに通知されない
- 画面の実際の描画: ライブラリから観測できる、退場にいちばん近い合図。アプリが起動画面を延ばしている間 (core-splashscreen の延長条件) は描画が止まるので、延長が終わってから来る
- ウィンドウのフォーカス: 分割画面・通知シェード・前面の Dialog のように、画面が見えているのにフォーカスが無い場面がある

core/ADR-0041 は、「待ちが解ける合図と提示先の条件がずれると、表示されないまま終わる不具合になる」を負の帰結に挙げている。

前提:

- KMP と MAUI は表示を各 OS の Native に委譲するので、Native の振る舞いがそのまま KMP・MAUI の振る舞いになる
- ライブラリは、Activity のライフサイクル通知で得た Activity から、その画面の描画を観測できる

## Decision

Android の提示先を「resumed な Activity」から「resumed で、かつ描画された Activity」に変える。Dialog・Loading・Toast の 3 機能で、同じ条件を使う。Android で画面が利用者に見えたとみなす時点 (core/ADR-0043 の「見えた」) は、この条件がそろった時点とする。

この条件は、新しく載せる先を決める条件とする。既に載っている Loading・Toast の器は、載っている Activity が破棄されるか、描画済みの別の提示先が現れるまで外さない。

範囲に含めないもの:

- iOS の提示先の定義 (変えない)
- アプリが前面にいるかどうかの判定 (core/ADR-0043 に関わるが、判定の手段は設計で定める)

理由:

- Android の提示先が、iOS と同じ「利用者に見えている画面」という意味になる
- core/ADR-0043 の「見えた時点から数える」が「提示先に載った時点から数える」と同じ意味になり、載せる合図と数え始める合図を別に持たずに済む
- 3 機能で定義を 1 つに保てば、core の契約で提示先の条件を機能ごとに書き分けずに済み、core/ADR-0041 が求める「待ちの合図を提示先の条件と揃える」を満たせる
- 描画済みとみなす状態は、画面が背面へ下がると下ろす (次の描画を待たずに提示先になるのを防ぐため)。そのため背面から戻ると、最初の描画までこの条件が崩れる。そこで載っている器まで外すと、戻るたびに Loading・Toast が一瞬消えて出直す。載っている器を残せば、背面の間も器を付けたままにする iOS と、変更前の Android の振る舞いが保たれる

## Alternatives Considered

- **提示先は resumed のまま、前面で提示先を待つ Toast の数え始めだけを描画に合わせる** — 却下。器が載る合図と数え始めの合図が 2 本に分かれ、「載っているのに時間は止まっている」状態ができる。起動直後の Toast の入りの演出は、起動画面の下で終わる
- **Toast だけ描画された画面を待ち、Dialog・Loading は resumed のままにする** — 却下。変更と検証の範囲は小さく、合図を取りこぼしたときの被害も Toast に留まる。しかし Android の提示先の定義が機能で 2 通りに分かれ、core の契約の記述も分かれる
- **ウィンドウのフォーカスを得た画面を提示先にする** — 却下。分割画面・通知シェード・前面の Dialog のように、見えているのにフォーカスが無い場面で、誤って提示先なしになる
- **描画から一定時間 (起動画面の退場の演出の分) を置いてから提示先とみなす** — 却下。値の根拠を置きにくい (core/ADR-0041 が Dialog の待ちに決まった時間の上限を却下したのと同じ理由)
- **条件が崩れたら載っている Loading・Toast の器も外し、描画の後に載せ直す** — 却下。背面から戻るたびに、戻った直後の数フレームだけ Loading・Toast が消えて演出なしで出直す。Loading の覆いが消える間は、下の画面が見えて触れる。iOS と振る舞いが分かれる

## Consequences

- 正: 起動直後の Toast が起動画面の下に載らなくなり、core/ADR-0043 のもとで、起動画面が退いた後に表示時間の大半が見える
- 正: 起動直後の Dialog・Loading も、起動画面が退いてから入りの演出つきで出る
- 正: アプリが起動画面を延ばしている間は描画が止まるので、その間は載せず、延長が終わってから出す
- 正: Android の提示先が iOS と同じ意味になり、3 機能で 1 つの定義に揃う
- 負: 描画の合図を取りこぼすと、Dialog は上限なく待つので、出ないまま返らない。Loading・Toast は出ないまま終わる。取りこぼしの被害が 3 機能に及ぶ
- 負: 描画を伴わない復帰 (pause だけからの復帰など) でも条件がそろうよう、描画済みとみなす状態の持ち方を設計する必要がある
- 負: 描画は起動画面の退場より前に来るので、退場の演出の分だけ、起動画面の下で載ることが残りうる
- 負: 器の載せ替えの規則が、提示先の条件とは別に要る。載っている器は提示先の条件ではなく、載っている Activity の破棄と、描画済みの別の提示先の出現で載せ替える
- 負: 公開済みベータの振る舞いが変わる。起動直後の Dialog・Loading・Toast は、以前より遅れて出る
