## Context

提示先 (iOS は前面でアクティブなシーンの key window、Android は resumed な Activity) が無いときに呼ばれた表示の扱いは、機能と OS で揃っていなかった (2026-09-27 コード確認)。

| 機能 | Android | iOS |
|---|---|---|
| Dialog | その場で失敗する (「提示先が無い」エラー) | 同左 |
| Loading | 処理は実行する。提示先が現れた時点で、入りの演出から表示する | 処理は実行する。表示しないまま終わり、あとから提示先が現れても出し直さない |
| Toast | 提示先の出現を待って表示する (表示時間は受理時点から数える) | 契約は同左。ただし起動直後の呼び出しで一度も表示されない疑いがある |

- Dialog の「その場で失敗する」を決めた ADR は無い。core の結果通知の契約に「出す先の画面が存在しない場合は失敗する」とあり、コードのコメントに「キューイングはせず即座に失敗する」とあるだけだった
- Loading の OS 差は、core の Loading 契約で「承認済みの差ではない」差として記述されていた。OS の制約から来た差ではなく、iOS の実装が待っていないことによる

この不揃いは fix-ios-sample-demo-autoplay で表面化した。iOS Sample は、最初の画面の表示時の処理 (SwiftUI の `.task`) から表示を呼んでいた。書く側から見れば「画面が出てから動かす」書き方である。しかし iOS では、起動直後の画面は非アクティブのシーンで始まり、あとからアクティブになる。そのため表示時の処理の時点では、まだ提示先が無い。実測では、Loading は 3 回中 2 回出ず、Toast は 5 回とも出ず、Dialog は 3 回とも失敗した。同 change は範囲を Sample 側に絞り、「Dialog / Loading も提示先の出現を待つ」案を範囲の都合で見送った。

- 呼び出し元からの打ち切りは、iOS・Android・KMP の Dialog が受け付ける。MAUI の Dialog は打ち切りの手段を持たない
- ライブラリは `0.1.0-beta.1` / `0.1.0-beta.2` として公開済みである

前提: KMP と MAUI は、表示を各 OS の Native に委譲する (MAUI の Dialog は、自前の提示先の判定も持つ)。そのため、Native の振る舞いがそのまま KMP・MAUI の振る舞いになる。

## Decision

- 提示先が無いまま呼ばれた Dialog・Loading・Toast は、**失敗せず、提示先の出現を待って表示する**。全機能・全形態で揃える
- 待ちに共通の上限は設けない。**各機能の寿命が尽きるまで待つ**
  - Toast: 表示時間が尽きたら、表示されずに破棄される (既存の契約のまま)
  - Loading: 処理は通常どおり実行する。提示先が現れた時点で表示が続いていれば、入りの演出から表示する。先に表示が終われば、何も表示しない
  - Dialog: 呼び出し元が結果を待っている間、待ち続ける。結果が確定するか、呼び出し元が打ち切るまで待ちは終わらない
- 範囲に含めないもの:
  - 何を提示先とみなすかの定義 (上記の iOS・Android の定義を変えない)
  - 提示の仕組みそのものを持たない環境 (Native を持たない MAUI の素の .NET)。待っても提示先は現れないため、今までどおりその場で失敗する

理由: 「画面が出てから動かす」ごく普通の書き方が、iOS では提示先ができる前に当たる。Loading・Toast は、失敗も返さずに黙って消えるため、利用者が気づきにくい。Dialog だけその場で失敗すると、同じ場面で機能ごとに結末が分かれる。待ちの上限を各機能の寿命に任せれば、3 機能とも「自分の寿命が尽きるまで待つ」という 1 つの規則で説明できる。Dialog の寿命は「呼び出し元が結果を待っている間」で、利用者が答えなければもともと終わりの時点を持たない。そのため、提示先を待つ時間もその待ちの一部として扱える。

## Alternatives Considered

- **iOS の Loading は表示しないままとし、承認済みの OS 差として契約にする** — 却下。承認の理由が「iOS の実装がそうなっているから」になり、OS の制約に根拠を持たない。KMP・MAUI の共有コードの同じ呼び出しで、OS によって Loading が出たり出なかったりする
- **Dialog は今までどおりその場で失敗し、待つのは Loading・Toast に限る** — 却下。同じ「画面が出てから動かす」書き方で、Dialog だけが失敗する不揃いが残る
- **Dialog の待ちに決まった時間の上限を設け、過ぎたら失敗する** — 却下。起動直後に要る待ちは一瞬で、背面からの復帰に要る待ちには上限が無く、値の根拠を置きにくい。Dialog だけが時間の規則を持つことになる
- **Dialog の待つ時間を呼び出し元が指定できるようにする** — 却下。全形態の show の入口に引数が増える
- **アプリが前面にいる間だけ待ち、背面なら今までどおり失敗する** — 却下。背面にいる間に呼んだ Dialog は、戻っても失敗のままになる。Dialog だけが前面・背面の規則を持ち、「前面にいる」の定義を OS ごとに決める必要がある

## Consequences

- 正: 最初の画面の表示時の処理から呼んでも、Dialog・Loading・Toast が表示される
- 正: アプリが背面にいる間に呼んだ Dialog は、失敗せず、戻った時点で表示される
- 正: 提示先が無いときの振る舞いが全機能・全形態で揃い、core の契約から OS 差の記述が消える
- 負: 画面が現れない場所から呼んだ Dialog は、失敗せず、返らないまま待ち続ける。今まで失敗で気づけていたものに気づけなくなる。止める手段は呼び出し元の打ち切りだけになるため、手段を持たない形態 (現状の MAUI) には打ち切りを足す必要がある
- 負: 長く背面にいたあとに、古い文脈の Dialog が表示されることがある
- 負: 処理の終わり際に提示先が現れると、Loading が短い間だけ表示されて閉じる
- 負: 待っている間の Dialog をライブラリが抱えることになり、複数あるときに出る順番をライブラリが決める必要がある
- 負: 待ちが解ける合図と提示先の条件がずれると、表示されないまま終わる不具合になる。3 機能の待ちの仕組みを、提示先の定義と揃えて持つ必要がある
- 負: 公開済みベータの振る舞いが変わる。Dialog は全形態で、失敗していた呼び出しが待つようになる。iOS の Loading は、出なかった表示があとから出るようになる。「提示先が無い」エラーは、ほぼ使われなくなる
