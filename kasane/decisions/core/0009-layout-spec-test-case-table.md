## Context

core/ADR-0007 は「共通仕様テスト (同じ属性入力 → 期待されるサイズ・位置) を3形態に同型で課す」ことを規則1本化の成立条件とした。先行する最初の縦通し実装では「同名テストを各形態にミラーし、各形態が DialogTestHarness 等の Support 群を持つ」規約が初版として動いている。レイアウト検証は属性 × 画面サイズ × 配置のマトリクスでケース数が多く、手書きミラーでは形態間のケース漏れ・期待値ズレをレビューでしか防げない。

## Decision

- **共通ケース表**: 「screen (window サイズ)・insets・contentSize・attributes → 期待 rect (x, y, w, h)」のデータ表を単一の正とし、各形態のテストが同じ表を読み込んで検証する。規則文とケース表が対になり、規則の曖昧さはケース表の期待値で強制的に解消される
- **配置**: 表の実体はリポジトリルートの `core/layout-spec/cases.json` に置く。ケース表は「両 Native が参照する契約データ」であり、どのビルドルートにも属さない。ローダーを持つのは Native 2形態のみ
- **層別の責務分担**: レイアウト計算の実体は Native 2実装にしかない (core/ADR-0001 の薄いラッパー構成) ため、ケース表の全量検証は iOS/Android に課し、MAUI/KMP は「属性がネイティブへ正しくパススルーされる」ことの同型テストに留める。Native の検証は実測 (iOS = シミュレータ上のレイアウト完了後の実 frame、Android = instrumented test の実 View rect) とする — rect 計算関数だけの単体検証では LayoutParams / constraints への反映漏れを見逃す
- **凍結運用**: ケース表は提案フェーズで作成・凍結し、実装フェーズでは期待値を変更しない (受け入れ基準を実装者が同時に決められる循環を断つ)。属性セットの改訂時は表を作り直して再凍結する。ケース ID は参照の安定を優先して欠番方式で運用する (廃止ケースを取り除いても残りを振り直さない)
- **attributes は供給合成後の実効値**: ケース表は供給経路 (show 引数・添付・既定値の合成) によらずレイアウト規則だけを検証する。これにより供給機構の変更 (core/ADR-0015) がケース表に波及しない。優先順位の検証はケース表ではなく少数の Scenario テストが担う
- **OS 差の統制**: OS 差は該当ケースに置く `approvedDiff` (差し替える期待値 + `reason` + オーナー承認 `approvedBy`) でしか表現できない。reason と approvedBy のないエントリは無効で、それ以外の期待値分岐は認めない。座標比較の許容誤差 `tolerance` は表全体に1つ持つ (Android の整数丸めの吸収用)

## Alternatives Considered

- **同名テストの手書きミラー (既存規約の延長)** — 却下。ケース追加のたび4形態で期待値を目視同期する必要があり、形態間の期待値一致がレビュー頼みになる。導入コストはゼロだがレイアウトのマトリクス検証には不向き
- **ケース表を kasane/concepts/ 配下に置く案** — 却下。ビルド・テストがハーネス層を参照する結合が生まれる
- **ケース表を各ビルドルートへコピー配置する案** — 却下。単一の正が崩れる
- **ケース表を実装タスクで作る案** — 却下。受け入れ基準を実装者が同時に決められる循環が生まれる
- **供給経路別にケースを分ける案** — 却下。優先順位の検証は Scenario (少数) で足り、直積でケース数が爆発する

## Consequences

- 正: 期待値が単一ソース化され、形態間の一致が構造的に保証される。ケース追加は表に1行
- 正: 「テストがなければ規則は絵に描いた餅」(ADR-0007 の弱点) にケース表という実体で答えられる
- 正: OS 差が承認制 (approvedDiff) で統制され、ケース表が実装の追認に堕ちる逃げ道が塞がれる
- 負: 表ローダーを各形態のテスト Support に新設する導入コストを払う
- 負: データ駆動テストは素直なテストコードよりやや間接的で読みにくい
- 負: Android の全量検証は instrumented test を要し、CI コストの都合でローカル実行 + 証跡記録の運用になる
