status: proposed

## Context

Android の instrumented テストが API 35 で間欠的に落ちたのを調べた結果 (change `fix-android-container-system-bar-appearance`、2026-09-27 の実測)、器ごとにシステムバーの扱いが揃っていないことが分かった。

- Android の Dialog の器は、表示した時点で提示先の画面からアイコンの明暗・バーの表示/非表示・隠れたバーの再表示の作法を写していた。core/ADR-0008 の透明な覆いの正式対応と、core の「覆いに透明を指定しても、システムバーの見えは変わらない」という約束を支える作りである
- Android の Loading / Toast の器は何も写していなかった。ステータスバーの明暗は前面の全画面のアプリウィンドウで決まるため、明るい画面で Loading / Toast を出すと、表示中だけアイコンが白く変わった。Loading はフォーカスを取るので、バーを隠した画面で出すとバーを再出現させた
- core の Loading / Toast の規則にはシステムバーの約束が無い。Dialog の約束も「覆いが透明なら」の 1 文だけだった
- iOS の器は、ステータスバーの見えを何も指定していない (Dialog は提示元に重ねて表示し、Loading / Toast は画面の上に View を重ねるだけ)。ダーク外観で暗幕を敷く器の表示中に文字色が白くなるのは、ステータスバーの下に来た暗幕に合わせた OS の調整で、器が指定を変えたものではない
- Android では、提示先が旧来のフラグだけで明暗を指定していると、OS からその値を読み取れず、写すことができない

前提: iOS と Android のどちらでも、器は提示先のシステムバーの指定を変えずに表示できる。iOS は何も指定しないことで、Android は提示先の指定を読み取って器のウィンドウに写すことで、これを満たす。

## Decision

Dialog / Loading / Toast の器は、表示中も提示先の画面のシステムバーの指定 (アイコンの明暗・バーの表示/非表示・隠れたバーの再表示の作法) を変えない。これを全形態に共通する core の約束とし、Dialog の「覆いが透明ならシステムバーの見えは変わらない」もこの約束に含める。

境界: 暗幕 (覆い) がステータスバーの下を暗くしたときに、OS がそれに合わせて文字色を選ぶことは、この約束の外に置く。器は指定を変えておらず、見えの変化は OS の判断による。

理由: 約束を core に置けば、MAUI / KMP の利用者も 1 か所読むだけで、どの形態でも同じ前提で画面を作れると分かる。Loading / Toast で同じ退行が起きたときに、約束違反としてテストで捕まえられる。iOS の器はすでにこの約束を満たしているので、iOS のコードを変えずに全形態共通の約束にできる。

## Alternatives Considered

- **Android の公開面にだけ書く** — 却下: Android の利用者には伝わるが、MAUI / KMP の利用者には、ステータスバーの見えが変わるのが OS による差なのかどうかが分からない。退行を捕まえるのも Android のテストだけになる
- **約束は足さず、Android の Loading / Toast の不具合の修正としてだけ扱う** — 却下: 利用者から見える文書に書かれず、テストが何を守っているのかの根拠も文書に残らない

## Consequences

- 正: 利用者は、Dialog / Loading / Toast のどれを出しても、アプリのシステムバーの指定 (明暗・表示状態・再表示の作法) が保たれる前提で画面を作れる
- 正: MAUI / KMP の利用者も core の約束として読め、形態ごとの差を確かめなくてよい
- 正: iOS は現状のままで約束を満たす
- 負: Android では Loading / Toast の器にも提示先からの写しが要る。器の種類を増やすたびに同じ扱いが要り、写し漏れはそのまま約束違反になる
- 負: 暗幕による OS の文字色の調整は約束の外なので、暗幕を敷く器の表示中にステータスバーの文字色が変わる場合 (iOS のダーク外観など) があることを、利用者向けに説明する必要がある
- 負: Android では、OS が値を返さない書き方 (旧来のフラグだけ) で指定された明暗も約束の対象になるため、非推奨の API からの読み取りを持ち続ける必要がある
