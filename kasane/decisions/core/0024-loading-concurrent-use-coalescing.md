## Context

Loading は常にウィンドウ全体を覆う単一の表示である (表示スコープの指定は持たない)。その上で「表示中にもう一度 Loading を使おうとしたら何が起こるか」の契約を決める必要がある。

- 移植元 (AiForms.Maui.Dialogs) の挙動は OS 間でバラバラだった: iOS は表示中の再表示要求を黙って無視し、さらに StartAsync は前の表示の消滅を約 1.25 秒待って諦めると**渡された処理自体を実行せずに黙って return** する。Android は前の Fragment の破棄を待ってから必ず表示する
- 「処理が実行されない」「要求が黙って消える」は呼び出し側から観察できない失敗であり、契約として予測不能
- 複数の非同期処理が同時にローディング表示を使う状況は、現代的なアプリでは普通に起こる

## Decision

多重利用は**合流**とする: 重なった利用は1つの表示に合流し、表示は最初の開始から最後の終了まで継続する。

- 渡された処理 (StartAsync 相当の action) は、表示状態によらず**必ず実行される** — 「必ず」は合流・表示状態を理由に実行を保留・放棄しないという意味であり、構成ミス (未登録 VM 等) は処理の実行前に fail-fast で失敗してよい (2026-08-25 提案レビューでの明確化)
- メッセージ・進捗の表示は**最新の報告が勝つ** (後勝ち)
- 明示の hide は合流数によらず**即閉じる** (まだ走っている処理の表示が消えるのは呼び出し側の責任)

## Alternatives Considered

- **先勝ち・後は無視** (原典 iOS の改良 — 処理未実行だけは直す) — 却下: 並行利用で先の処理の完了とともに表示が消え、後の処理がまだ走っているのに操作ブロックが解けてしまう。黙った無視も残る
- **表示中の再表示要求をエラーとして通知** — 却下: 呼び出し側に毎回の状態確認・回避を強いる。ローディング表示は fire-and-forget で使える気軽さが本質で、エラー処理を要求する API は用途に合わない

## Consequences

- 正: 並行する非同期処理からの利用で表示が正しく「全処理の完了まで」継続する
- 正: すべての要求が意味を持ち (無視・未実行がない)、観察可能な意味論として Scenario テスト (ADR-0016) で固定できる
- 負: 合流カウントの管理 (開始・終了の対応付け) を Native 2実装がそれぞれ正しく持つ必要がある
- 負: 「hide は即閉じ」と合流の組み合わせにより、hide 後もまだ走っている処理は表示なしで走り続ける — この状況の妥当性は呼び出し側の判断に委ねられる
