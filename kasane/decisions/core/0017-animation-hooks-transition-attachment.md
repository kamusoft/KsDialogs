## Context

移植元の提示/退出アニメーションフック (RunPresentationAnimation / RunDismissalAnimation) は、基底ビューの引数なし void 仮想メソッドで、OS 側の 250ms トランジションとの時間による暗黙同期に依存する (README 自身が「250ms を超えるアニメは中断されうる」と脆さを自認)。KsDialogs の登録モデル (View factory + 宣言的 UI) には利用者が継承する基底がなく、運び方の再設計が必要だった。

既定の出現/消滅について、KsDialogs は OS 既定トランジション任せだったが、iOS の crossDissolve は演出が見える一方、Android の Dialog 既定は実質トランジション無しで、既定品質が OS 間で割れていた。

退出演出は器が閉鎖を実行するため器の協力なしには実現できず、特に cancelled 経路 (外側タップ・戻るボタン) はライブラリ発の閉鎖でアプリ側から割り込めない。退出の完了を待つ以上、「結果が決まった瞬間」と「show が返る瞬間」が分かれ、その間に起きる二重報告・器の消失・閉鎖信号の重なりの扱いを決める必要があった。

## Decision

1. **両フック**: presentation / dismissal の両方を提供する (片側のみは非対称で使いにくい — オーナー判断)。どちらも省略可で、省略した側には器の既定の演出が適用される
2. **完了通知つき**: フックは async/suspend とし、器は dismissal フックの完了を待ってから閉鎖する。原典の時間による暗黙同期は継承せず、**フックの完了に上限 (タイムアウト) を設けない** — フックが有限時間で完了することは利用者の責務 (契約の前提条件) とする。ただし契約違反に陥っても次の 2 経路では器がフックを見捨てて先に進む (脱出口): (a) 呼び出し元キャンセル (Swift / Kotlin) は実行中のフックを打ち切って撤去・配送へ進む、(b) OS 発の器消失は下記 5 のとおり。開発支援として、デバッグビルドではフックが一定時間 (既定 5 秒、契約ではなく警告閾値) を超えた時点で警告ログを出す (打ち切りはしない)
3. **供給は第3の添付スロット `DialogTransition`**: DialogOptions / DialogPlacement と同じ添付機構 (core/ADR-0015 の枠) で運び、**採用時点も属性と同じ初回レイアウトパス完了時点**とする (以後の添付変更には追随しない)。DialogOptions への内蔵はしない — クロージャは等値比較不能で、ADR-0015 の値オブジェクト契約・スナップショット凍結契約に振る舞いを混ぜない。show 引数でも受けない (置き場所と違って呼び出しごとに変える需要がなく、供給点を増やさない)
4. **フックは統一形**: 4形態 × 2技術系すべてで「コンテンツのプラットフォーム View (宣言的 UI ではホスト View) を受け取る」1つの型 (`suspend (View) -> Unit` / `@MainActor (UIView) async throws -> Void` / `Func<VisualElement, Task>` — 失敗の表現力を3形態で揃える)。宣言的 UI のコンテンツも器の中では必ずプラットフォーム View に包まれている (Compose = AbstractComposeView 派生ホスト、SwiftUI = UIHostingController の view。core/ADR-0011 の単一系統) ため成立する。フックは UI スレッド (iOS = MainActor / Android = Main / MAUI = UI スレッド) で開始し、呼ばれた時点でホスト View はウィンドウ上にありレイアウト済み・属性凍結済みである
5. **実行する閉鎖経路**: 退出フックを実行するのは**ライブラリ発の閉鎖経路** (報告・外側タップ・戻るボタン・呼び出し元キャンセル) で、**高々1回** (最初の閉鎖信号だけが退出を始め、以後の信号は no-op)。OS 発の器消失 (画面破棄・提示関係の外部からの解除 — core/ADR-0006 規則6) では器が既に画面を失っており演出不能のため実行せず、未確定なら cancelled をラッチし、実行中のフックがあれば打ち切って (MAUI は待つのをやめて) 直ちに撤去・配送する。閉鎖原因の識別 (報告 / 外側タップ / 戻る / 呼び出し元キャンセル / 器消失) は内部に留め、公開 API には出さない (結果通知契約の「どの操作でキャンセルされたかの内訳は返さない」を維持)
6. **ラッチと配送の分離**: 結果は最初の報告 (completed / cancelled) で不可逆に確定 (**ラッチ**) し、呼び出し元への**配送**は「dismissal フックとオーバーレイの消滅 (並行) の両方の完了 → 器の撤去」の**後**に行う。退出中の二重報告・退出中の OS 発器消失でも、ラッチ済みの結果が配送される。この結果、添付の有無によらず**全 show の完了時刻が既定の退出処理の分 (約 250ms) 遅れる**
7. **既定はライブラリ実装のクロスフェード** (原典 250ms 相当): OS 既定トランジションは使わず、器が両 OS とも自前で入退場を駆動する (iOS は `present(animated: false)` / `dismiss(animated: false)`、Android はウィンドウアニメーションに頼らない)。既定クロスフェードも内部的にプリセット fade と同じ実行経路を通す (フック実行経路が常時使われテストされる)
8. **添付したフックは既定を置き換える (合成しない)**。オーバーレイ (背後の覆い) はコンテンツのホスト View とは**別レイヤ** (親子にしない) で、フックの有無・プリセットの種類によらず器が常にフェード駆動する。フェード時間は `DialogTransition.overlayDuration` に従い (プリセットは自身の duration を自動設定、カスタムフックでは省略可 = 既定 250ms)、イージングは器の標準に固定。フックはオーバーレイに触れない。`none` プリセットはコンテンツ側だけ無演出で、オーバーレイは既定どおりフェードする
9. **プリセット**: fade / slide (4方向、leading・trailing はレイアウト方向追随) / zoom (開始 0.8 倍) / none を `DialogTransition` の factory として提供し、none 以外は duration (既定 250ms) と easing を引数に取る。easing は形態ごとのネイティブ表現 (Android = Interpolator / iOS = UITimingCurveProvider / MAUI = Easing) をそのまま受け、形態横断の easing 抽象は作らない。成立しない duration (0・負値・NaN・無限大・形態のアニメーション API が扱えない大きさ) は例外にも丸めにもせず、そのフックは演出なしで即完了する (overlayDuration も同じ規則)。MAUI のプリセットは C# 側で MAUI アニメーション API により実装し、カスタムフックと同じブリッジ経路を通す (プリセット記述子の DTO は作らない)
10. **器の状態機械**: `created → attached → presenting → shown → dismissing → removed`。attached の間 (ウィンドウに載せてから初回レイアウトパス完了まで) は中身もオーバーレイも非表示で、presenting に入る時点で**中身の表示と presentation フックの開始を同時に**行う (最終位置が一瞬見えるちらつきを構造的に防ぐ)。提示前 (created / attached) の閉鎖信号は両フックとも実行せず演出なしで撤去・配送する。presenting 中の報告・外側タップ・戻るは presentation を完走させてから dismissing へ進む (直列。中断しない。呼び出し元キャンセルだけは presentation を打ち切って dismissing へ進み、dismissal は実行する)。dismissing 中は入力を受け付けない。presenting の完了条件は presentation フック完了かつオーバーレイの出現フェード完了
11. **フックの失敗は演出の失敗であって結果の失敗ではない**: throw / fault / cancel は器が吸収してデバッグログに残すだけで、presentation の失敗でも shown へ進んで報告を受け付け (途中まで変えた見た目はライブラリが復元しない)、dismissal の失敗でも撤去を続行してラッチ済みの結果を配送する
12. **MAUI のブリッジ**: 両 Native のブリッジ (iOS ObjC 互換面 / Android Java 互換面) はコンテンツ単位の実行口 (`runPresentation(view, completion)` / `runDismissal(view, completion)` 相当) と `overlayDuration` を運び、Native の器は completion が呼ばれるまで待つ。C# 側は Task の完了 (成功 / fault / cancel のいずれでも) で completion をちょうど1回呼ぶ。MAUI の呼び出し元への配送の合図はブリッジの閉鎖完了通知 (撤去後) であり、ラッチ (結果の確定) とは別に運ぶ。糖衣 (`IDialogTransitionAware` 等の interface / 仮想メソッド形) は設けず、添付プロパティの code-behind 供給のみ
13. **KMP**: kmp/ADR-0002 (レジストリ実体は各 Native へ全委譲) により、添付は各 Native 側で書くものなので共有コード側の API は増えない

## Alternatives Considered

- **dismissal フックのみ (presentation は onAppear 等の標準手段に委ねる)** — 却下 (オーナー判断)。ADR-0014 の基準には忠実だが、片側だけの対応は非対称で使いにくい
- **両フック必須** — 却下。未指定側の「既定と同じ」を利用者が書けない (既定実装は内部)
- **形態横断の共通フック型を core に置く** — 却下。フックが受け取る View もアニメーション API も形態固有で、共通化すると型消去とブリッジだけが増える (core/ADR-0007 と同じ「観察可能な規則だけ共通化」の構図)
- **DialogOptions にクロージャプロパティを内蔵する案** — 却下。値オブジェクトに振る舞いが混入し ADR-0015 の改訂が必要になる
- **transition を show 呼び出し時点で読む案** — 却下。宣言的 UI の添付は初回レイアウト中に届くため取りこぼす
- **宣言的 UI は慣用形 (phase 通知を CompositionLocal / Environment で流し、中身が演出して完了報告する) とする案** — 今回は却下、将来の非破壊追加候補として保留。完了報告の呼び忘れ→閉鎖待ち続けに対するタイムアウト救済設計が必須になり、入場の自己管理・Compose の完了検知イディオムも利用者負担が大きい。添付スロットと器の退場待ち機構は共通のため、要素単位の退場演出の需要が出たら後から足せる (もっと綺麗な形にできる余地あり — オーナー感触)
- **移植しない (フックなし)** — 却下。cancelled 経路の退出演出が不可能になる
- **既定を OS 既定トランジションのまま維持する案** — 却下。Android の既定が実質無演出で、既定品質が OS 間で割れる
- **iOS は crossDissolve を維持しフック時のみ自前駆動する案** — 却下。既定とフックで閉鎖経路が2系統になり、退出待ちの検証対象が倍になる
- **iOS を UIViewControllerTransitioningDelegate で実装する案** — 却下。提示機構の委譲 (core/ADR-0006) に自前 presentation controller を重ねる原典構成への回帰で、多段表示の OS 差の前提が変わるリスクを負う
- **原典同様フックを既定アニメと並走させる (合成する) 案** — 却下。原典のフックは「コンテンツ内部の追加演出」だったが、本設計のフックは「入退場そのものの差し替え」であり、合成すると slide 指定でもフェードがかかり予測可能性が壊れる
- **オーバーレイもフックに渡す案** — 却下。覆いの演出まで利用者責務になると、既定の見た目の一貫性 (モーダル感) が崩れやすい。需要が出たら非破壊で拡張できる
- **オーバーレイをコンテンツの親にする案** — 却下。覆いのフェードがコンテンツの演出を巻き込み、コンテンツ側の duration / easing が観察できなくなる (動的モックで実証)
- **none をオーバーレイ含む全演出の無効化にする案** — 却下。覆いが瞬時に消えるとモーダル化の表現が OS 間で割れ、none の用途 (テスト・演出抑制) に覆いの扱いまで混ざる
- **結果は即配送し、アニメは並走させる案** — 却下。撤去前に配送すると、結果を受けて次のダイアログを出す典型フローで前のダイアログがまだ見えている競合が生まれ、「show が返った = 消えた」という素朴な期待を裏切る
- **フックに安全弁タイムアウトを設ける (上限超過で打ち切り・撤去・配送) 案** — 却下 (オーナー判断)。宙吊りを構造的に排除できる代わりに、正しい長い演出まで上限で打ち切られる新しい誤動作が生まれ、原典の「250ms を超えると中断」の脆さを値を変えて再生産する。上限値が契約になり API も増える。バグのあるフックは「ダイアログが閉じない」という見える症状で発見できるため、前提条件 + 脱出口 + デバッグ警告の方が公開ライブラリとして筋が良い。opt-in のタイムアウト引数も同じ理由で却下 (MAUI では打ち切れない非対称も残る。需要が出たら非破壊追加できる)
- **OS 発の器消失でもフックを実行する案** — 却下。器が画面を失った後に演出は物理的に不能で、実行しても観察できない
- **フックの失敗で show を失敗させる案** — 却下。利用者は結果 (OK/キャンセル) を既に報告済みで、演出のバグで業務結果が失われるのは本末転倒
- **Kotlin でも `.cancelled` を返す (CancellationException を握りつぶす) 案** — 却下。コルーチン規約違反で、構造化並行性 (親のキャンセル伝播) を壊す
- **presentation 中の閉鎖で presentation を中断し即退出する案** — 却下。中断位置からの退出演出が定義困難で、プリセットの対称ペアが崩れる
- **fade のみで出発する案 / バウンス・スプリングまで初期提供する案** — いずれも却下。前者は既定と同じで単独では価値が薄く、後者はパラメータ設計が OS 間で揃えにくく需要も未確認 (iOS の easing を `UITimingCurveProvider` にしたのは spring を後から受けられるようにするため)
- **MAUI のプリセットをネイティブプリセットへ写像する案** — 却下。ブリッジに「プリセット記述子」DTO が増え、カスタムフックと2経路になる。C# 実装なら1経路で済む
- **MAUI 側で Task 完了を待ってから Native の閉鎖を呼ぶ (Native は待たない) 案** — 却下。presentation 側は Native が表示を駆動するため MAUI 側で待てず、入退場で機構が割れる。退出でも外側タップ等の Native 発閉鎖に MAUI が割り込めない
- **MAUI の糖衣 (IDialogTransitionAware interface / 原典同様の仮想メソッド)** — 却下。前者は添付と interface の2経路になり優先順位規則が必要になり、後者は基底クラス継承の強制が登録モデル (任意の View を factory で返す) と衝突する

## Consequences

- 正: フック型が全形態・全技術系で1つになり、文書・テスト・実装が単線で済む
- 正: 完了通知方式により原典の「250ms を超えると中断」の脆さが消える
- 正: cancelled 経路を含むライブラリ発の全閉鎖経路で退出演出が保証される (OS 発の器消失のみ例外)
- 正: 既定クロスフェードにより Android でも無演出でなくなり、既定も同じ経路を通るためフック実行経路が常時検証される
- 正: show が返った時点でダイアログは画面にないことが保証され、結果を受けて次のダイアログを出す流れで競合しない
- 負: **添付の有無によらず全 show の完了時刻が既定の退出処理の分 (約 250ms) 遅れる**。即時配送を前提にした利用コード・テストは影響を受ける
- 負: 利用者のバグ (完了しないフック) で「ダイアログが閉じない」症状が出る経路を契約の前提条件として受け入れる。MAUI は show が CancellationToken を受けずフックの Task も打ち切れないため、脱出口が OS 発の器消失だけになる
- 負: 宣言的 UI のフック内だけ UIKit / Android View の API が混ざる (ブロック単位の入退場演出には実用上十分)
- 負: MAUI はクロージャを XAML に書けないため code-behind 供給になる
- 負: MAUI ブリッジの ABI に実行口 (フック 2 本 + overlayDuration + 閉鎖完了通知) が増え、binding の再生成を伴う
- 負: 器の閉鎖経路に「フック完了の await」と「撤去完了の待ち合わせ」が入り、退出タイミングの検証 (core/ADR-0016 の Scenario テスト) が必要になる。iOS では撤去の要求から完了通知までの間に提示機構が器を手放しうるため、配送口は器の寿命から独立させる (器が撤去まで進めずに解放されても show は返る)
- 負: iOS のプリセット factory は `@MainActor` で呼ぶ必要がある — 既定の easing (`UICubicTimingParameters`) が MainActor 隔離のため、nonisolated な既定引数として書けない。添付を書く場所 (UIView の初期化・SwiftUI の body) はいずれも MainActor なので通常は意識せずに済む
- 負: iOS の「中身の表示と presentation フック開始の同時性」(決定 10) は、フック型が `@MainActor` で宣言されているため同一アクター上の直接 `await` が最初の中断点まで同期実行される性質に依存する。中断のない開始を明示できる `Task.immediate` は iOS 26 以降で、最低対応 OS (iOS 17) では使えない — 最低対応 OS を上げる時点で置き換えを検討する。この性質はデルタスペックの Scenario (UI lint でフレーム記述を禁じる) ではなく回帰テストと実機の録画フレームで固定する
- 負: フック未完了のデバッグ警告の有効条件が非対称 — iOS はライブラリ自身のビルド構成 (`#if DEBUG`。SPM ソース配布では利用者の Debug と一致する)、Android は提示先アプリの `FLAG_DEBUGGABLE`。プリビルド xcframework 配布へ変える際は iOS 側の判定を見直す
- 負: 成立しない duration の境界が形態で微妙に違う — Android は `kotlin.time.Duration` をミリ秒に落とすと 0 になる正の微小値 (例 0.5ms) も即完了扱い (iOS は 0.5ms のアニメーションを組む)
