## Context

core/ADR-0041 で、提示先が無いまま呼ばれた Toast は、失敗せず提示先の出現を待つことになった。待ちの上限は Toast の寿命で、寿命は表示時間である。表示時間は受理の時点から実時間で数え、アプリが背面にいる間も進む (core の Toast の契約の時間モデル)。

Android の提示先は resumed な Activity である。起動直後は「最初の画面の表示時の処理 → 画面が resumed になる → 最初の描画 → 起動画面の退場」の順に進む。Toast は resumed の時点で提示先に載るが、まだ起動画面の下にある。利用者に見える時間は「表示時間 −(受理から起動画面の退場まで)」になり、起動が遅いほど短くなる。これが 0 以下なら一度も見えずに終わる。

Sample の自動再生での実測 (API 36 のエミュレータ):
- Sample 側の待ち (受理を最初の描画の後まで遅らせる処理) を外すと、Android 系 3 ルートで起動直後の Toast が出ない回が増えた。例: KMP Android の既定 Toast は 5 回中 5 回 → 1 回、Android のインライン経路の Toast は 3 回 → 0 回
- 待ちを戻しても、表示時間 1500 ms の既定 Toast は 5 回中 3 回しか出なかった。出なかった 2 回は、起動から最初の描画までが 4.8 秒と 6.9 秒の回だった
- Dialog と Loading は、寿命が表示時間で切れないので全回で表示された。iOS 系では起きていない

提示先の条件を「利用者に見えている画面」まで強めても、受理の時点から数える限り、見える時間の式は変わらない。見えないまま表示時間を使い切っていた表示が、「表示されずに破棄」に変わるだけである。この問題はエラーにもならないので、利用者は気づきにくい。

アプリが前面にいても提示先が無い場面は、画面を開いている途中 (起動・背面からの復帰・画面の切り替え・作り直し) のほかに、割り込み (システムの許可ダイアログ、コントロールセンターなど) で提示先を一時的に失っている間がある。この 2 つを見分けるには、画面やシーンの状態がどう移ってきたかの履歴が要る。Android のライブラリはアプリの起動時から Activity の追跡を始めるので、履歴を持てる。iOS のライブラリにはアプリの起動時に自動で動き出す仕組みが無く、シーンの通知は表示を待っている間だけ購読する。利用者が最初にライブラリを呼ぶのは、たいてい最初の画面の表示時の処理である。その時点では、起動の途中を知らせる通知はもう過ぎている。

前提:

- KMP と MAUI は表示を各 OS の Native に委譲するので、Native の振る舞いがそのまま KMP・MAUI の振る舞いになる
- 各 OS で、アプリが前面にいるかどうかと、画面が利用者に見えた時点を、利用者のコードの協力なしにライブラリが判定できる
- Android は起動画面の退場そのものをアプリに通知しない。ライブラリから観測できる最も近い合図は、画面の実際の描画である

## Decision

アプリが前面にいるのに提示先が無い間に受け付けた Toast は、表示時間を受理の時点ではなく、提示先に載った時点 (画面が利用者に見えた時点) から数える。

- 前面にいるとは、アプリの画面が背面に下がっていないことを指す。画面を開いている途中と、割り込みで提示先を一時的に失っている間の両方を含む
- アプリが背面にいる間に受け付けた Toast は、従来どおり受理の時点から実時間で数える
- 提示先に載らないままアプリが背面に下がったら、この扱いはそこで終わり、下がった時点から数え始める
- 全形態で揃える

core/ADR-0041 の決定のうち、Toast の寿命 (受理の時点から数えた表示時間) を、アプリが前面にいるのに提示先が無い間に受け付けた Toast に限って本決定で置き換える。他の決定は維持する。

範囲に含めないもの:

- 何を提示先とみなすかの定義
- 前面にいるかどうかを判定する各 OS の手段
- Dialog・Loading の寿命 (どちらも表示時間を持たず、この問題は起きない)

理由:

- 最初の画面の表示時の処理から Toast を呼ぶのは普通の書き方だが、起動の遅い構成ほど Toast が見えないまま終わる。原因は、利用者が画面を待っている間に表示時間を使ってしまうことなので、その間だけ数えない
- 背面にいる間に呼んだ Toast まで「見えてから数える」にすると、戻ったときに古い通知がまとめて出るので、背面の扱いは変えない
- 前面・背面だけで分ければ、今の状態だけで決まり、両 OS を同じ規則で言える。ライブラリを呼び始めた時点にも左右されない

## Alternatives Considered

- **受理の時点から数えたまま、Android の提示先の条件だけを「見えている画面」に強める** — 却下。見える時間は「表示時間 −(受理から見えるまで)」のままで、起動直後に見える Toast は増えない。見えないまま使い切っていた表示が、表示されずに破棄される表示に変わるだけ
- **すべての Toast を、画面に出た時点から数える** — 却下。背面にいる間に呼んだ Toast が待ち続け、戻ったときにまとめて出る (古い通知が溜まる)。Toast も Dialog と同じく、上限なく待つことになる
- **提示先が無い間は、表示時間を止める** — 却下。背面にいる間に呼んだ Toast が、戻ったときに残りの時間だけ古い通知として出る。「背面にいる間も時間が進む」をやめることになる
- **画面を開いている途中 (起動・背面からの復帰など) に限り、割り込みの最中は含めない** — 却下。見分けるには状態の履歴が要る。iOS のライブラリは起動時に動き出せず、最初に呼ばれた時点では起動の途中の通知が過ぎているので、判定に推定が混じる。割り込みの下で Toast が見えないまま終わることも残る

## Consequences

- 正: 最初の画面の表示時の処理から呼んだ Toast が、画面が見えてから表示時間いっぱい表示される。起動の遅い構成や、負荷の高い端末でも、見えないまま終わらない
- 正: 起動直後の Toast のために、Sample や利用者のアプリが呼び出しを最初の描画の後まで遅らせる必要がなくなる
- 正: 割り込み (許可ダイアログなど) の最中に受け付けた Toast は、割り込みが終わってから表示時間いっぱい表示される
- 正: 背面にいる間に呼んだ Toast の扱いは変わらない
- 負: Toast の寿命の規則が、受け付けた時点の状態で 2 通りに分かれる。ADR-0041 の「3 機能とも自分の寿命が尽きるまで待つ」のうち、Toast の寿命が 1 文では説明できなくなる
- 負: 各形態で、前面にいるかどうかと、提示先に載ったかを判定する手段を持つ必要がある。判定と実際の見え方がずれると、前面で待っている Toast が見えないまま時間を使うか、見えてから遅れて数え始める
- 負: 前面にいるのに提示先が長く現れない間 (アプリが起動画面を延ばしている、許可ダイアログを出したままなど) に受け付けた Toast は、受け付けてから出るまでが長くなる
- 負: 公開済みベータの振る舞いが変わる。起動直後や割り込みの最中に受け付けた Toast は、以前より遅れて出て、長く表示される
