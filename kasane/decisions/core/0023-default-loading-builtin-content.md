## Context

Loading の器とコンテンツの構成は「器は OS 提示スタックから分離し、コンテンツ載せ・レイアウト・演出の部品を Dialog と共有する」と決めた (ADR-0022)。その上で、引数なしで呼べる既定ローディング (スピナー + メッセージ) をどう実現するかを決める必要がある。

- 移植元 (AiForms.Maui.Dialogs) は既定ローディングをネイティブ部品の直接組み立て (iOS: UIActivityIndicatorView + UILabel を直組み) で実現し、カスタム View 版 (View ホスティング経路) とは別経路にしていた
- その帰結として、既定専用の設定オブジェクト (LoadingConfig) がカスタム View には一切効かない・スタイル指定の流儀が2つに分裂する、という歪みが生じていた。また LoadingConfig は初回初期化の一度きりしか適用されず、表示後の変更が効かない弱点があった

## Decision

既定ローディングは、ライブラリが同梱するローディングコンテンツ (スピナー + メッセージ) を、カスタム View 版と同じ共有部品 (コンテンツホスティング・レイアウト規則・演出の添付) に載せて実現する。ネイティブ部品を直接組み立てる専用経路は作らない。

styling は内蔵コンテンツ固有の項目 (インジケータ色・メッセージのフォントサイズと色・既定メッセージ・進捗フォーマット) を1つのスタイル値オブジェクトにまとめ、アプリ側で一括設定する口のみとする。表示 API (show / StartAsync 相当) にスタイル引数は設けない。器はスタイルを各表示の開始時に読み、設定変更は次の表示から効く (表示中の変更は効かない)。色を含むため KMP 共有コード (commonMain) からは設定できず、各 OS 側で設定する (DialogOptions と同じ非対称)。

なお配置オフセットは DialogPlacement (offsetX / offsetY)、背後の覆いの色は DialogOptions (overlayColor — アルファ込みのため原典の Opacity も吸収) が既にカバーしており、Loading 用に重複した属性は設けない。

## Alternatives Considered

- **原典踏襲の native 直組み** — 各 OS がスピナー + ラベルを直接組み、styling は Loading 専用の設定オブジェクトで受ける。却下: ADR-0022 で共有した部品と別に、オーバーレイ内の組み立て・配置コードを Native 2実装で二重に持つことになる。また既定とカスタムで経路が分かれると、演出・表示スコープ・単一性の仕様を2通り定義する必要が生じ、原典の「LoadingConfig が既定にしか効かない」流儀の分裂を再生産する
- **styling を表示 API の引数で都度指定** — 却下: ローディングの見た目はアプリ全体で1つという静的な性質に反し、呼び出しごとに変えられる誤用の口になる (DialogOptions に show 引数を設けない ADR-0015 と同じ理由)。表示 API の引数も膨らむ
- **styling 面を持たない** (見た目を変えたい利用者はカスタム View へ誘導) — 却下: 実装は最小になるが、移植元仕様 (LoadingConfig 相当) の明確な削り込みになり、Loading の主要機能の移植完了というロードマップのゴールに反する

## Consequences

- 正: 演出・表示スコープ・単一性の仕様と実装が、既定・カスタムの区別なく Loading 全体で一本化される
- 正: 共有部品 (ホスティング・レイアウト・演出) の検証がそのまま既定ローディングにも効く
- 負: 既定ローディングの表示もホスティングを一段通るため、最短経路 (native 直組み) に比べ表示までの処理は増える (実害は小さい見込み)
- 負: 内蔵コンテンツの見た目と属性が公開 API 表面になり、変更に互換性の配慮が必要になる
- 正: スタイルを各表示の開始時に読むため、設定変更が次の表示から効く (原典 LoadingConfig の「初回初期化の一度きりしか適用されない」弱点を解消)
- 負: スタイル値オブジェクトの設定の置き場 (受け口) を形態ごとに設ける必要があり、KMP 共有コードからは設定できない非対称が残る
