## Context

core/ADR-0006 は多段表示を OS の提示機構へ委譲し、「OS 間の挙動差は共通仕様テストで記録し、仕様側に明記して吸収する」ことを成立条件とした。レイアウト領域には core/ADR-0009 の共通ケース表 (cases.json + approvedDiff) があるが、これは属性 × 画面 × 配置のマトリクス検証のための器であり、同 ADR 自身が「マトリクスでない検証は少数の Scenario テストが担う」と切り分けている。

提示挙動 (多段表示の閉じ順・器消失時の cancelled 確定・出入りの演出の順序と完了待ち・ウィンドウ変化への追随・システムバーの引き継ぎ) は「show A → show B → A を先に報告 → B を観察」のような**系列**であり、ケース数は領域ごとに数本から数十本程度。実測済みの OS 間差 (下の段を先に閉じたときの見え方等) は concepts/core/api/multi-display-semantics.md の差分表としてオーナー確認済みで記録されている。

挙動の契約は concepts の本文に散って書かれるため、「この文の挙動はどのテストが固定しているか」を文書とテストの双方から機械的に辿れる手段も要る。

## Decision

- **検証方式**: 挙動系の共通仕様は、Native 2実装への同名 Scenario テストで検証する。データ表 (cases.json 方式) は流用も新設もしない
- **安定 ID**: 挙動系の Scenario には `PB-<領域>-<NN>` 形式の安定 ID を付け (例 `PB-MD-01`。領域は TR = 演出 / MD = 多段表示 / WN = ウィンドウ変化 / SB = システムバー / KC = KMP 経路 / IA・AA・MA = 各形態の添付面 / SM = Sample のように 2 文字で表す)、デルタスペックの Scenario 見出しとテスト名の両方に含めて機械的に対応付ける。concepts の本文は該当箇所に ID を添え、文書 → テストの接地アンカーとする。テスト名の表記は言語の制約に従って割れてよい (Swift の表示名 `[PB-MD-01] …` / Kotlin・C# の関数名 `PB_MD_01_…`) — 突合側が正規化する
- **網羅の検査は仕様の外に置く**: 「全 ID のテストが存在し green」のような自己参照のメタ Scenario はデルタスペックに書かない。ID の網羅性は検査スクリプト `scripts/scenario-id-coverage.py` (Scenario 見出しの ID とテストの宣言に現れる ID を突合。archive 済みの仕様も既定で走査する) でローカルに検査する。ID を数えるのはテストの宣言 (関数名と直前の属性) だけで、コメントや文字列中の ID は網羅と見なさない
- **OS 間差の正**: 期待値が OS で割れる挙動は、concepts の該当文書 (多段表示なら multi-display-semantics.md) の差分表を正とし、各 Native の Scenario テストは自 OS の期待値をその表に従って検証する。ID は共通のまま THEN だけが割れる。テストが表にない OS 差を吸収してはならない — 新たな差が実測で見つかったら、先に concepts の差分表へ追記 (オーナー確認) してからテストを追随させる
- **既存テストの扱い**: 同じ挙動を固定している既存テストは作り直さず温存し、ID を 1 対 1 で付与する (改名のみ、期待値不変)
- **実ウィンドウが要る挙動だけを instrumented に置く**: 契約ロジックは JVM / シミュレータの単体テストで、実提示機構・実ウィンドウ・実入力が要る系列 (下先閉じの OS 差・器消失・ウィンドウ変化・出入りの順序と完了待ち・システムバー) だけを instrumented / 実 UIWindow のテストに置く
- **層別の責務**: core/ADR-0009 の層別分担に準拠する。挙動の実体は Native 2実装にあるため全量検証は iOS/Android に課し、MAUI/KMP はパススルー検証に留める。演出の見た目 (実際の動き) は自動テストの対象外とし、実機確認と証跡記録で受け入れる — 自動テストが固定するのは順序と完了待ちだけ
- **実行運用**: Android の検証は instrumented test を要するため、ADR-0009 と同じ「ローカル実行 + 証跡記録」の運用に乗る

## Alternatives Considered

- **挙動ケース表の新設 (approvedDiff 流用)** — 却下。系列挙動をデータ表現する独自スキーマの設計・ローダー実装が、領域あたり数本のケースには過剰投資。approvedDiff の構造的統制は魅力だが、挙動差の正は既にオーナー確認済みの concepts 差分表として存在し、テストがそれを参照する形で統制は保てる
- **ドキュメント記録のみ (自動テスト化しない)** — 却下。器消失検知 → cancelled 確定などの実装退行を検知できず、core/ADR-0007 で自覚済みの弱点「テストがなければ規則は絵に描いた餅」へ逆行する
- **既存テストを捨てて instrumented に全面移行する案** — 却下。契約ロジックの高速な JVM 検証を失い、CI コストだけ増える
- **スクリーンショット比較で演出も自動検証する案** — 却下。中間フレームの比較は端末・タイミング依存で flaky の温床
- **「全 ID のテストが存在する」をメタ Scenario として spec に書く案** — 却下。自己参照で Scenario の体をなさず、網羅性はテスト外の検査で機械的に見られる

## Consequences

- 正: 既存の Scenario テスト規約にそのまま乗り、導入コストが低い
- 正: 多段表示に限らず、後続の挙動差記録 (出入りの演出・ウィンドウ変化・システムバー) が同じ枠組みに乗った
- 正: concepts 本文の ID から固定しているテストへ、テスト名から仕様の Scenario へ、どちら向きにも grep で辿れる。仕様が archive へ移っても ID の対応は保たれる (網羅検査が archive を既定で走査する)
- 負: 統制は approvedDiff ほど構造的でない — テストと concepts 差分表の一致はレビュー頼みになる
- 負: 同名ミラーの iOS/Android 間同期は手動 — ケース数が少数である前提が崩れたら (マトリクス化したら) ADR-0009 方式への移行を検討する。ミラー実装は同じ設計から独立に書くため、片方が踏んだ穴は他方にも高確率で存在し、同じ設計から書いたテストは同じ盲点を持つ
- 負: 網羅検査はローカル実行 (リポジトリに CI ワークフローがない) のため、回し忘れは人の規律に依る
- 負: ID を持たない Scenario (Sample の通し確認など、自動テストで受け止められないもの) は検査の除外指定に並べる必要がある
