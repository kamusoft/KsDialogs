## Context

Sample の撮影証跡 (視覚照合・4ルート通し) の収集が実装フェーズの最大コストになっている。add-loading の実測では Samples フェーズ約 139 分の大半が「6アプリのビルド+デプロイ」「撮影用の一時改変 (刻み間隔延長・デモ先出し) の出し入れと復元確認」「状態を作る手動タップの再現」で、撮影そのものではなかった。一時改変の復元では実装を巻き戻す事故も発生している (lessons/inbox の verification-temp-edit-restore-by-copy-not-checkout)。撮影手順は kasane/config.yaml の `ui.screenshot` に文章メモがあるだけで、ワーカーが毎回手順を再構築していた。

調査 (add-sample-capture-automation の探索) で判明した前提: 起動引数を読む箇所は6アプリとも当時ゼロ、Android は両ルートともランチャー Activity が exported 済みで intent extra がそのまま通り、MAUI iOS は `Platforms/iOS/Program.cs` が引数を素通し済み。KMP のデモ起動ロジックは共有 Presenter に集約済み (例外は Inline Dialog のみ)。デモを識別する ID は存在せず、ルート間対応は文言のみ (cross/ADR-0007 の一致単位)。

起票時は「デモ駆動モード + 単一入口の撮影スクリプト」の2本構成 (補完関係) として決定したが、実装フェーズで iOS シミュレータへの座標タップをスクリプトから注入する CLI 手段が環境に無いことが判明した (simctl 単体に入力注入なし。従来の手順メモが挙げる「シミュレータ操作ツール」はエージェント専用 MCP でスクリプトから呼べない)。外部ツール導入 (idb 等)・XCUITest ランナー同梱はいずれもオーナー判断で不採用とし、撮影スクリプトは取り下げた (2026-08-27 改訂)。

## Decision

Sample の撮影自動化は**デモ駆動モード**で行い、専用の撮影スクリプトは持たない:

1. **Sample のデモ駆動モード**: 起動時の引数渡し (iOS = launch argument / Android = intent extra) で「指定デモの自動再生」「Loading 進捗の刻み間隔の変更 (ms 直指定)」を Sample 自体が受け付け、撮影用の一時改変を構造的に不要にする
   - 指定キーは**安定デモ ID** (kebab-case、例 `basic-dialog`) を9デモぶん新設し、4ルートが各自同じ値を書く (ルート間でキー定義を共有しないのはパリティ規約の既存流儀)
   - **全ビルド構成で有効** (Release 除外なし)。引数を渡さない通常起動の挙動は不変が前提
   - デモ自動再生の担当は「起動〜表示まで」。自動再生はプロセスの起動につき1回だけ消費する (コールド起動前提。画面・Activity の再生成では再発火しない)
2. **撮影はエージェント手順で行う**: デモ駆動モードで状態を作り、撮影・残りの少数タップは simctl / adb / シミュレータ操作ツールで行う。`scripts/capture/` は作らない

ドキュメントの正は次のとおり配置する: kasane/config.yaml `ui.screenshot` はデモ駆動モード前提の撮影手順として書き直す (起票時の「スクリプト docstring へのポインタ化」は取り下げに伴い撤回)。安定デモ ID 14件とアプリ識別子の一覧は kasane/handbook/cross/sample-parity.md「撮影支援の起動引数」節が正。sample-parity.md に「撮影支援機構 (画面に出ない・引数なしなら挙動不変) はデモ項目の一致要件の枠外だが、機構そのものの外部契約 (キー名・安定 ID・不正値の倒れ方) は4ルート一致」の扱いを追記する。

## Alternatives Considered

- **受け口 = 環境変数**: 却下。Android にアプリへ環境変数を渡す標準手段がなく、4ルートのパリティが成立しない
- **受け口 = ビルドフラグ**: 却下。指定を変えるたび再ビルドとなり、「6アプリのビルドが最大コスト」という課題と正面衝突する
- **デモ指定キー = メニュー文言の流用**: 却下。文言修正が撮影手順の全修正になり、壊れたことに撮影実行まで気づけない。スペースを含み引用符も要る
- **デモ駆動モードを Debug 構成限定にする**: 却下。Sample は配布製品でなく守る対象がない一方、4ルート × 2構成の条件コンパイルが散る。一般公開後は利用者の検証機能としても価値がある
- **撮影スクリプト (`scripts/capture/` 単一入口 + 宣言的操作列)**: 起票時に採用したが実装フェーズで取り下げ。iOS シミュレータへの座標タップをスクリプトから注入する CLI 手段が環境に無く、成立させるには外部ツール導入 (idb 等) か XCUITest ランナー同梱が要り、いずれもオーナー判断で不採用
- **座標タップ全廃 (デモ側で結果確定まで自動進行)**: 却下。9デモ × 4ルートに撮影用シーケンサを作り込むことになり、公開予定のデモアプリが撮影都合で汚れる
- **文言検索ベースのタップ (座標を持たない)**: 却下。Android は UI ダンプで可能でも iOS シミュレータに同等の標準手段がなく、片側だけになる
- **ドキュメント追随を後続 change に分離**: 却下。旧手順メモと新しい受け口が並存し、次の撮影でどちらを信じるか迷うドリフトが始まる

## Consequences

- 正: 撮影用の一時改変 (刻み間隔延長・デモ先出し) が構造的に不要になり、復元事故の型 (verification-temp-edit-restore) が根絶される
- 正: 状態を作る手動タップの再現と、指定変更のたびの追加ビルドが消える (効率化の本体はデモ駆動モードが担う)
- 正: 撮影手順の正が config.yaml `ui.screenshot` (手順) と kasane/handbook/cross/sample-parity.md (デモ ID・アプリ識別子) に一本化され、手順再構築のコストが消える
- 負: 安定デモ ID という新しい4ルート一致対象が増える (デモ追加時は文言 + ID の両方を4ルートで揃える)
- 負: 表示後の少数タップ (結果確定等) と撮影はエージェント作業として残る (起票時に狙った「1コマンド化」はしない)。タップ座標は撮影時にスクリーンショットの画素から実測する
- 実装結果: sample-parity.md への枠外追記は実装と同時に実施済み。自動再生の one-shot 消費は4ルートとも「自動再生入口の先頭でプロセス単位のフラグを検査・消費」する構造で実現され、画面再生成での再発火をコードの形で防いでいる
