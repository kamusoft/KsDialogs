## Context

iOS の器は、SwiftUI で書かれた中身 (Dialog・Loading・Toast) をホストに載せて扱う。これまでのホストは、中身に安全領域を一切渡していなかった。器のレイアウト規則はすでに安全領域を基準領域として扱っている。ホストに安全領域の余白を足させると、中身が要求するサイズがその分だけ膨らむ。それを避けるための設定だった。

その結果、器の中の SwiftUI の中身から見ると、安全領域は常に 0 になる。中身が画面のどこにステータスバーやホームインジケータがあるかを知る手段は無かった。一方、UIView で書いた中身には、UIKit の通常の伝播で、器と安全領域の重なりが safe area として届くとみられる (未実測)。core/ADR-0011 は「中身を UIView と SwiftUI のどちらで書いても、観察できる挙動は同じ」としており、これと食い違っていた。

差が表に出るのは、基準領域を窓全体にして、画面の端まで広げた中身だけである。既定の基準領域 (可視領域) では、器が安全領域の内側に収まるため、重なりはもともと 0 になる。ColorAnalyzer の KMP 移植では、窓全体を覆う抽出ダイアログがこの形だった。中身は標準の SwiftUI と同じ意味のつもりで安全領域を無視する指定を付けていたが、実際には安全領域が 0 だった。そのため、アプリ側で窓の安全領域を直接読む回避策が要った。

前提: ホストに安全領域を渡しても、器のサイズ計算 (中身の要求サイズの決まり方) が崩れず、大きさが行ったり来たりしないこと。実装の時点で実測して確かめる。崩れた場合は、この ADR を代替案の「独自の値で渡す」案で書き直す。

## Decision

iOS の器に載せた SwiftUI の中身には、器と安全領域の重なりを、SwiftUI 標準の安全領域として届ける。中身は、安全領域を避ける・無視するといった SwiftUI 標準の書き方のまま、システムの領域を扱える。

範囲: SwiftUI で書かれた Dialog・Loading・Toast の中身。UIView で書かれた中身の扱いは変えない。器の配置とサイズの規則 (基準領域の決まり方) も変えない。

理由: 利用者が KsDialogs 独自の読み方を覚えずに、SwiftUI の標準の書き方で済むのが一番自然だから。UIView で書いた中身との見え方の差もなくなり、core/ADR-0011 の「技術によらず同じ挙動」に揃う。既定の基準領域では重なりが 0 のままなので、既定で使っている利用者の見た目は変わらない。

## Alternatives Considered

- **安全領域は 0 のまま、器と安全領域の重なりを KsDialogs 独自の値で中身へ渡す** — 却下 (前提が崩れた場合の代替)。既存アプリの見た目は変わらないが、利用者は KsDialogs 独自の値を読む必要がある。UIView の中身とは読み方が違うまま残る。公開 API が増え、Android 側とどう対応させるかも考える必要がある
- **安全領域が 0 になることを仕様として文書に書き、必要な中身は窓の安全領域を自分で読む** — 却下。コードの変更は要らないが、回避策がアプリごとに散らばる。UIView の中身との差も残る

## Consequences

- 正: SwiftUI の中身で、安全領域を避ける・無視するといった標準の書き方がそのまま効く。アプリ側で窓の安全領域を読む回避策が要らなくなる
- 正: 中身を UIView と SwiftUI のどちらで書いても、システムの領域の見え方が揃う
- 負: 基準領域を窓全体にして端まで広げた既存の SwiftUI の中身は、安全領域を無視する指定が無ければ、安全領域の内側へ寄るようになる (見た目が変わる)
- 負: 安全領域に重なる中身では、中身が要求するサイズに重なりの分が入りうる。器のサイズ計算がその入力の変化に耐える必要がある
