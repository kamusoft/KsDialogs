## Context

iOS の器は、SwiftUI で書かれた中身 (Dialog・Loading・Toast) をホストに載せて扱う。これまでのホストは、中身に安全領域を一切渡していなかった。器のレイアウト規則はすでに安全領域を基準領域として扱っている。ホストは受け取った安全領域を、自分が求めるサイズへそのまま足して答える。渡さない設定は、中身の要求サイズがその分だけ膨らむのを避けるためだった。

その結果、器の中の SwiftUI の中身から見ると、安全領域は常に 0 になる。中身が画面のどこにステータスバーやホームインジケータがあるかを知る手段は無かった。一方、UIView で書いた中身には、UIKit の通常の伝播で、器と安全領域の重なりが safe area として届いている。core/ADR-0011 は「中身を UIView と SwiftUI のどちらで書いても、観察できる挙動は同じ」としており、これと食い違っていた。

差が表に出るのは、基準領域を窓全体にして、画面の端に付けた中身である。既定の基準領域 (可視領域) では、器が安全領域の内側に置かれるため、移動量で寄せない限り重なりは 0 になる。ColorAnalyzer の KMP 移植では、窓全体を覆う抽出ダイアログがこの形だった。中身は標準の SwiftUI と同じ意味のつもりで安全領域を無視する指定を付けていたが、実際には安全領域が 0 だった。そのため、アプリ側で窓の安全領域を直接読む回避策が要った。

制約: 既定の可視領域で使っている利用者の見た目を変えない。安全領域を無視する指定の中身と、中央に置いた中身の大きさと位置も変えない。ホストに安全領域をそのまま渡すと、ホストの答えに重なりが足される。そのため、上端・下端に付けた器は重なりの分だけ大きくなり、無視する指定の中身でも外形と位置が変わる。中央に置いて安全領域に重なる中身は、置き直すたびに重なりが増えて窓の大きさまで膨らむ。

前提: ホストの答えから、ホストが受け取っている安全領域を引き戻せば、安全領域を受け取らないときと同じ要求サイズが得られる。

## Decision

iOS の器に載せた SwiftUI の中身には、基準領域が窓全体で、レイアウトの解で位置が端 (前端・後端) に固定される軸について、器と窓の安全領域の重なりを SwiftUI 標準の安全領域として届ける。器へ伝える要求サイズは、安全領域を受け取らないときと同じ値にし、受け取った重なりを器の大きさへ戻さない。中身は、安全領域を避ける・無視するといった SwiftUI 標準の書き方のまま、器の内側でシステムの領域を扱える。

範囲: SwiftUI で書かれた Dialog・Loading・Toast の中身 (KMP の Swift 面から登録したものを含む)。届けるのはシステムの領域 (ステータスバー・ホームインジケータ等) だけで、キーボードの領域は含めない。含めると既定の可視領域でもキーボードを避けて中身が動き、UIView の中身とも揃わないためである。位置が中央に固定される軸と、窓全体以外の基準領域 (移動量でシステムの領域に重なる場合を含む) では、今と同じく渡さない (0)。UIView で書かれた中身の扱いと、器の配置とサイズの規則は変えない。

理由: 利用者が KsDialogs 独自の読み方を覚えずに、SwiftUI の標準の書き方で済むのが一番自然だから。窓全体基準で端に付けた中身では、UIView で書いた中身との見え方の差がなくなり、core/ADR-0011 の「技術によらず同じ挙動」に揃う。渡す範囲を端の軸に絞り、要求サイズに重なりを入れないことで、器の大きさと位置はどの配置でも変わらない。既定の可視領域・無視する指定の中身・中央の中身の見た目を変えずに済む。窓全体以外の基準領域では、器はすでにシステムの領域を避けて置かれているので、移動量で重なった分は利用者が選んだ寄せ方として扱う。

## Alternatives Considered

- **ホストに安全領域をそのまま渡し、重なりの分を要求サイズに入れる** — 却下。上端・下端の器が重なりの分だけ大きくなり、無視する指定の中身でも外形と位置が変わる。中央に置いて安全領域に重なる中身は窓の大きさまで膨らむ
- **要求サイズには入れないが、中央に固定される軸にも重なりを渡す** — 却下。中央に置いて安全領域に重なる中身が、器の中で動く
- **基準領域を問わず、端の軸で重なりがあれば渡す (可視領域で移動量により重なった場合を含む)** — 却下。既定の可視領域で使っている中身の見た目が変わる
- **安全領域は 0 のまま、器と安全領域の重なりを KsDialogs 独自の値で中身へ渡す** — 却下。既存アプリの見た目は変わらないが、利用者は KsDialogs 独自の値を読む必要がある。UIView の中身とは読み方が違うまま残る。公開 API が増え、Android 側とどう対応させるかも考える必要がある
- **安全領域が 0 になることを仕様として文書に書き、必要な中身は窓の安全領域を自分で読む** — 却下。コードの変更は要らないが、回避策がアプリごとに散らばる。UIView の中身との差も残る

## Consequences

- 正: 窓全体基準で端に付けた SwiftUI の中身 (窓全体を覆う中身を含む) で、安全領域を避ける・無視するといった標準の書き方がそのまま効く。アプリ側で窓の安全領域を読む回避策が要らなくなる
- 正: 器の大きさと位置は、中身が受け取る安全領域に左右されない。既定の可視領域・無視する指定の中身・中央の中身の見た目は変わらない
- 負: 窓全体基準で端に付けた既存の SwiftUI の中身は、安全領域を無視する指定が無ければ、器の内側で安全領域を避けて寄る。器は大きくならないので、中身が使える大きさは重なりの分だけ減る
- 負: 中央に固定される軸と、窓全体以外の基準領域では、UIView の中身 (重なりを受け取る) と SwiftUI の中身 (0) の差が残る
- 負: 要求サイズはホストの答えから受け取った安全領域を引き戻して求めるので、器はホストの答えをそのまま使えない。中身の大きさの変化に器が追従することは、器の側で保つ必要がある
