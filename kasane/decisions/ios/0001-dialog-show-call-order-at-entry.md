## Context

core/ADR-0041 で、提示先が無いまま呼ばれた Dialog は提示先の出現を待つことになり、待っている Dialog が複数あれば呼んだ順に出す (後から呼んだものが手前) ことになった。ライブラリは待っている Dialog を列で持ち、列に並んだ順に 1 枚ずつ明ける。ただし、どの時点の順を「呼んだ順」とするかは決まっていなかった。

iOS の `Dialog` の show は、実行文脈の指定の無い async 関数だった。UI スレッドから呼んでも、いったん大域の実行器へ移ってから UI スレッド (MainActor) の提示処理へ戻るので、A、B の順に呼んでも列に B、A の順で並ぶことがあった。A、B の順に呼ぶと A、B の順に表示するという契約を満たさないことが、実測で分かった (300 回中 6〜14 回)。UI スレッドへ移るのに Task を作る入口 (KMP の iOS 互換面・MAUI の iOS ブリッジ) では、列の順が Task の開始順だけで決まっていた。

show の入口には、利用者が DI で受け取るための公開プロトコル `KsDialog` がある。利用者はこれに自前の型を準拠させることもできる。ライブラリは `0.1.0-beta` として公開済みである。

前提: 公開プロトコルの要件に実行文脈の指定を付けても、外部の準拠型はソースを変えずにコンパイルできる (Swift 6・Swift 5 の言語モードほか 3 設定 × 準拠型 4 種で実測)。

## Decision

同じ UI スレッドから続けて呼んだ Dialog の show が、呼んだ順のまま待ちの列に並ぶことを、iOS の show の入口で保証する。そのため、show は呼び出し元の実行文脈のまま走らせる。`Dialog` の show 群に加えて、公開プロトコル `KsDialog` の要件と拡張にも同じ指定 (`nonisolated(nonsending)`) を付ける。UI スレッドへ移るのに Task を作る入口は、呼び出しの時点で同期に列の順番札を取り、札の順で列に並ぶ。

範囲に含めないもの: 別々のスレッドからの呼び出しどうしの順は定めない。

理由: 表示の順番を列で明示しても、列に着くまでの間に順が入れ替われば「呼んだ順」は保てない。入れ替わりは、UI スレッドから呼んだ show が UI スレッドを離れることと、Task の開始順に頼ることから生じる。呼び出し元の実行文脈のまま走らせれば、UI スレッドから呼んだ show は UI スレッドを離れずに列まで進む。公開プロトコルの要件まで指定を揃えるのは、DI で `KsDialog` として受け取った呼び出しでも同じ順を保つためである。Task を作る入口は、Task の開始順に左右されない時点 (呼び出しの時点) で順番を決める。

## Alternatives Considered

- **show の実行文脈の指定を変えない (テストの側で呼び出しの間に待ちを挟んで安定させる案を含む)** — 却下。UI スレッドから続けて呼んだ show でも、列に並ぶ順が入れ替わり、呼んだ順に表示する契約を満たさない
- **show 群を UI スレッド専用 (`@MainActor`) にする** — 却下。順序は保てるが、公開プロトコルの隔離が変わり、利用側のコンパイルに影響するおそれがある
- **`Dialog` の実装と拡張だけに指定し、公開プロトコルの要件は変えない** — 却下。DI で `KsDialog` として受け取った呼び出しでは、順が崩れる (実測で 500 回中 197 回)
- **Task を作る入口は、Task の開始順に頼る** — 却下。実測では開始順は安定していたが、言語の保証が確認できず、iOS 17 の実行環境でも確かめられていない

## Consequences

- 正: UI スレッドから続けて呼んだ show は、具体型経由でも `KsDialog` 経由でも、Task を作る入口経由でも、呼んだ順に列へ並び、呼んだ順に表示される
- 負: 公開プロトコル `KsDialog` の要件の呼び出し規約が変わる。準拠型を含むバイナリを配る利用者は、組み直しが要る
- 負: 今後 iOS に Dialog の show の入口を足すときは、同じ指定が要る。UI スレッドへ移るのに Task を作る入口は、順番札を取る必要がある
- 負: 別モジュールの呼び出し口 (MAUI の iOS ブリッジ) が順番札を取るには、利用者向けの公開面の外に口が要る
- 負: 別々のスレッドから呼んだ show の順は保証されない
