## そちらに関係する理由

`overlap` の `.github` / `scripts` / `skills` すべてに掛かる。加えて、**そちらの構成でも同じ形で現れうる穴**を
2 つ見つけた (下記「提案する対応」の 1 と 2)。

## 1. 公開待ちの自己テストが「停止」で表れる穴 — そちらにもある可能性が高い

こちらの `central-portal.sh` の自己テストは、**待機の止まらない誤実装を失敗ではなく停止として表す**状態だった。
機構はこうである。

- 期待が「失敗」の検査は `if ( ... )` の条件で呼ぶため、その中では `set -e` が働かない
- 台本が尽きたモック応答を呼び出し側が状態として扱うと、巡回が既定の上限 (90 分) まで空回りする
- 結果、終端の状態 (`FAILED` / `NOT_FOUND`) を終端として扱わない誤実装を与えても、自己テストは
  NG ではなく「終わらない」形になる

塞ぐのに 3 サイクルを要した。**1 種類の誤実装を塞ぐと別の同型が残る**ためで、最終形は二層になった。

| 層 | 内容 |
|---|---|
| 内側 | `cmd_wait_published` が、状態を取り出せなかった ID を待機対象に残さず失敗させる |
| 外側 | 公開待ちを回す検査に、期待の成否によらず短い上限を与える |
| 対 | 上限に達したことだけでは「上限が効いた」と「終端を取りこぼして台本を使い切った」を区別できないので、照会回数の表明を添える |

内側を入れた直後、**上限判定を丸ごと外しても自己テストが緑になる**という後退が起きた (上限を名乗る検査が、
上限ではなく内側の層で通っていたため)。照会回数の表明を足して両方向を押さえた。

検証は誤実装のスイープで行った。最終的に `central-portal.sh` に 18 種・`wait-for-registries.sh` に 7 種の
単一誤実装を注入し、停止 0 件・19 種が NG であることを確認している。

**そちらの `central-portal.sh` にも同じ構造があるなら、同じ穴が open のはず。** 確かめ方は単純で、
`PUBLISHED` を待機対象から外さない / `FAILED` を終端として扱わない、といった誤実装を 1 箇所だけ入れた写しで
`--selftest` を回し、**タイムアウトするか NG が出るか**を見ればよい。

## 2. publish の時間予算 — こちらは「最悪ケースを収容しない」を選んだ

そちらの Requirement は「publish の実行時間の上限は各項の合計以上である」だが、こちらはこれを**採れなかった**。
Maven Central の枠が Android / KMP の 2 つあるためである。

| 項 | そちら (枠 1) | こちら (枠 2) |
|---|---|---|
| 待機の上限 | 検証 30×2 + 公開 90 = 150 | 検証 30×**4** + 公開 90 = 210 |
| 各待ちの最後の照会 | 5×3 = 15 | 5×**5** = 25 |
| 巡回間隔の端数 | 2 | 3 |
| 待機外の照会 | 5×6 = 30 | 5×**14** = 70 |
| 本体処理 | 20 | 16 |
| **合計** | **217 ≤ 240** | **324** |

余裕を足すと 350 分前後で、GitHub Actions の job 実行時間の上限 360 分に対して余裕が残らない。
そこで **「公開待ちと本体処理を収容し、検証の決着待ちは予算外」** とし、`timeout-minutes` は 150 のまま据え置いた
(公開待ち 90 + 最後の照会 5 + 端数 1 + 本体 16 = 112 ≤ 150)。検証は枠ごとに数秒〜数分で決着するのが常態で、
deployment ID は upload 直後に artifact へ保存されて次の試行が引き継ぐため、超過時は打ち切って再実行に回す方が
安全側に倒れる、という判断である。

機械検査 (`check-time-budget.py`) はそちらの構造を写しつつ、publish 側の式だけこの形にしてある。
**反映待ち job の側はそちらと同じ式**で検査できた (待機の上限 + 期限を跨げる照会 1 件の応答上限 + job の前後)。

そちらは枠 1 つで 240 分に収まっているので直す必要はない。ただし将来 KMP 枠を足すなら、この壁に当たる。

## 3. インストール例の lint — 宣言が `SKILL.md` の外にもある構成

こちらは対象が 16 ファイル・28 行で、そちら (10 ファイル・14 行) と違う点が 2 つあった。

- **`references/` にも宣言がある** — KMP の Skill がホスト別の手順を `references/android-host.md` と
  `references/ios-host.md` に分けており、そこにも依存宣言がある。そちらの lint は対象表も構造の突合も
  `skills/{en,ja}/*/SKILL.md` のパターンだけを見るので、この形だと `references/` を取りこぼす。
  こちらは**インストール宣言を持つ文書すべて**を列挙して対象表と突き合わせる形にした
- **散文の中にも宣言がある** — コードブロックの再掲や手順の 1 行目に依存宣言が現れる箇所が 4 行あった。
  これも `{version}` にしたが、走査はコードブロック内に限るので契約の検査は掛からない。
  そのため、散文の宣言の一覧を持ち、**コードブロックの外にその宣言が実在すること**だけを検査する形を足した
  (値は見ない)。一覧が腐っても誰も気づかない状態を避けるため

## 4. `## Changes` の必須化で、マージ済みの pull request に後から追記が要る

実際に起きた。前回の Release 以降に `main` へ入っていた pull request (こちらは #3) が `## Changes` を
持っておらず、そのままだと本番の validate で止まる状態だった。マージ前に気づけたので、その pull request の
本文に `- none` を追記して解消した (ノートは実行時の本文を読むので、マージ済みでも直せば反映される)。

そちらは既に `0.1.0-beta.3` を出しているので通過済みかもしれないが、**方式を導入した最初のリリースでは
必ずこれが起きる** (それ以前の pull request は誰も `## Changes` を書いていないため)。
手順書の失敗時の表にこの経路があると、当日の手戻りが小さい。

## 提案する対応

- **1 の穴の確認**を勧める。誤実装を 1 箇所入れた写しで `--selftest` を回し、停止するか NG が出るかを見るだけで済む。
  停止したなら、内側 (答えの返らない照会を待機対象に残さない) と外側 (短い上限) と照会回数の表明の 3 点セットで塞げる
- **2 は直す必要がない**。枠が 1 つなら現行の形で収まっている。KMP 枠を足すときに思い出せばよい
- **3 と 4 は構成依存**。そちらの `skills/` が `SKILL.md` だけなら 3 は当てはまらない
