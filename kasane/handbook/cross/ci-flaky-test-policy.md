# 状態遷移の観測と CI 限定スキップ

この文書は、実機・Emulator・Simulator の上で OS 側の状態遷移 (IME の出し入れ・ウィンドウの追加と入力の宛先・器の出入りの演出・画面の再生成) に触れるテストの**観測の仕方**と、それでも CI でだけ落ちるテストの**切り分けと skip の許容条件**を定める。読むと、間欠失敗を待ち時間の延長でごまかさずに済み、どこまでが直す対象でどこからが CI 限定 skip の対象かが判断でき、skip を付けるのに何が要るか (切り分けの実測とオーナー承認) が分かる。

CI が回す範囲と job ごとの実行条件は [検証 CI の範囲と実行条件](verification-ci.md) が持つ。実行コマンドと件数の得方は [テスト実行規約](test-execution.md) が持つ。

## 観測は終端状態の合意を待つ

**単一のフラグや、アサーション時点の 1 回の読みだけで状態遷移の完了を判定しない。** 遷移の途中には終端状態と見分けのつかない一瞬がある — 要求だけが先に切り替わる窓、器が取り付いてから入力の宛先が切り替わるまでの隙、アニメーションが折り返す瞬間。その一瞬を「終わった」と読んで先へ進むと、続く操作が「もう終わっている」として捨てられ、待ちが無音のまま時間切れになる。

判定は次の 3 つを揃えて行う。

| 要素 | 内容 |
|---|---|
| 合意 | 独立した複数の観測 (要求上の見え・実際に占める枠・入力の宛先) が目的の終端状態で一致する |
| 非進行 | その遷移を動かしているアニメーション・演出が走っていない |
| 安定 | 上の 2 つが数フレーム分の時間、続けて成り立つ |

この待ちは共通プリミティブとして置き、テストごとに書き起こさない。面ごとの置き場は次のとおり。

| 面 | 落ち着き待ち | 観測履歴 |
|---|---|---|
| Android instrumented | `InstrumentedStateSettling.awaitSettled` (IME 版は `ImeSettleWaiting`) | `StateHistory` |
| iOS | `DialogTestWaiting.awaitSettled` | `DialogTestStateHistory` |
| MAUI iOS 橋渡し | `BridgeTestWaiting.awaitSettled` | `BridgeTestStateHistory` |

何を独立した観測と見なすかは面ごとに違うので、合意と非進行の組み立ては呼び出し側が渡し、プリミティブは**安定** (成り立ち続けること) と履歴を受け持つ。時間切れの説明文には、単調時計付きの観測履歴を添える — 失敗した回に何が起きていたかは事後には読めないため。

**通り過ぎる一瞬 (「出の途中」のような中間状態) をポーリングで捕まえない。** 観測したい中間状態が環境の設定 (端末側のアニメーション無効化など) で 0 秒に縮む可能性があるなら、その状態をテスト側の仕掛け (完了を押さえる演出フック) で確定させる。捕まえられなかった回を「起きなかった」と読み替える形は作らない。

**「起きない」ことの確認には履歴を使う。** 「表示されない」「増えない」「その 1 つだけが破棄される」は、アサーション時点の顔ぶれではなく、要求から観測までの間に一度でも起きたかを記録した履歴で見る。

## CI でだけ落ちるテストの切り分け

CI の赤が間欠的なとき、待ち時間の延長や観測点のゆるめ方で吸収する前に、次の順で切り分ける。

1. **検証機の負荷を実測する。** load average と居座りプロセスを確認し、汚染があれば掃除してから測り直す (汚染下の失敗率を根拠にしない)
2. **落ちた assertion が遷移途中の状態を読んでいないか見る。** 読んでいれば上の規律で観測を直す。ここで直るものは skip の対象ではない
3. **手元で反復する。** 同じテストを 10 回以上、CI と同じ実行条件 (アニメーション無効・同じ API レベル) で回し、失敗の有無を記録する
4. **手元で落ちるなら直す。** CI 限定 skip の対象にしない
5. **手元で通り CI で落ちるなら、重要度で振り分ける** (次節)

CI の赤が実行機の容量差 (並列スイートの飢餓) によるものかは、[検証 CI の範囲と実行条件](verification-ci.md) の見分け表で判定する。飢餓なら skip ではなく実行条件 (直列化) で対処する。

## CI 上だけ skip してよい条件

次の 3 つを**すべて**満たすときに限り、CI 上だけ実行しない扱いを許容する。

- 手元の反復で通る (前節 3 の実測がある)
- CI では落ちる (落ち方が記録されている)
- 重要な機能のテストでない

**重要な機能のテスト**とは、公開契約の保証そのものを固定する Scenario を指す — 入力を遮る・遮らない、通知がちょうど 1 回届く、結果が呼び出し元へ返る、といった利用者が依存する振る舞い。前提の成立確認や環境のタイミングに依存する観察はこれに当たらない。重要な機能のテストは、手元で通っても skip せず観測か実行条件で直す。

### 先に試すことが決まっている

3 条件の判定に入る前に、次の順序を守る。順序を飛ばした skip は、直せる欠陥を隠したまま固定する。

1. **観測を直す** — 終端状態の合意を待つ形へ書き換える。それで手元の反復が通るなら、その修正で終える (skip は不要)
2. **手元で落ちるものは候補にしない** — 環境の揺らぎではなく欠陥なので、直す
3. **機構を診断する** — 「なぜ CI で落ちるか」を実行機の観測 (logcat・テスト結果の失敗形・負荷) で言えるようにする。**診断のない skip は禁止**する

## skip はオーナーの承認で決まる

skip を付けるのは、エージェントの判断ではなくオーナーの承認である。手順は次の 4 段で、順番を入れ替えない。

1. 切り分けの実測 (手元の反復・CI の落ち方・機構の診断) を change の `evidence/` に残す
2. 実測を添えてオーナーに判断を依頼する
3. オーナーが `kasane/config.yaml` の `lint.ci-skip.allow` に項目 (`test` / `mechanism` / `approved` / `review-by`) を足す — **これが承認**にあたる
4. 承認された後にコードへ印を付ける

`test` に書く値は `python3 scripts/ci-skip-lint.py --list` が表示する識別子をそのまま使う。入れ子の型 (`extension Foo { struct Bar }`) では見た目の suite 名と解決される識別子が食い違い、手で書くと承認済みなのに対応が付かない。

許可リストに無い印は `scripts/ci-skip-lint.py` が落とす (lint job の検査の 1 つ)。理由の文字列が切り分けの 3 要素を欠いていても、許可リストの項目が `mechanism` を欠く・`approved` が無い・未来日でも落ちる。

**許可リストの追加はオーナーの操作である。** エージェントが印と許可リストの項目を同じ回に自分で書けば lint は通るため、機械の歯止めはここまでしか及ばない。エージェントの diff に `lint.ci-skip.allow` の追加が含まれる場合は、`deviation.md` にオーナー指示の記録 (日付と指示の要旨) を残す。記録が無ければレビューは CHANGES_REQUESTED にする。

## skip の書き方

skip は次の仕組みで書く。どちらも判定材料は **CI 側が明示的に渡す値**で、実行機が持つ汎用の CI 環境変数には頼らない (手元で意図せず skip されないため)。

| 対象 | 仕組み | CI 側が渡すもの |
|---|---|---|
| Android instrumented | `@SkipOnCi(reason = ...)` と `SkipOnCiRule` | 実行引数 `ksdialogsCi=true` |
| iOS / MAUI iOS 橋渡しの Swift | trait `.skipOnCi(...)` | 環境変数 `TEST_RUNNER_KSDIALOGS_CI=1` |

skip は前提の不成立として起こし、結果に skipped として数えられる形にする。実行数を「tests から skipped を引いた数」で見る件数検査は、skip した分を実行済みとして数え上げない。

ただしこの件数検査が落ちるのは実行数が 0 になったときだけで (`.github/workflows/verify-android-instrumented.yml` の `executed <= 0`、Swift 側は合算 0 件)、**skip が 1 件増えたことは検出しない**。件数検査は「テストが丸ごと空振りした」ことの歯止めであって、skip の増加に対する安全網ではない。

### 正規の印以外の手段で実行から外さない

**上の 2 つ以外の書き方で、テストを CI の実行から外さない。** 具体的には Kotlin の `@Ignore` (`@org.junit.Ignore` / `@kotlin.test.Ignore` を含む)、Swift の素の `.disabled(...)` / `.enabled(if:)` / `XCTSkip` 系、NUnit の `[Ignore(...)]` / `Assert.Ignore(...)` / `Assert.Inconclusive(...)`。これらは承認手順を一切通らずに赤を消せてしまい、結果では skipped に数えられるため件数検査も素通りする — 承認された道より安く、痕跡も残らない出口になる。`scripts/ci-skip-lint.py` は許可リストとの突き合わせを持たず一律で違反にする (正規の印を組み立てるヘルパ自身の定義だけが対象外)。

この検査は **CI が回すテストルートすべて**に掛かる — 正規の印を置ける 3 つ (Android instrumented・`ios/Tests/`・MAUI iOS 橋渡し) と、印の仕組みを持たない 4 つ (Android のローカル単体テスト `src/test/`・kmp のテストソースセット・MAUI の NUnit・MAUI Android 橋渡しの Kotlin JVM テスト `maui/android/native/**/src/test/`)。**印を置く場所が無いことは、そこで `@Ignore` を使ってよい理由にならない。** 実行機の揺らぎを持たないルートで CI 限定 skip が要る事態は、まず前提の置き方を疑う。

照合はコードの本文だけを見る (コメントと文字列リテラルの中身は落とす) ので、規約の引用や説明文に書かれた語は拾わない。Swift の `.disabled(...)` / `.enabled(if:)` は `@Test(...)` / `@Suite(...)` の引数並びにある分だけを見る — 同じ綴りが SwiftUI の修飾子として正当に現れるため。

一方、**前提条件の表現は skip ではない**ので対象にしない。JUnit の `Assume` / `assumeTrue`、NUnit の `Assume.That(...)`、Swift の `#require` による早期打ち切りは、「この API レベル・この実行環境では検証が成立しない」という判定材料の不在の宣言であり、成立する環境では必ず実行される。判定の境目は「CI かどうかで実行を分けているか」であって、結果が skipped になるかどうかではない。

理由の文字列には、切り分けの 3 条件の根拠を**そのファイルだけで意味が通る形**で書く。作業文書のパス・run 番号・変更識別子は書かない ([ソースコメント規約](comment-policy.md))。

- 手元の反復で通ること (回数を添える)
- CI での落ち方 (どの assertion が何になるか)
- 重要な機能のテストでないと判断した理由

## 期限と棚卸し

skip したテストは残り続ける前提で置かない。許可リストの `review-by` (既定は承認日の 90 日後) を過ぎた項目は lint が警告として出し、乖離の棚卸しで再評価する — 実行条件 (ランナーの容量・API レベル・観測の仕組み) が変わって外せる根拠が出たら、印と許可リストの項目を同時に外す。

## レビューでの照合

skip の追加を含む変更のレビューは、次の 4 点を確認する。1 つでも欠けていれば指摘する。

- 許可リストとの対応 — 印の付いたテストが `lint.ci-skip.allow` にあり、`approved` / `review-by` が入っている
- 承認の出どころ — 許可リストの追加が diff にあるなら、`deviation.md` に対応するオーナー指示の記録がある (無ければ CHANGES_REQUESTED)
- 実測 — 手元の反復と CI の落ち方が `evidence/` にあり、理由の文字列と食い違わない
- 機構の診断 — なぜ CI でだけ落ちるかが観測で説明されている (「環境の揺らぎ」だけの説明は診断ではない)

あわせて、diff に正規の印以外の無効化手段 (`@Ignore`・素の `.disabled(...)` 等) が入っていないかを見る。lint が落とすので通常は届かないが、走査根の外 — テストの置き場でないコード (`samples/**`・ビルドスクリプト) と、上の 7 ルートに当たらない置き場に新設したテスト — は検査されない。テストルートを増やしたら `scripts/ci-skip-lint.py` の `SCAN_ROOTS` にも足す。

## なぜ歯止めを機械で持つか

skip は、直せない失敗と直せる失敗の区別がつかないまま赤を消せてしまう手段であり、作業を進める側にとって常に最短の出口として見える。規約文だけでは「今回は例外」の判断が積み上がるため、承認をオーナーが書く許可リストという形にして、lint が対応の無い印を落とす。
